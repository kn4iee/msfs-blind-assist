# BlueBird 757-200

BlueBird Simulations' 757-200, package `bluebirdsim-aircraft-757-200` (release 0.1.0), with the Pratt &
Whitney and the Rolls-Royce engines. Profile "BlueBird 757-200", code `BBS_757`, chosen from the Aircraft
menu like every profile. Rules: `.claude/rules/b757*.md`, loaded when their code is read; their full text is
`docs/invariants/b757*.md`. Every measurement this document relies on is stated here, with its date and how
it was made: the simulator was MSFS 2024 with BBS Nest running unless a line says otherwise.

How the aircraft is reached, in short. Its cockpit controls are L:vars written by replaying the vendor's own
click code through the MobiFlight calculator ([How it writes](#how-it-writes)). Its CDU screens are text on
the simulator's Comm Bus, read through the Coherent debugger ([CDU](#cdu)). Its tablet and its CRT displays
are drawn inside the aircraft's WASM module with no text behind them, so they are read from that module's
memory, read-only ([The 757 EFB](#the-757-efb-shiftt), [Displays read from memory](#displays-read-from-memory),
[wasm-memory.md](wasm-memory.md#the-bluebird-757-module)). Nothing works unless
[BBS Nest](#bbs-nest) runs.

## The control map

`MSFSBlindAssist/Resources/bbs757_control_map.json` is generated from the installed package and never
hand-edited: regenerate it after a BlueBird update. It is an embedded resource, loaded once by
`Bbs757ControlMap.Load` (a missing or malformed resource gives an empty map and a logged error, never an
exception). Today it holds **439 controls** (159 toggles, 153 buttons, 82 switches, 26 held buttons, 19
guards) on 65 panels, and 8 status rows, from package release 0.1.0.

### The generator

`python -I tools/b757-gen/generate_b757_map.py [<package folder>] [--out <json>] [--curation <json>]`
finds the package in `Community` or `Community2024` under the simulator's `LocalCache\Packages` when no
folder is given, and reads the package only. Its tests need no aircraft:
`python -I tools/b757-gen/test_generate_b757_map.py` (stdlib `unittest`).

- **`extract_controls.py`** expands the vendor's templates in the cockpit behavior XML
  (`BBS_752_BASE_INTERIOR.xml` and what it includes) and classifies every interactive control: its kind,
  the click code of each mouse action, its state code, its tooltips, the vendor's banner comment it sits
  under, and `_component_vars`, the L:vars the control's whole component reads and writes. For release
  0.1.0 it lists 1,231 controls, 511 of them circuit breakers and 138 CDU keys. The sim's own templates
  are not in the package, so their parameters are taken as the control.
- **`generate_b757_map.py`** turns those rows into the map. Derived: the kind, the state var, the
  positions (from the clamps in the turn code, or one tooltip per position), the click code, a held
  button's hold (the template's `MIN_HELD_DURATION`, else 1500 ms), the section (the node's prefix:
  `B757_OVHD_` Overhead, `B757_MCP_` Glareshield, `B757_MAIN_`, `B757_ADI_` and `B757_HSI_` Forward panel,
  `B757_PED_` Pedestal, anything else Other) and a label made from the node name. Everything the XML cannot
  say is in `curation.json`. The vendor's tooltip titles are never labels: they were copied between
  controls (every window heat button is titled "Anti-ice Window").
- **`rpn_replay.py`** is a small RPN interpreter for the subset the cockpit's click code uses, so the
  tests can replay a click offline (below).

Each control carries `node`, `section`, `panel`, `label`, `kind` (`toggle`, `switch`, `button`, `held`,
`select`, `guard`), `state_var`, `positions` (`value`, `label`), `press`, `release`, `hold_ms`, `cw`,
`ccw`, on a guarded control `guard`, `guard_closed` and `close_sets`, and `variant` (`pw`, `rr` or null).
`press`, `release`, `cw` and `ccw` are the cockpit's own click code, verbatim: the app replays exactly
what a click runs, so a slip the cockpit has stays in the replay. Code that looks like a slip is only
reported (`suspected_slips`): eight fuel pump and crossfeed buttons whose press ends in a set with no
`L:` in front, and the first officer's right DDRMI switch, whose press ends in a closing brace nothing
opened. Measured 2026-10-26 and 2026-10-28 through the calculator: the sim runs such a click up to the
slip (L Pumps FWD went off and on, its `_ON` legend write was lost; the DDRMI switch toggled 0 to 1).

### What is left out, and the cockpit rule

`drop_reason` is the one place a row is dropped, judged on the row as the extractor read it, so no
label, position or kind entry brings back a control the rules drop. In order: an excluded banner (unless
the node is under `include_nodes`), an excluded node, a kind the map has none for (circuit breakers, CDU
keys, levers, infinite knobs), a finite knob with more than 12 positions or none countable, no click
code, a state that is not an L:var, and last the cockpit: **no cockpit node**. The second row of a node
the PW and RR interior files repeat is dropped as a duplicate.

- **The cockpit rule.** BlueBird ships six interior models (a PW and an RR cockpit, each also as an AWE
  and a no-cab variant), which agreed on every control node when compared on 2026-10-26. A control can be
  clicked only where the model has a node of its name, so the run reads the node names of
  `BBS_752_PW_INTERIOR.gltf` and `BBS_752_RR_INTERIOR.gltf` (it stops when either is missing, found twice
  or holds no named nodes) and leaves out every control neither has: a switch the cockpit lacks is noise
  to a pilot who cannot find it. 22 controls went this way: a second EICAS Computer knob, the five ADF
  panel switches (so there is no ADF panel), the right weather radar test button, eleven P6 display and
  event buttons, guards 13 to 15 and the P61 panel guard. BlueBird's published variable list has a row for
  20 of them, but a row is a variable the XML declares, not a control in the cockpit, so
  `keep_without_node` stays empty.
- **`(PW)` / `(RR)`.** A control only one model has gets that suffix on its label (unless the label
  already ends so) and `variant` `pw` or `rr`: the PW fuel control switches, and on the RR its fuel
  control switches, the two ELEC ENG Cont switches and their guards. A label that names the wrong variant
  stops the run.
- **Left out on purpose.** The 511 circuit breakers and the CDU keys (banners). Infinite knobs: the MCP's
  value knobs, the radio, ADF and transponder tuning knobs, the altimeter knobs, the EFIS minimums knob
  and the landing altitude knob (the app sets those values through its own windows and fields). The four
  weather radar knobs: nothing in the package reads them (no gauge, no WASM code; the navigation display
  draws no weather radar), so no position means anything. The yoke trim switches. The manual cabin
  altitude switch and the eight P61 test switches (`exclude_nodes`): they are spring-loaded, so the app
  gives them held buttons instead (below); the eighth, the duct leak / fuel quantity test switch, gets no
  button either, because nothing in BlueBird reads its var and holding it at 0 and at 2 changed no
  variable (measured on the ground with BBS Nest running, 2026-10-28). The nodes named
  `B757_PFD_1/2_SCREEN_KNOB`, which write raster vars nothing reads ([B757-16]). The thrust levers and
  reversers (banner `THROTTLES MAIN`): the map has no thrust lever control and the app no thrust panel;
  only the left TO/GA button and the A/T disconnect are taken in from that banner.
- **Kept though it does nothing:** ALT SEL Push stays on the MCP panel under its cockpit name. It changed
  nothing in a VNAV climb (2026-10-28) or a VNAV step climb (2026-10-29), and no BlueBird manual describes
  altitude intervention, so no window offers it.

### The curation keys

`tools/b757-gen/curation.json`. An unknown key, an entry for a node the package does not have, and an
entry that does nothing are errors (`CurationError`), so a stale entry never hides. Its `_notes` hold the
evidence for each entry; the facts they lean on are restated at the end of this section.

- `exclude_banners`, `exclude_nodes`: what is left out.
- `include_nodes`: single controls taken in from an excluded banner; the banner stays excluded. Each
  must be placed by a `node_panels` rule, or the run stops (it would land on a panel named after the
  excluded banner).
- `panels` (vendor banner to panel name, or `{name, section}`) and `node_panels` (the first matching
  `{banner?, prefix?}` rule wins and gives `{panel, section?}`): where a control goes. A banner with no
  entry is not guessed: the run prints it.
- `labels`, `spelling` (vendor words repaired: CENTRE, GAURD, VHFL), `positions` (names in value order,
  laid onto the control's own values, or explicit `{value, label}` pairs when the click code never rests
  on a value the extractor counts: the start selectors never write 2, the chronometer ET lever skips it).
- `kinds`: two re-readings only. A momentary button made a `toggle` (the APU fire handle: its click sets
  its own state var by a gate, not a flip) and a select made a `button` (the 14 audio microphone selects:
  a press selects that microphone and clears the panel's other six, so a combo could never reach Off).
- `guarded` (`state_var`, `positions`, `guard`, `guard_closed`, `close_sets`): a switch whose vendor
  click runs only while its guard is open (the emergency lights switch, the two stab trim cutouts). The
  extractor writes that gate as an `[if <test>] ` note in front of the click code, which is not RPN, so
  none of the click is kept [B757-6]. The entry is checked against the vendor's code: the click writes
  `state_var`, its gate reads the guard's var, and the guard's own click writes `close_sets` to the
  control. The guard keeps its own row.
- `direct_write`: switches whose click code the map leaves out, written through their state var
  [B757-14]. The chronometer ET levers (the clockwise code lowers the value and the anticlockwise code
  jumps HOLD straight to RESET, so a step can land on 2, which is no position) and the flight deck door
  switch (its two codes write 2 and 0 whatever it reads, so a step to Auto from one end landed on the
  other). `check_direct_write` stops the run unless the click writes nothing but the state var and
  `O:` vars: another L:var, a K: or H: event or a gate note would be lost.
- `levers` (`state_var`, `{value, label}` positions): a drag handle, which has no click code a pick
  could replay, built as a switch written through its state var: the gear and flap levers, the sun
  visors' tracks, the headrests, the stowage doors. Also the two seat levers, the one case of a control
  the rules keep: their click writes only `O:` vars, which the sim's calculator cannot set, so the entry
  writes the var the component moves. The state var must be one the lever's component reads or writes,
  and each position must lie in the range the lever's own code clamps to.
- `direct_positions` (the same form): a knob the rules drop that a combo can drive: Auto Rate, the three
  zone temperature selectors, the eight display brightness knobs. Nothing of the click code is kept, so
  the positions are not held to its clamp.
- `hold_ms` (node to 500-10000 ms): makes a plain button a held button with that hold; the press and
  release stay the cockpit's own.
- `keep_without_node`: keeps a control no cockpit model has. Empty.
- `panel_order`, `control_order`: the order (below).
- `status`: the read-only L:vars of the Status display: APU, Master Warning and Master Caution
  (announced, with Ctrl+M rows), the two AC bus power sources, APU RPM, Cabin Altitude and Chocks
  (shown only). Cabin Altitude reads `L:B757_TEST_CABIN_ALT`, which BlueBird's WASM writes every tick
  (1,161 ft on the ground, 2026-10-28); `B757_DEBUG_PRESSURE_CABIN_ALT_FT` is declared and never written.

A toggle, guard or select that writes a value other than 0 or 1 stops the run until `positions` names
its values (A/T Arm writes 10). **The gate-note check** (`reject_gate_notes`): any control outside
`guarded` whose press, release, cw or ccw still carries an `[if …]` note stops the run.

### The click-code replay test

`ClickCodeReplay` in `test_generate_b757_map.py` replays every control of the embedded map through
`rpn_replay.replay` the way the app uses it: every code must parse; a toggle, guard or select is pressed
once from each position and must land on another of its positions; a switch with `cw` and `ccw` is
stepped from each position and must land on the next or previous one (or stay at an end); a switch with
only a press must cycle forward. This is the test that found the chronometer and door switch defects.

- `PRECONDITIONS` names the six fire controls whose click acts only while another L:var allows it: a
  fire handle is pulled only while it is unlocked or its fire is active (the engine handles also want
  their rotation at Center), and a handle's rotation steps only while the handle is pulled. Each entry
  must be needed: the test fails when the click works without it.
- `VENDOR_SLIPS` pins the nine controls whose click no RPN parser accepts. Each must still fail to
  parse, and with the slipped token left out it must do what the map says.
- The interpreter gives 0 for a pop from an empty stack, which 46 press codes rely on (the bus tie
  buttons run a `!` with nothing left to negate). The APU fire handle's press has an `and` with one
  operand; read that way its rotation plays no part. Measured 2026-10-26 to 27: unlocked, the handle
  pulled, and the same press stowed it after the relock.

### Position names

No control in the map reads "Position n" today; the generator still falls back to it for a position
nothing names. Names come, in this order of trust, from: a live read; BlueBird's published variable list
(support.bluebirdsim.com/docs/simvars, read 2026-10-25 to 2026-10-28); the nine vendor panel states in
`Data/panel_states/*.snap` (cold and dark to final approach) together with the manual's procedure text;
the vendor's tooltips where there is one per position; the click code; and, for the furniture, the
interior models. They are the panel's legends as printed (OFF, AUTO, STBY N). The names the flows lean
on (seat belts and no smoking OFF / AUTO / ON, pack selectors OFF / AUTO / STBY N / C / W, Mode Select
AUTO 1 / AUTO 2 / MAN, Ignition 1 / 2 / BOTH, Bank Limit AUTO to 25, thrust reference L / BOTH / R, wiper
OFF / LOW / HIGH, autobrake RTO / OFF / DISARM / 1-4 / MAX AUTO, IRS OFF / ALIGN / NAV / ATT, TCAS STBY
to TA/RA) are backed by the presets and the manual at the positions those cover and by BlueBird's list
elsewhere. A misnamed position would not be caught by reading a preset back, which returns the same
values. Still resting on one source alone: the ND mode and range lists (the tooltip list read with its
last word as index 0, which is the only reading that puts every preset on MAP), which MCP node is CMD L,
C or R (node order 1, 2, 3), and the start selectors' OFF, CONT and FLT (BlueBird's list).

### Sections, panels and their order

**The map's order is the order the pilot tabs through.** The definition builds sections, panels and
controls in map order (`BuildPanelsOnce`), so the generator sorts them last, after every label is made
(an order never renames or renumbers a control). Sections keep `SECTIONS`' order; the app adds Status
last. Panels are keyed by name, so no panel name may be in two sections or shared with an app panel.

- **Overhead:** Electrical, APU, IRS, CVR, Emergency lights and passenger oxygen, Window heat,
  Pressurization, Hydraulics, Fuel, Passenger signs, Exterior lights, Air conditioning and bleed, SELCAL
  and cabin call, Electronic engine control (RR), Yaw dampers, Panel lighting, Ram air turbine and engine
  limiters, Anti-ice, Wipers, Equipment cooling, Indicator lights and door lock.
- **Glareshield:** MCP, VOR/DME, Master warning and caution.
- **Forward panel:** Brakes, Caution, config and G/S inhibit, Landing gear, Captain foot and shoulder
  heat, Captain instrument source selectors, Heading reference, Thrust mode select, Alternate flaps,
  Ground proximity overrides, First officer instrument source selectors, First officer foot and shoulder
  heat, Yokes, Captain autoland status, Standby instruments, Captain DDRMI, Captain chronometer, First
  officer autoland status, First officer DDRMI, First officer chronometer.
- **Pedestal:** Control stand, Engines, TCAS and transponder, (the app's COM radios), Radio tuning panel
  1, Audio panel 1, Radio tuning panel 2, Radio tuning panel 3, Audio panel 2, ILS tuning, Fire
  protection, Stabilizer trim, (the app's Rudder and aileron trim), EICAS control, Captain EFIS, First
  officer EFIS, CDU brightness, Weather radar.
- **Other:** P61 panel, Oxygen, Flight deck door, Forward attendant panel, Windows and sun visors, Seats
  and stowage.

**Each panel is one panel of the cockpit.** Every map node was placed by the 3D position of its mesh in
the two interior models (2026-10-28; the nodes both models have sit within 7 mm of each other) and the
clusters named from the labeled pictures in BlueBird's Complete Flight Guide v1.01 (printed pages 33A to
33E, 95, 102 to 104). The vendor's file sections had produced panels no cockpit has ("Main panel
switches" held 39 controls of 13 real panels), so the owner chose "follow the cockpit" on 2026-10-28:
each guard sits with its switch, both EFIS control panels and the brightness knobs are on the Pedestal
where they are, the oxygen mask boxes, the door and the forward attendant panel (cabin lights, by door
1L) are under Other. Seven groupings that are not one physical panel were kept as sensible: Engines,
Electrical, Air conditioning and bleed, Exterior lights, VOR/DME, Master warning and caution, Yokes. The
fire and overheat tests stay with the fire handles, though they sit at the other end of the aisle stand
(the owner's choice).

**`panel_order`** (section to panel names; listed panels first, the rest alphabetically, named by the
run) follows the preflight flow's *changes*: a section's panels come in the order of the first step of
the Simplified Procedures in BlueBird's User Procedures v1.01 (PDF pages 34 to 62, cold and dark to
securing) that changes one of the panel's controls on a normal flight, by page and then line.
- Counted: a press of a test or button; setting a value; ON, ARM, START, SET or a selector to a position
  the control does not rest in cold and dark; and a step that sets or tunes a radio, audio or ILS value
  even when it says AS REQUIRED (the radios are tuned on every flight).
- Not counted: a step that only checks (the whole cockpit safety inspection; any CHECK, VERIFY, CONFIRM);
  any other AS REQUIRED or AS DESIRED step; a step that sets a control to where it already rests in
  BlueBird's own cold and dark panel state (`coldanddark_wpb.snap`).
- Panels no step changes follow, in cockpit order. Two starts are pinned whatever the flow gives: the
  Pedestal opens with Control stand, Engines, TCAS and transponder (`Bbs757DefinitionTests`), and the
  Forward panel with Brakes, the autobrake's panel (the owner: it is used most; the flow agrees).
- Judgment calls: Hydraulics, Fuel, Exterior lights and Air conditioning count at their Before Start
  lines, because their earlier lines set controls where they already rest; Pressurization counts at the
  landing elevation; both EFIS panels at the radio minimums; Stabilizer trim at the takeoff trim setting;
  the flight deck door rests Open, so DOORS CLOSED changes it.

**`control_order`** (panel to node names; listed controls first, the rest in the vendor file's order)
puts every-day controls first (the owner's instruction of 2026-10-28), in three tiers: what the normal
procedures move on every flight, in the order the flow first uses it, a left and right pair together;
then what is set once in preflight, tests and display options; then non-normal, emergency and
maintenance controls. A guard comes right before the switch it covers, except the emergency lights
guard, which follows its switch because the app opens and closes it. Sources: the User Procedures and
the Normal Checklist v1.01, by page; general 757 practice only for the lower tiers. Judgment calls: the
exterior lights follow the manual's order literally (the landing lights are not hoisted); the alternate
stab trim buttons count as set-once (normal trim is the yoke switches); Fire protection lists the fire
handles and the cargo fire controls before the three tests, so a key pressed on the panel's first control
during a fire is no test bell. Ten controls' meaning could not be established and keep their node-made
names, among them the audio panels' "Mic Lm" and "Mic RR" selects (probably HF L
and R), Flt Int, the EFIS INOP button, EICAS Event and Sys Fail.

An order entry that names a section the map lacks, a panel the section has none of, a node not in that
panel, a repeat, an empty list, or a `control_order` panel two sections share stops the run.

**App rows are not nodes** and are placed by the app's code: the Squawk Code field right after TCAS Mode,
the landing altitude field first on Pressurization and the two cabin buttons last, the stab trim buttons
first on Stabilizer trim, the fourteen P61 test buttons right after Squib Test.

### Engines, and the engine-type filter

The three overhead start selectors and the fuel control switches share the Pedestal's Engines panel,
engine by engine (the owner's order): Ignition, L ENG Start, L Fuel Control, R ENG Start, R Fuel Control.
Their `node_panels` rules name the section Pedestal, because a `B757_OVHD_` node otherwise lands in the
Overhead. The start selectors read GND (1), AUTO (3), OFF (4), CONT (5), FLT (6): the code never writes

### PanelSweep

`tools/b757-gen/PanelSweep` is a standalone console tool (never part of the solution, [CORE-4]) that
checks the map against the live aircraft. It compiles the app's own `Bbs757ControlMap.cs`,
`Bbs757Write.cs` and `Bbs757Rpn.cs` (linked, not copied) and reads the embedded map. For every toggle,
select and switch it reads the control, writes each other position through `Bbs757Write.ToPosition`
(calls 400 ms apart), reads back 1.5 s later, compares with `Bbs757Rpn.PositionIndex`, and puts the
control back (up to three tries), writing `sweep-<date>.tsv`.

- Build: `dotnet build tools/b757-gen/PanelSweep -c Debug -p:Platform=x64`. `PanelSweep.exe --dry-run`
  never connects: it prints what it would write, the counts and two audits (no denied node planned, no
  command over MobiFlight's buffer). `--panel NAME` limits a run, `--out DIR` places the table.
- A live run wants the 757 on the ground, parked, engines off, APU running, MSFSBA closed and the pilot
  at the sim. It asks for a typed `YES`, then refuses unless the sim reports on ground with both engines
  off and a probe write to `L:PANELSWEEP_PROBE` reads back. The whole map takes about 16 minutes (198
  controls, 313 writes).
- Writes are one-shot `MF.SimVars.Set` commands with a `{seq} 0 *` prefix. Never `MF.SimVars.Add`, which
  registers an expression MobiFlight re-runs on every poll: measured 2026-10-28, a write registered that
  way ran again and again and drove the rudder trim to its stops (−17 and +16.7 units).
- It never writes buttons, guards or guarded controls, nor anything in `denylist.txt`: the fire handles,
  unlocks and rotations, cargo fire, the stab trim cutouts, the battery and the electrical sources, the
  APU and IRS selectors, the fuel control and start selectors, the generator drive disconnects, the RAT,
  passenger oxygen, the emergency lights, the gear and flap levers, the parking brake, the alternate
  flaps selector and its arm switches, the gear lock override, switches under a cover the map does not
  link to them, and the guards of all of these. It also denies any control sharing a state var with a
  denied one. A denylist line naming a node the map lacks stops a live run.
- **The run of 2026-10-28** (the map before the furniture panels): 168 controls, 276 position writes,
  267 landed, every control put back, no SimConnect exception. The nine that did not land are BlueBird's
  behavior, not the writer's: the flight deck door lock's Unlocked and Deny and both chronometers' RESET
  (momentary, back at rest by the read), and Autobrake 1, 2, 3, 4 and MAX AUTO, which BlueBird returns to
  DISARM unless the IRS are aligned, there is hydraulic pressure and the parking brake is off (tried by
  hand afterwards: with all three, the knob stayed on 1). The 30 furniture controls have not been swept.

## How it writes

Each map control is one OnRequest L:var keyed by its node (`ControlVariable`); a button or held button
renders as a button, everything else as a combo of its positions. `HandleUIVariableSet` answers every
map control "handled", refusals included, so the generic path never sends its own write. Writes reach
the sim through `Bbs757SimIo` (`WriteIoFor`), which the tests replace; every write is one
`ExecuteCalculatorCodeUnique` call, whose unique prefix matters (measured 2026-10-26: two identical
calculator strings in a row reach MobiFlight as one). Everything runs on the UI thread and nothing
blocks it.

**Before any write** the definition asks `CalcWriteCanLand` (it registers `MSFSBA_BRIDGE_PROBE`, so the
calc-path probe gives a verdict) and says "{label} unavailable" when nothing could land.

**A positional pick** (`SetPositionAsync`): 300 ms after the last row the pilot arrows onto
(`PickSettleMs`; arrowing through a closed combo commits each row it passes) the control is read fresh,
and `Bbs757Write.ToPosition` plans the calls:
- a toggle, guard or select replays its press once when it is not at the pick (`Bbs757Rpn.ToggleTo`);
- a switch steps by position *index* with `cw` or `ccw`, or cycles forward with its press, wrapping
  (`StepTo`, at most 20 steps a call);
- a switch with no click code (the sim's own 3-state template, and every `direct_write`, `levers` and
  `direct_positions` control: 37 today) is written through its state var, `Bbs757Rpn.SetLVar`, invariant
  whatever the PC's culture;
- an unread or NaN reading, a target that is no position, or (for a control that clicks) a reading that
  is none of its positions sends nothing and says "{label} unavailable": a toggle's press flips it, so a
  press on an unknown reading could land anywhere.

A pick that lands says nothing (the screen reader read the combo, [CORE-7]). 1.5 s after the write
(`ReadBackDelayMs`) the control is read again so its combo shows where it really is.

**Pick bookkeeping.** `BeginPick` enters the pick in a pending set, canceling an earlier pick of the same
control; `EndPick` removes it and says whether the entry was still its own (only then is the re-read
made). While a pick is pending, `ProcessSimVarUpdate` consumes every delivery of that control: the fresh
read answers with the position from before the write, and letting it reach the focused combo would have
the screen reader speak the old position over the pilot's pick. `OnSimContextReset` (a flight load or a
dropped connection) cancels and forgets every pending pick (`CancelPendingPicks`), and `OnSwitchedAway`
cancels the profile's lifetime, so nothing writes into the next flight or aircraft.

**Spring-loaded positions read back as their rest.** Measured 2026-10-26: the chronometer ET's RESET
reaches 3 and BlueBird returns it to HOLD after 0.4 s; the flight deck door switch's Unlocked and Deny
land and are back on Auto about 0.9 s later (the component's 1 Hz update, which only its own click's
`O:UpdateTime` stamp delays). So after such a pick the combo shows HOLD or Auto, which is the aircraft's
state, and the plain positional path never says "did not move". The door switch is cosmetic: BlueBird's
systems module never reads it.

**A button** (`PressFromPanelAsync`, `PressAsync`): the press code, a hold of 200 ms
(`Bbs757Write.ButtonHoldMs`) or, for a held button, its `hold_ms` (3000 ms for the curated tests, the
template's own time or 1500 ms otherwise), then the release code. The release waits on
`CancellationToken.None`: a press is always let go, even across a profile switch. Then:
- A button with no readable state says "{label} pressed".
- A button that moves a state row (`LinkedStatusKey`) reads that row back about 1.5 s after the release
  and says it instead: the 14 MCP mode and CMD buttons their light ("CMD R on"), the three speedbrake
  spots the lever ("Speedbrake armed"), EXT PWR its ON light. The press arms an echo window
  on that row (`ArmOwnWriteEcho`, 5 s) so the row's own change announcement does not say it twice; the
  read-back closes the window and becomes the row's baseline (`SettleOwnWriteEcho`), so a later change
  still speaks. A Parking Brake or TCAS Mode pick arms the same window and settles it with its re-read.
- **Lamp Test** (`Bbs757LampTest`, `PressLampTestAsync`) latches: its press toggles `L:OVHD_TEST_LTS`
  while circuit 27 is on, and a second press turns it off (measured in flight 2026-10-28). 500 ms after
  the release the latch is read and said: "Lamp test on" or "Lamp test off".

**The parking brake.** In BlueBird's REALISTIC parking brake mode the lever's toggle alone does nothing
(measured 2026-10-28: the var stayed 0; with both brake axes at full the same write set it and it stayed
set). When the re-read shows the brake did not move and BlueBird's own setting does not say EASY,
`Bbs757ParkingBrake.RetryWithFullBrakingAsync` sends full braking and the lever value in one string, then
releases the pedals.

**Guarded controls** [B757-12], [B757-6]. A control whose map row names a `guard` (Emergency Lights; Stab
Trim C and R Cutout) carries no click code: BlueBird gates the click on the guard, and closing the guard
writes `close_sets` to the switch itself (ARMED, NORMAL). `SetGuardedAsync` reads the control and its
guard fresh and sends what `Bbs757Guarded.Plan` plans, 300 ms apart (`StepGapMs`): for `close_sets`, the
guard's press to close it when it is open, then the state write as well; for any other position, the
guard's press to open it when it is closed, then the state write. The guard's press flips it, so an
unread control or guard sends nothing ("{label} unavailable"). The control is read back after 1.5 s and
a pick that did not land says "{label} did not move" once. Measured 2026-10-26 on the ground: a write of
2 to the emergency lights with the guard open held and reached the systems (the cabin emergency lighting
came on, the emergency battery began to drain); the guard's own press then closed it and put the switch
on ARMED; stab trim C took CUTOUT with its guard open and went to NORMAL on closing (R is the same
template, not tried). Once the first call has gone, a newer pick of the same control does not cut the
sequence short (a half-run one would leave the guard open with no write behind it); a flight load or
dropped connection does, through `_pickEpoch`, which `CancelPendingPicks` bumps and the sequence checks
before and after each gap. A pick on a guard's own row re-reads every control that guard covers.

**The fire handles** [B757-13]. BlueBird's unlock click sets `L:BBS757_FIREUNLOCKn` and starts an `O:`
timer whose update loop clears it 1.5 s later. A calculator write cannot set an `O:` var, so after an app
press the handle stayed unlocked (measured 2026-10-26: still 1 four seconds later). `PressAsync` therefore
calls `RelockIfUnlock`: for the three unlock buttons (`Bbs757Write.RelockAfterUnlock`, known by their
state var and only as momentary buttons) the app writes 0 to the var itself 1.5 s after the press
(`FireHandleRelockMs`). The relock does not consult `_pickEpoch`: it writes the cockpit's resting value,
and skipping it would leave the handle unlocked. A handle pick replays the handle's own click, which pulls
only while the handle is unlocked or its fire is active (and stows it otherwise); **picking "Pulled" on a
locked handle does not press Unlock first**, so the click writes 0 and the combo goes back to "In".
Without a fire warning a pull therefore needs the Unlock button and then the handle pick within the 1.5 s
window (measured 2026-10-26 to 27 on the APU handle: pulled inside the window, APU FAULT and shutdown; stowed by
the same press after the relock). The rotation steps only while its handle is pulled.

**`direct_write` controls** [B757-14]: the chronometer ET levers and the flight deck door switch go
straight to the picked value through their state var, as any switch with no click code does.

**Brightness** [B757-16]. BlueBird's brightness code reads one knob var per display and sets the
display's emissive output to knob ÷ 40 × 1.5 with a floor of 0.1: 0 dims a display to its minimum, never
off, and every knob loads at 40. Measured 2026-10-28: the captain PFD's `B757_PFD_BRIGHTNESS_L` read 1.5
at 40, 0.75 at 20 and 0.1 at 0; the captain ND and CDU and the upper EICAS read 1.125 at 30; the lower
EICAS 0.5625 at 15 (the first officer's three follow by name and were not written). The cockpit mouse
stops at 30 (20 on the F/O ADI knob), but the systems take 0-40, so the positions are not held to that
clamp. **The PFD is dimmed by the ADI knobs' var, `B757_PFD_1/2_SCREEN_KNOB`**: the map's `B757_ADI_n_LCD_KNOB`
controls write it. The nodes that are *named* `B757_PFD_n_SCREEN_KNOB` write
`BBS757_RASTER_BRIGHTNESS_CA/FO`, which nothing in the package reads; never write those. The ND, EICAS and
CDU knobs write the var of their own name. A dark display also defeats a display read by AI vision.
BlueBird's automatic cockpit lighting (an EFB setting, off by default) resets the PFD, ND and EICAS knobs
at dusk and dawn; that is read from its code, unmeasured.

**The landing altitude** [B757-7]. The 757 has no cruise altitude selector; the Pressurization panel's
first row is the app's "Landing Altitude" field (`Bbs757LandingAltitude`, typed text through
`HandleOverheadTypedText`). `L:B757_OVHD_LDG_ELEV` holds the feet and `L:B757_OVHD_LDG_ELEV_CHG` is the
knob's step input. A direct write of the value alone holds but leaves the panel's digits stale until the
next knob step, so `Bbs757LandingAltitude.Write` sends the target minus 10 and then one step:
`1020 (>L:B757_OVHD_LDG_ELEV) 1 (>L:B757_OVHD_LDG_ELEV_CHG)`. Measured 2026-10-26: that read 1030 and the
step var read 0 again; −70 and a step read −60; the range edges read −1070 and 14100, and one more step
at 14100 stayed there. The text is parsed in any culture ([CORE-17]), rounded to the nearest 10 ft and
refused outside −1070 to 14100 ("Landing altitude must be from -1070 to 14100 feet.", or "Type the
landing altitude in feet first."). The value *read back* 1.5 s later is spoken, never the one typed:
"Landing altitude 1030 feet", "Landing altitude minus 60 feet", "Landing altitude unavailable". A
read-only row shows it ("1030 feet").

**Spring switches** [B757-15] (`Bbs757SpringControls`, `PressSpringAsync`). Four cockpit switches are
spring-loaded and have no positions to pick, so the app gives each two buttons that hold it to one side
for one second: Left / Right Rudder Trim and Left / Right Aileron Trim (the app's Rudder and aileron trim
panel: in the cockpit they sit on their own trim panel at the aft end of the aisle stand), Nose Down /
Nose Up Stab Trim (the alternate stab trim, first on Stabilizer trim) and Climb / Descend Cabin (the
manual cabin altitude switch, last on Pressurization). The labels end "1 s"; the P61 test buttons end
"3 s". Measured 2026-10-28 on the ground:
- Each trim switch rests on 1; 0 is left or nose down, 2 right or nose up. BlueBird trims every frame
  while one is off 1, and **nothing in the aircraft returns it to 1 but the cockpit mouse's own
  release**: a lost release ran the rudder trim to its stop twice (−17 and +16.7 units). Rates: rudder
  about 0.85 units/s, with no hydraulic pressure needed; stabilizer about 0.3°/s, needing center hydraulic
  pressure and the cutouts NORMAL; the aileron trim moves the control wheel about 0.06 units/s.
- The cabin switch rests on 4 and BlueBird uses only the side of 4 (the click writes 0 or 7), only with
  Mode Select at MAN; its XML writes 4 back within about a second. With the outflow valve at 1, a 0 held
  1.2 s closed it to 0.869 and a climb held 1.3 s opened it to 0.963; at 4 it held.

So a press writes the hold, writes it again every 500 ms (a P61 test every 30 ms for 3 s), and **always
releases**: the waits are on `CancellationToken.None`, a hold that fails part-way is released at once,
and the release is verified (`ReleaseSpringAsync`): written, read back 250 ms later, and written again
while the switch is off rest, three writes in all. A switch still off rest is released in the background
every 2 s for up to 60 s (`KeepReleasingAsync`), even after a profile switch, and the press says "Rudder
trim switch did not return; the trim may keep running" (the cabin switch: "… check the outflow valve"; a
P61 test: "… the test may keep running"), then "Rudder trim switch returned" once it rests. One hold per
switch at a time: a press while its switch is holding or being released is ignored. A cabin button reads
Mode Select first and says "Set the pressurization mode to MAN first" outside MAN.

After the release the readout is read fresh 500 ms later and said once: "Rudder trim 0.9 units right" /
"centered" (`L:B757_PED_RUDDER_TRIM_INDICATOR`, −17 to +17; the stock `RUDDER TRIM PCT` stayed 0);
"Aileron trim right" / "left" / "centered", the direction only, from the control wheel
`L:B757_FC_YOKE` (1.5 neutral; BlueBird publishes no aileron trim units and the stock `AILERON TRIM PCT`
stayed 0); "Outflow valve 87 percent open" (`L:BBS_CABIN_VALVE`; the cabin altitude does not move on the
ground with the valve open). The stab trim is the exception, because the shared trim call-out already
speaks while the stabilizer moves: the press says "Stab trim did not move" when the trim moved under
0.05 units, "Trim 5.3" when it moved and the call-out is muted or off, and nothing otherwise. A P61 test
reads nothing back and says "{test} done" ("Takeoff config test done"); the lights and warnings it
raises are spoken by the cockpit-wide announcements.

**Readout rows.** Panels gained read-only rows on their status display, read while the panel is shown,
never announced and with no Ctrl+M row: Landing Altitude and Outflow Valve on Pressurization, Rudder Trim
and Aileron Trim on Rudder and aileron trim (the words their press says after the name), and the Status
panel's Cabin Altitude in whole feet. `FormatOverheadDisplay` writes their text.

**`OnOwnWrite`.** Every write the app makes tells the cockpit-wide announcements which control it was
(`Bbs757CockpitAnnouncements.OwnWrite`), so that control's change within the next 5 s is the app's echo
and is not spoken as a background change. It is called with the control's node for a pick and a press; a
guarded control's node *and* its guard's; the unlock button's node again before the relock; a spring
switch's L:var; `Bbs757LandingAltitude.DisplayKey` for the landing altitude; and by the radio, ILS and
MCP changeover writes with their own keys. The First Officer's writes (`FoSetCoreAsync`,
`FoPressCoreAsync`) go through the same planners, bookkeeping, relock and `OnOwnWrite` calls, silently.

## Flight-control readouts and call-outs

`BBS757Definition.Readouts.cs` registers the rows and speaks them; the words are in `Bbs757Readouts`,
`Bbs757McpLights` and `Bbs757Annunciators` (all pure). BlueBird's own variables are the truth wherever a
stock one was measured wrong. What is read, and why:
- **Flaps**: stock `FLAPS HANDLE INDEX`, detents UP, 1, 5, 15, 20, 25, 30; surfaces `TRAILING EDGE FLAPS
  LEFT ANGLE`. The stock index follows BlueBird's lever: on 2026-10-25 (on the ground, engines off) one
  `K:FLAPS_INCR` moved it 0 to 1 together with `L:B757_FC_FLAP_LEVER`, with the surfaces staying up for lack
  of hydraulics. Each detent's angle is BlueBird's `flight_model.cfg` ([FLAPS.0] 0, 1, 5, 11, 20, 25, 34
  degrees: flaps 15 is 11 degrees, 30 is 34), so the surfaces are "at" the detent within 0.4 degree of that
  angle (below half the smallest gap: UP and 1 are a degree apart, so the lever on 1 with the surfaces at 0
  is never "Flaps 1"). Output L reads the angle twice 500 ms apart when it is off: "Flaps 5, moving, 3
  degrees" or "Flaps 1, surfaces at 0 degrees" ("1 degree" in the singular).
- **Gear**: the three stock legs, `GEAR CENTER/LEFT/RIGHT POSITION` (0 up, 1 down): "Gear down" when all
  three are 0.99 or more, "Gear up" at 0.01 or less, else "Gear in transit". The lever is BlueBird's
  `L:B757_GEAR_HANDLE_POS` (0 UP, 0.5 OFF, 1 DOWN), read on request, never the stock `GEAR HANDLE POSITION`,
  which has no OFF: on a flight of 2026-10-28 the gear stayed down after takeoff with BlueBird's lever at OFF
  (0.5, the gear lights lit) while the stock handle read 0, so the readout said "lever up". The same flight
  showed that each of the simulator's gear key presses steps BlueBird's lever one detent (DOWN, UP, OFF,
  DOWN). Shift+G therefore says the legs, then the lever at its nearest detent, always: "Gear up, lever
  off", "Gear down, lever down" (`Bbs757Readouts.GearReadout`; an unread lever says the legs alone).
- **Speedbrake**: `L:B757_FC_SPOILER_LEVER` (0 down, 10 armed measured; 100 is the UP click): below 5 down,
  to 15 armed, from 95 up, between "up N percent" to the nearest ten.
- **Parking brake**: `L:B757_FC_PARK_BRAKE`. Never the stock `BRAKE PARKING POSITION`, which read 0 with
  BlueBird's brake set (2026-10-25, [B757-1]).
- **MCP lights**: `L:B757_MCP_<THR|SPD|LNAV|VNAV|FLCH|HOLD_1|VS|HOLD_2|BCRS_1|LOC|APP|CMD_1|CMD_2|CMD_3>_BUTTON`
  (each button's decal lights from it), read under keys `BBS757_MCP_LIGHT_<name>` because the light var has
  the button node's own name. HOLD_1 is HDG HOLD, HOLD_2 ALT HOLD; CMD 1 to 3 are CMD L, C and R. Spoken
  "CMD R on", "VNAV off".
- **EXEC light**: `L:FMC_EXEC_ACTIVE_1`, the captain's CDU light, read under `BBS757_EXEC_LIGHT`; both CDUs
  lit together after ACTIVATE and went out after EXEC (measured 2026-10-25), so the first officer's `_2` is
  not read. "EXEC light on" / "EXEC light off" (the iFly CDU window's words), Ctrl+M row "EXEC light", on no
  panel and no status display.

These rows ride the 1 Hz batch and speak their changes from `ProcessSimVarUpdate` through one
`Bbs757ChangeTracker`: a row's first phrase is a silent baseline, an unchanged phrase is silent, and a
change inside an echo window the app's own write armed is tracked but not spoken. Each has a Ctrl+M row;
MainForm's mute wrap gates them ([VAR-8]). The three gear legs speak the one "Gear" row's call-out (the
nose leg's row; the main legs have none), so they are `IsMuteWrapExempt` and check that row's mute
themselves. They show on the Status panel (flaps with the flap angle, gear, speedbrake, parking brake) and
the MCP panel's status display (the lights).

**Baselines after a flight load or a reconnect.** The two differ, because SimConnect's value cache differs. A
flight load on a live connection (`OnSimContextReset`) calls `QuietReadoutBaselines`: for `LoadQuietMs` (60 s;
not measured: the load event fires during the loading screen and BlueBird sets its panel up some time after)
`Bbs757ChangeTracker.BeginLoadQuiet` tracks every change and speaks none, since the new flight's flaps, gear
and lights are the cockpit as found. The baselines and the gear legs are KEPT: the connection kept its cache
and the batch delivers a value only when it changes, so a row the new flight leaves as it was is not
delivered again, and with its baseline cleared its first real change would be taken for the baseline and
never said (heard as the parking brake released after loading parked, unspoken). The echo windows and the
resting altimeter are cleared. A dropped connection (`OnVariableCacheCleared`) calls `ResetReadoutBaselines`:
the reconnect delivers every row anew, so each first delivery is a silent baseline again. The announced
rows' raw values (`_annunciatorValues`) stay in both cases: they are facts, not baselines.

### Announced lights and states

`Bbs757Annunciators.Rows` is a table of BlueBird L:vars, each a batched announced row with a Ctrl+M row,
spoken through the same tracker. A row gives its key, L:var, label, phrase function, the map panel whose
status display shows it (or none) and the words that display uses per value.

| Rows | L:var | Spoken | Shown on |
| --- | --- | --- | --- |
| External Power On | `B757_OVHD_EXT_PWR_BUTTON_ON` | "EXT PWR on" / "EXT PWR off" | Electrical |
| External Power Available | `B757_OVHD_APUGENEXTPWR_R_AVAIL_DECAL` | "External power available" / "External power not available" | Electrical |
| Autoland Status Upper | `B757_MAIN_L_AUTOLAND_1_BUTTON_ON` | 0 "LAND 3", 2 "LAND 2", 1 blank (quiet) | Status |
| Autoland Status Lower | `B757_MAIN_L_AUTOLAND_2_BUTTON_ON` | 0 "NO LAND 3", 2 "NO AUTOLAND", 1 blank (quiet) | Status |
| Altitude Alert | `BBS757_CA_ALTIMETER_ALT_ALERT_LIGHT` | "Altitude alert"; going out quiet | none |
| Configuration Warning | `B757_MAIN_CONFIG_1_DECAL` | "Configuration warning"; going out quiet | none |
| IRS L / C / R Aligned | `B757_OVHD_IRS_<x>_ALIGN_DECAL` | "IRS L aligned" when the light goes out with that IRS at NAV | none |
| Left / Right Start Valve | `B757_OVHD_<L|R>_ENG_START_SWITCH` | "Left start valve closed"; open quiet | Engines |

- **`Quiet` phrases** ([B757-53]). The tracker speaks a change from a remembered phrase and treats the first
  phrase after an untracked state as a baseline. A state the pilot need not hear (a blank autoland line, an
  alert going out, an IRS aligning, a start valve opening) is therefore a phrase prefixed
  `Bbs757Annunciators.Quiet` ("quiet: "): tracked, never spoken (`IsSpoken`). Were it null, the next spoken
  state would be taken for a baseline and lost: an altitude alert would never be said. Null is kept for a
  value that is no state at all: an unreadable one, or a door between its ends, so a moving door says only
  where it stops.
- **The autoland status** rows read the variables that drive the annunciator's two lines. Measured on an
  ILS autoland on 2026-10-27, read every second or so from the simulator's `VLogic` Coherent view: with APP
  armed and three autopilots on, the upper pair read 1 and the lower pair 1; at LAND 3 the upper pair went
  to 0 and "LAND 3" was heard; after the landing with the autopilots off (2026-10-28) the upper pair read 1
  again. The value 2 (LAND 2, NO AUTOLAND) and what the variables read cold and dark are not measured: if
  one rests at 0 unpowered, the Status display would read LAND 3 or NO LAND 3 with nothing armed.
- **An IRS aligned.** The ALIGN light going out says "aligned" only with that IRS's mode selector at NAV
  (2): turning the selector off also puts the light out. The selector's value comes from a silent row of its
  own (`BBS757_IRS_<x>_SWITCH_WATCH`, batched, no Ctrl+M row), handed to the phrase as `RelatedKey`. The
  batch delivers in name order, so `B757_IRS_x_SWITCH` arrives before `B757_OVHD_IRS_x_ALIGN_DECAL`.
- **The start valves follow the start switch, not the VALVE light.** Measured on 2026-10-27 over three
  starts, both engines: the VALVE decal only flashes for 2 s whenever the start switch moves, either way,
  while the switch holds GND (1) as N2 climbs and BlueBird releases it to AUTO at starter cutout, about 46 %
  N2. So GND is "open" (quiet: the pilot just picked GND) and any other position "closed", which is the
  cutout call.
- **The altitude alert** was heard once on a level-off on 2026-10-27, with no repeat while the light
  flashed.

**EXT PWR and ground power.** The EXT PWR button (`B757_OVHD_EXT_PWR_BUTTON`) is a linked control
(`LinkedStatusKey`): its press reads the ON row back about 1.5 s later and says "EXT PWR on" or "EXT PWR
off" instead of "pressed". `LinkedPhrase` and the row's own phrase must be the same words: the read-back
rebaselines the row with `LinkedPhrase`, so different words would announce every press twice ([B757-53]).
The press also arms the AVAIL row's echo for the whole 5 s window, because BlueBird may put AVAIL out as ON
lights (not measured), and "External power not available" beside "EXT PWR on" would sound like power lost.
The Electrical panel's status display also shows "Ground Power" (`L:BBS_757_GPU_AC_PWR_CONNECTED`,
"Connected" / "Not connected", key `Bbs757SharedKeys.GpuConnected`), registered by the EFB partial and
spoken "Ground power connected" / "Ground power disconnected" through the same tracker; a run of the EFB
window's own taps is its echo. Measured 2026-10-25: one tap on the tablet's GPU tile took the connection
and EXT PWR AVAIL from 1 to 0 together, and a second tap brought both back within 4 s.

**Linked controls.** `LinkedStatusKey` names the row a control's press or pick moves: an MCP button's light,
the three speedbrake spots' lever, the parking brake, EXT PWR's ON light and the TCAS mode knob's watch
row. The write arms a 5 s echo on that row (`OwnWriteEchoMs`); the read-back after the write speaks the row
(for a press) or lets the screen reader's own reading of the combo stand (for a pick), then makes that
phrase the baseline and closes the window, so a later change still speaks.

**Trim.** The shared trim call-out (`MON_ElevatorTrim`, the stock `ELEVATOR TRIM POSITION` in degrees on
the 1 Hz batch) speaks BlueBird's indicator units: the definition overrides `DescribeElevatorTrim` with
`Bbs757Readouts.StabTrimUnits`, `max(0.436, -0.002148·d² + 0.803152·d + 1.11308)`, the strip's own code in
the cockpit XML (2.3 degrees at load is 2.95 units), keyed on the tenth it speaks: "Trim 5.3", the 737s'
words (`StabTrimUnitsCallout`), invariant. The stock trim events reach the stabilizer (measured 2026-10-25:
five `ELEV_TRIM_UP` moved it 2.300 to 2.381 degrees), so the setting is heard about once a second while it
moves. The base class's first-reading baseline, hysteresis and Shift+T toggle apply as on every aircraft;
it keeps the shared Ctrl+M row and has no key and no status row.

**No glideslope call-out** ([B757-5]). BlueBird's VOR and ILS receivers are its own: on 2026-10-25 the
VOR/DME panel showed 116.90 while `NAV ACTIVE FREQUENCY:1..3` read 110.50, and nothing done to BlueBird's
radios changed a stock NAV variable; on an ILS autoland on 2026-10-28 `NAV GSI:1`, `NAV CDI:1` and `NAV HAS
GLIDE SLOPE:1` read 0 for the whole approach (and `AUTOPILOT MASTER` 0 with three autopilots engaged). So
`BBS757Definition.UsesStockNavReceivers` is false, which gates two things in `BaseAircraftDefinition`: the
base variables lose `MON_GlideSlopeAlive` (no row, so no Ctrl+M row), and the shared "Glideslope alive" /
"Glideslope lost" branch returns without speaking should the row ever arrive. Every other aircraft keeps
both (`Bbs757GlideslopeGateTests`).

**Output mode**, read at once and spoken immediately (`ReadoutAsync`; a batch-covered row from the cache,
anything else fresh; a failed read says "… unavailable", never nothing):
- **L** flaps, **Shift+G** gear and lever, **B** the three altimeters and the decision height ("Altimeter:
  1018, 30.05. DH 200"), **F** and **Shift+F** fuel (the loadsheet's tank gallons × `FUEL WEIGHT PER
  GALLON`, pounds or kilograms, rounded to 10, the total the sum of the spoken tanks), **W** and
  **Shift+W** `TOTAL WEIGHT` (whole pounds or kilograms, the other Boeings' words).
- **Shift+1 to Shift+5** the flap maneuver speeds for flaps up, 1, 5, 15 and 20, **Shift+6** VREF 30 and
  25, from `TOTAL WEIGHT` read fresh ([B757-9], `Bbs757FlapSpeeds`). VREF comes from twelve points measured
  on BlueBird's own APPROACH REF page on 2026-10-25: a trial gross weight typed into 1L on the first
  officer's CDU every 10,000 lb from 140,000 to 250,000 lb, the page's VREF 30 and 25 noted, then `DELETE`
  in 1L to give the FMC its own weight back (VREF 30: 109, 113, 117, 121, 125, 129, 133, 137, 140, 144, 148,
  152 kt; VREF 25 two knots more throughout). The page refused 120, 130 and 255 as INVALID ENTRY, so the
  table is BlueBird's whole range: linear between the points, and a weight outside 140,000 to 250,000 lb
  says "Flap speeds unavailable.", never an extrapolation or a generic formula. The maneuver speeds are the
  owner's schedule over VREF 30: flaps up + 80, 1 + 60, 5 + 40, 15 + 20, 20 + 20 kt. Spoken "Flaps 5
  maneuver speed 164 knots, calculated" and "VREF 30 124 knots, VREF 25 126 knots, calculated".
- **D** and **Shift+D** the distance and time to the destination and to the top of climb or descent, read
  off PROG page 1 on the first officer's CDU (`Bbs757Prog`, through the definition's `CduPages`): PROG is
  pressed unless a PROG page is up, then PREV until the page counter reads 1 (at most twice), which leaves
  that CDU on PROG page 1. The parse finds the label rows rather than counting rows (layout measured
  2026-10-25: " DEST" then "KMIA    568  0332Z   6.1"; "TO T/C" or "TO T/D" then "0218Z/ 56NM"). With a
  planned step climb ahead the row says "TO STEP CLB" and the T/D shows only once no step is left (seen
  2026-10-27). Spoken "568 miles to destination KMIA, ETA 03:32 Zulu", "Top of climb in 56 miles, 02:18
  Zulu", "Step climb in 1219 miles, 17:40 Zulu, top of descent after it", "No top of climb or descent
  ahead", or "The first officer's CDU did not answer." `L:BBS_VNAV_TOD` is not used: it does not count down.
- **Shift+H, S, A, V** the MCP's own values, each followed by the lit MCP mode buttons that go with it
  (below, "The MCP value windows").
- **Alt+I** the standby instruments, an AI read on the EICAS instrument view (`Bbs757DisplayReads`,
  `Standby757`): no variable carries them.

## Cockpit-wide announcements

Every annunciator light worth a pilot's attention, and every switch moved by anything but the pilot's own
pick in the app (a cockpit preset, a quick start, BlueBird's automation, a hardware panel, the mouse), is
spoken. `BBS757Definition.Announcements.cs` wires it; `Bbs757CockpitAnnouncements` turns changes into
lines; `Bbs757LightTable` is the light list.

- **The watch list, not SimConnect rows** ([B757-11]). A few hundred more announced variables would not fit
  the connection's data definitions, so none is added: the names go to the tablet agent
  (`Resources/coherent-bbs757-tablet-agent.js`, `watch(names)`), which reads each `L:` name in the hidden
  `BBSTablet` view and answers only those that changed since the last call (`changes()`); the first call
  after `watch` is a baseline and answers nothing. `CoherentBbs757TabletClient` asks every 500 ms on its one
  socket (`WatchIntervalMs`; while a list is set the loop, and with it the CDU scrape, runs at that pace),
  sends the list again whenever the agent is installed afresh or answers that it watches nothing, and
  raises `LvarsChanged` on the UI context.
- **What is watched** (`BBS757Definition.CockpitWatched`, once per definition). `Bbs757LightTable.WatchSet`
  takes every light of the table plus the state var of every map control a pilot can leave in a position
  (no momentary or held button, no control without a state var), and drops every name another row already
  speaks: the `Name` of each announced variable that has a Ctrl+M row (a silent row, read only to phrase
  another's, hides nothing), plus `BBS757Definition.SpokenByOtherRows`, the controls a row speaks under a
  different variable (`B757_FC_FLAP_LEVER`, `B757_GEAR_HANDLE_POS`, `B757_FC_PARK_BRAKE`, `AT_ARM_SWITCH`).
  One owner per spoken row: the TCAS mode knob, the IRS align lights, the configuration warning and the
  disconnect lights are the definition's rows, so the watch leaves them out.
- **The light table.** 132 lights curated from the 518 light nodes of BlueBird's interior model XML (the
  test fixture `bbs757-lights.json` holds those names, and `Bbs757LightTableTests` pins that every table
  entry is one of them, none twice). A fault light says "{label} light on" and "{label} light off"; an
  indication (APU run) only as it comes on. Left out on purpose: backlights, display brightness and test
  lights; the 511 breakers; legends that only follow their own switch (ON, OFF, ALTN and bar legends, whose
  switch is announced itself); valve-in-transit lights, which flash on every normal switch move; the first
  officer's master lights, which repeat the captain's; the CDU message, display and offset lights; the gear
  position lights.
- **A switch** says "{label} {position}" from the control map, or the value itself where the map names no
  position.
- **The own-write window.** Every panel press and pick calls `OnOwnWrite(node)`; a change of that control
  within 5 s (`Bbs757CockpitAnnouncements.OwnWriteEchoMs`), or while its pick is still pending, is the
  pilot's own and is not said: the screen reader read the combo.
- **Bursts.** More than five switch moves in one read or within a second are one line, "Panel state
  changed: N switches" (a preset moves dozens). Lights are summed up the same way, "9 lights on", "1 light
  on, 9 off" (a lights test, power coming on or going off).
- **A flight load is silent.** `ResetAnnouncements` (from `OnSimContextReset`) silences everything;
  `OnConnectionBatch`, which runs when the BBS Nest check settles, sends the list again (a fresh baseline in
  the agent) and calls `Settle`; speech starts 5 s later (`SettleQuietMs`). `OnConnectionBatch`'s announcer
  may be suppressed, so nothing is spoken inline there.
- **Ctrl+M** (`Bbs757CockpitAnnouncements.MonitorRows`, added by `AddCockpitMonitorRows` after the
  variables' rows): "All Annunciator Lights", "All Switches From Any Source" (it mutes the burst line too),
  one "Switches: <panel>" row per panel, keyed by panel name, then "Light: <label>" per light and "Switch:
  <panel>, <label>" per switch. `IsMuted` checks a row's own key, its group's and, for a switch, its
  panel's. The keys start `BBS757W_` and live in the same disabled set as every other 757 row. The lines
  are spoken outside MainForm's mute wrap, so the mute is checked here.
- **Off in tests.** `BBS757Definition.CockpitWatchEnabled` is false for the whole test assembly: a
  definition fed a settling batch would otherwise start a real tablet client and, on a PC with the 757
  loaded, take the view's one socket from the running app.

**No capture call-outs.** Two autolands (2026-10-27 and 2026-10-28), with every BlueBird L:var read in a
loop, found no variable that follows a flight mode, FLARE or ROLLOUT; the only stand-ins for a localizer or
glideslope capture are indirect (the LNAV light going out with APP lit; the ALT HOLD light going out, and
only when the glideslope is met in ALT HOLD). Nothing is built on them: the flight mode annunciations are
read from the aircraft's memory instead (see the FMA reader).

## Altimeters, minimums and squawk

- **Ctrl+B, "Altimeter and minimums"** (`Forms/BBS757/BBS757AltimeterForm.cs`, `Bbs757Altimeters`). The
  altimeter box takes inches (27.00 to 32.00) or hectopascals (940 to 1090), typed in any culture (CORE-17),
  and sends `K:KOHLSMAN_SET` with 16 × hPa. Measured 2026-10-25: 16320 set all three altimeters (`KOHLSMAN
  SETTING MB:1..3`) to 1020, the reads lagging a few seconds, while `K:KOHLSMAN_INC` moves only altimeter 1
  and is not used. Standard sends 16212 (1013.25 hPa), and so does a typed standard value (29.92 inches, or
  1013 or 1013.25 hPa; 29.92 inches alone would be 16211). The three are read every second for up to 6 s
  and spoken: once when they agree within 0.5 hPa (`AltimeterPhrase.Sentence`, the words every aircraft
  uses), else one by one, numbered as the simulator numbers them (which is the captain's, the first
  officer's or the standby is unmeasured).
- **Radio minimums** in the same window: the stock `DECISION HEIGHT` is the ADI's DH (the ADI showed DH200
  with the stock variable at 200), is read-only, and steps 10 ft per `K:INCREASE_DECISION_HEIGHT` /
  `DECREASE_DECISION_HEIGHT` (measured 2026-10-25). A set reads it, sends the difference (at most 250 steps
  a round), then, as the MCP speed set does, reads until it settles and re-sends a shrinking remainder up to
  three times; a read outside 0 to 2500 ft sends nothing ("DH unavailable"). Spoken: "DH 200".
- Both ride the MCP sets' machinery (`RunMcpSetAsync`): refused aloud when the calculator cannot land a
  write, a repeat of the same value ignored while one is in flight, canceled on a flight load or a profile
  switch. The window's status box opens on the current values and keeps the last result.
- **Squawk**: the TCAS and transponder panel's "Squawk Code" field (`Bbs757Squawk`), four digits 0 to 7,
  sent as `K:XPNDR_SET` in BCD (measured 2026-10-25: 0x4743 set 4743, a decimal 4743 set 1207), `TRANSPONDER
  CODE:1` read back 1.5 s later and spoken as one number, "Squawk 4743" (the owner's rule on every
  aircraft); a transponder holding another code says "Squawk 4743 entered, the transponder reads 1200". The
  panel's status display shows the code. The definition takes the box's raw text (`HandleUITypedText`,
  offered by MainForm before it parses the number), so an empty box says "Type a four-digit squawk first."
  and letters or an 8 or 9 say "Squawk must be four digits, each 0 to 7." 0000 is a real code.

**Changes from any source are announced**, each with a Ctrl+M row ("Squawk", "TCAS Mode", "Altimeter"):
- **The squawk** ([B757-54]). `Bbs757Annunciators.SquawkWatchKey` is `Bbs757Squawk.CodeKey`: the watch is
  the squawk field's own read-back row, made a batched announced row, not a second row. Two Continuous rows
  on one variable name shift every later slot of the batch ([VAR-7]), and `VarNameCollisionTests` fails on
  it. A code turned on the panel's knobs is spoken "Squawk 4743"; the field's own set arms a 5 s echo first
  (`OnOwnSquawkSet`), since its read-back is the one confirmation.
- **The TCAS mode**, `L:B757_PED_TCAS_MODE_KNOB` (0 to 4) under `BBS757_TCAS_MODE_WATCH`: "TCAS STBY", "TCAS
  ALT RPTG OFF", "TCAS XPNDR", "TCAS TA ONLY", "TCAS TA/RA". A pick on the panel is a linked control, so it
  is not said a second time.
- **The altimeter**, the stock `KOHLSMAN SETTING MB:1` under `BBS757_ALTIMETER_WATCH`, in the B key's words
  ("Altimeter: 1020, 30.12", "Altimeter standard"). A baro knob turning is heard once, where it stops: the
  value waits in a `Bbs757RestingValue` until it has gone 1.5 s without a newer change, released by a 250 ms
  UI timer, which checks the row's mute itself. The app's own Ctrl+B set is not repeated: the value counts
  as spoken while the set runs, for 5 s from its start (`OnOwnAltimeterSet`) and for 3 s after it ends. A
  reading of 0 (unpowered) is not a pressure and is ignored.

## The MCP value windows (Ctrl+H, S, A, V)

`BBS757Definition.Mcp.cs`, the sets and phrases in `Bbs757Mcp` and `Bbs757Mach` (pure). Each is the HS787's
modeless `ValueInputForm`: Enter sets the value and the window stays open. The MCP's values are BlueBird's
own L:vars; the stock autopilot variables sit at unrelated offsets (stock speed 100 against 200 shown,
2026-10-25) and are never read. Heading and altitude are direct writes of `L:BBS_AP_TARGET_HEADING` and
`L:BBS_AP_TARGET_ALTITUDE` (a written 90 gave 091 after one knob step; a written 12000 held); the vertical
speed `L:BBS_AP_TARGET_VS` is written directly (500 and -1500 read back), then stepped by
`K:AP_VS_VAR_INC/DEC` (100 fpm each) if the window did not take it. What is spoken is the value read back,
never the request ("Heading 090", "Speed 250", "Altitude 12000", "Vertical speed minus 1500"). Ranges:
heading 0 to 360, speed 100 to 399 kt or Mach 0.40 to 0.86, altitude 100 to 49000 ft rounded to 100,
vertical speed -8000 to 6000 fpm rounded to 100. A set is refused aloud when the calculator cannot land a
write; a newer set of the same value supersedes one in flight, except that a repeat of the speed being set
is ignored.

**The speed** (`Bbs757Mcp.SetSpeedAsync`, [B757-3]). The target `L:BBS757_ORANGE_AIRSPEED_BUGS` is
read-only (a written 210 was overwritten) and moves only by `K:AP_SPD_VAR_INC/DEC`, which BlueBird speeds
up within a burst, as a knob turned fast: events 1-10 move 1 kt each, 11-25 2 kt, from the 26th 5 kt
(measured 2026-10-25: 10 events +10, 20 +30, 25 +40, 30 +65). A burst is one calculator call or several
back to back; a pause of about 0.3 s starts a new one. Sets that sent one event per knot went badly wrong
on the first flight: 53 events moved the target 180 kt and 47 drove it to the 100 kt floor. A set reads the
target, sends one planned burst (`SpeedBursts`: the most events whose tiered sum does not pass the
change), waits `SpeedBurstGapMs` (600 ms, twice the reset) and sends the 0-4 kt left as a burst of its own.
Each burst is one RPN loop, `N sp0 :1 l0 0 > if{ (>K:AP_SPD_VAR_INC) l0 1 - sp0 g1 }` (`SpeedBurstCode`),
short for any count. It then reads until two reads 150 ms apart agree and, while the remainder shrinks,
corrects it up to three times in bursts of at most 10 events (`LinearBurstMax`), each followed by the same
pause, so every correction event moves 1 kt. 200 to 153 is 26 events (45 kt) and 2; 100 to 280 is 53
events; every speed from 100 to 399 lands with no correction on the measured tiers (`Bbs757McpTests`). A
newer speed set that supersedes one just after its burst first waits out the rest of that pause from the
last speed write, whichever set sent it (`SpacedAsync`), so its burst is not counted into the old one's.

**The blank window under VNAV.** `L:BBS_IAS_BLANKED` is 1 while VNAV owns the speed and the MCP window is
blank. Measured in a VNAV climb on 2026-10-26: the bug behind the blank window still read 250 while the
aircraft flew 262 kt; Speed Intervene opened the window on 261, with VNAV still engaged; the descent showed
the same. So while the flag is 1 the speed box takes no value (`McpInputEnabled`; an unread flag keeps it
open), and Shift+S says "MCP speed window blank. Speed Intervene opens it." rather than the stale target.
The flag is a batched row that is announced but consumed (`ProcessAutoflightUpdate`), with no Ctrl+M row:
only a Continuous variable that is also `IsAnnounced` joins the batch (measured 2026-10-26: left
unannounced it was never delivered), and the windows' 400 ms caption refresh needs it in the cache.

**Mach** (`Bbs757Mach`). The speed box takes knots ("250") or a Mach in hundredths ("0.78", ".78", "M.78",
"m0.78", a comma decimal too, CORE-17); a Mach with three decimals, an "M" before knots, or anything out
of range says "Enter a speed from 100 to 399 knots, or a Mach number from 0.40 to 0.86." Measured level at
FL290 on 2026-10-26, the pilot pressing in the app's windows and the variables read through MobiFlight:
- **The changeover.** VNAV did not change to Mach by itself; the IAS/MACH button set
  `L:BBS_AIRSPEED_IN_MACH` to 1. On the ground the same press changes nothing (2026-10-25, twice). A set in
  the units the window is not showing presses IAS/MACH first, silently (`EnsureUnitsAsync`), and reads the
  flag every 250 ms for up to 2 s: if it does not change the set says "IAS/MACH changeover is not available
  now" and sends nothing more. The changeover is a toggle, so a Mach set with the flag unread presses
  nothing ("Mach unavailable").
- **The Mach is read from the speed window's wheels, never `L:BBS_TARGET_MACH`** ([B757-50]). In Mach mode
  `L:BBS_TARGET_MACH` stayed 0 and `L:BBS757_ORANGE_AIRSPEED_BUGS` became the Mach's IAS equivalent (281.1).
  `B757_MCP_Gau_SPD_AUTO_100` and `_10` are wheel positions: the hundreds wheel reads 10·d and shows the
  tenths digit, the tens wheel reads 10·(d+1) and shows the hundredths (70 and 40 are ".73").
  `Bbs757Mcp.MachFromDrums` decodes them and answers null for a wheel between digits and for anything below
  .40: in IAS the wheels show knots, which decode as .10 to .39, and they still show knots for a second or
  two after a changeover.
- **Steps and limits** ([B757-51]). One event moves the target 0.01 Mach; bursts follow the knot tiers (5
  events +5, 10 events 10; a burst of 20 downward stopped at the .40 floor). A burst of 30 took .40 to .95:
  there is no stop at the aircraft's .86, and events past the 25th were not measured cleanly. So the app
  keeps to 0.40 to 0.86 itself, `Bbs757Mach.Bursts` plans no burst past 25 events, and `SetMachAsync` never
  corrects more in the set's direction than the planned difference in all (a burst that seems short may
  still be rolling in). An overshoot is brought back.
- **The loop** waits for the wheels: they move 1 to 2 s after a burst. It reads until two reads 500 ms
  apart show the same Mach (none within 3 s: "Mach unavailable", nothing sent), sends the burst and its
  rest, waits for the wheels to leave the old value and to agree again, then corrects. Spoken: "Mach 0.78".

**The mode buttons** (`McpWindowButtons`, laid out by `Bbs757McpWindowLayout`), as the PMDG 737's windows
carry theirs. The keys are fixed by node, so a relabelled control keeps its key, and they match the PMDG
windows:

| Heading | HDG SEL Alt+S, HDG HOLD Alt+H, LNAV Alt+L |

### Autoflight announcements

`Bbs757AutoflightAnnouncements` holds the keys and words; the definition's `ProcessAutoflightUpdate` feeds
them. All watch BlueBird's own variables on the 1 Hz batch, each a row of its own key on a name the sets
read on request under another key (never two Continuous rows on one name, [VAR-7]).
- **The MCP values once they rest**: "MCP heading 090", "MCP altitude 12000", "MCP vertical speed minus
  1500", "MCP speed 250", "MCP Mach 0.78", each with a Ctrl+M row. A continuous row is delivered only when
  it changes, about once a second, so "rested" is 1.5 s with no newer change (`Bbs757RestingValue.RestMs`;
  anything under the 1 s delivery period would speak every step of a spin). A 250 ms UI timer releases them
  (`ReleaseRestedAutoflight`), outside MainForm's mute wrap, so it checks each row's mute itself ([VAR-8]).
  A value spun away and back says nothing; the first value after a flight load is a silent baseline.
- **The app's own sets are not repeated.** A row whose value is being set from a value window, or was
  within the last 3 s (`OwnSetEchoMs`), takes the new value as spoken: the set spoke its read-back.
- **The speed rows are judged once the batch is in** ([B757-52], `EvaluateSpeedRows`). Whether the speed or
  the Mach may speak depends on the blank flag and the Mach flag, and the batch arrives sorted by name: the
  speed and the Mach's hundredths wheel before the Mach flag, the blank flag and the tenths wheel. Judged
  per delivery, a changeover would speak the Mach's IAS equivalent as a new speed. So the five inputs are
  only kept as they arrive, and the timer's next tick judges them together (a batch is delivered in one go
  on the UI thread, so a tick never falls inside one). The speed speaks only with the window open in IAS,
  the Mach only with it open in Mach. A change of either flag is no knob turn (VNAV taking or giving back
  the speed, Speed Intervene, a changeover): both rows take their values as spoken and anything waiting is
  dropped. The Mach flag and the tenths wheel are silent rows with no Ctrl+M row.
- **A/T arm**, `L:BBS_AUTO_THROTTLE`: "A/T armed" / "A/T disarmed", once per change, from any source, a
  press of A/T Arm in the app included.
- **The disconnect lights**, `L:B757_MAIN_APDISC_1_DECAL` and `L:B757_MAIN_ATDISC_1_DECAL`: "Autopilot
  disconnect" and "Autothrottle disconnect" as the light comes on. Going out is tracked and silent, so the
  light coming on again is a change. "Autopilot disconnect" was heard once from the yoke button in flight
  on 2026-10-27.

## Radios

`BBS757Definition.Radios.cs`; the pure parts are `Bbs757Radios` (COM), `Bbs757NavRad` (VOR, courses, the CDU
pages' parsers) and `Bbs757IlsPanel` (the ILS knobs and words).

### COM

BlueBird's VHF L, C and R are the simulator's own COM 1, 2 and 3 ([B757-8]). Measured 2026-10-25 on the
ground: one step of `L:B757_VHF_L_FRAC_INC` moved `COM STANDBY FREQUENCY:1` from 120.900 to 120.905 (the
`VHF_C` knobs tune COM 2, `VHF_R` COM 3), and a standby set with the stock `K:COM2_STBY_RADIO_SET_HZ` stayed
and the knob continued from it, so the module keeps no frequency of its own. Measured 2026-10-26 at KATL: the
three stock swaps (`COM_STBY_RADIO_SWAP`, `COM2_RADIO_SWAP`, `COM3_RADIO_SWAP`) each swapped their radio and
held; tuning panel 2's transfer button swapped COM 2 and panel 3's COM 3.

- **The panel.** "COM radios", the app's own panel in the Pedestal right after the transponder's
  (`AddRadioPanels`): for each radio a "COMn Standby Frequency" box and a "COMn Transfer" button, and a status
  display of the six frequencies with three decimals (`Bbs757Radios.Frequency`: "121.900", where the unit
  alone would round to "122").
- **The rows.** `COM ACTIVE FREQUENCY:n` and `COM STANDBY FREQUENCY:n` in MHz on the 1 Hz batch, a Ctrl+M row
  each. A change is spoken once, "COM1 active 124.850" / "COM1 standby 121.500", the other Boeings' words,
  after a silent first reading (`ProcessRadioUpdate`, `Bbs757ChangeTracker`). The phrase is the three-decimal
  text, so the simulator's float noise (121.9 read as 121.89999999999999) is never a change.
- **A typed standby** (`SetStandbyAsync`). The definition takes the box's raw text (`HandleRadioTypedText`).
  `Bbs757Radios.TryParseCom` reads it in any culture (CORE-17): digits and one "." or ","; two decimals ending
  2 or 7 get a trailing 5 ("121.57" is 121.575); then 118.000 to 136.990 with the kHz part mod 25 being 0, 5,
  10 or 15. An empty box says "Type a frequency first."; anything else refused "Frequency must be 118.000 to
  136.990, on a 25 or 8.33 kilohertz channel.". When no calculator write can land: "COM1 unavailable", nothing
  sent. Otherwise `<Hz> (>K:COM_STBY_RADIO_SET_HZ)` (COM 1's events carry no digit; `COM2_…`, `COM3_…`), and
  1.5 s later the standby row is read fresh and what it holds is spoken ("COM1 standby 121.500"), never the
  request (CORE-7); unreadable: "COM1 standby 121.500 sent, the radio did not report back". The row's own
  change meanwhile is that write's echo (`ArmOwnWriteEcho`) and is not said a second time.
- **A transfer** (`TransferAsync`). Both rows are read fresh, their echo windows opened, the stock swap
  written, and 1.5 s later both rows read again. Swapped (`Bbs757Radios.Swapped`: the new active is the old
  standby and the reverse, compared at 1 kHz; equal rows count as swapped) says one sentence from what the
  radio reports: "COM1 active 121.500, standby 124.850". A row unreadable afterwards: "COM1 transfer sent, the
  radio did not report back". Rows left as they were go to the fallback (`PanelFallbackAsync`): the three
  tuning panels' lights are read fresh (`L:BBS_RTP_L_LIGHTS`, `_C_`, `_R_` for panels 1, 2, 3; bit 2 VHF L, 4
  VHF C, 8 VHF R; read 2, 4, 8 on 2026-10-26), the first panel whose lights select the radio
  (`TransferPanelFor`) has its button `L:B757_PED_COMHEAD_<n>_SWAP_BUTTON` held 1 for 200 ms and released, and
  the rows are read again: the sentence, or "COM1 did not transfer". No panel selecting the radio: "No tuning
  panel selects COM1", nothing pressed. A second press of the same radio while its transfer runs says "COM1
  transfer in progress" (each swap toggles, so two could undo each other); other radios run at once. A flight
  load, a dropped connection or a profile switch stops a transfer silently, so it never presses a panel button
  into the next flight; a button already held is still released.

### NAV: VOR tunings and courses

BlueBird's VOR and ILS receivers are its own, so the 757 never reads the stock NAV variables ([B757-5]).
Measured: on 2026-10-25 the VOR/DME panel showed 116.90 AUTO while `NAV ACTIVE FREQUENCY:1..3` read 110.50,
and a write of `L:BBS_ILS_COURSE` (95, held) left `NAV OBS:1..3` at 0; on 2026-10-26 `NAV ACTIVE
FREQUENCY:1..4` stayed 110.50 and `NAV HAS LOCALIZER:1..3` 0 with the ILS panel on 108.70; on 2026-11-05 in
cruise they read 110.50 throughout while the ILS panel and the FMC-tuned VORs changed. So
`BBS757Definition.UsesStockNavReceivers` is false: the shared "glideslope alive" call-out, which reads NAV 1,
is not registered on the 757 (no Ctrl+M row either), and output N never falls through to MainForm's stock
readout.

- **VOR frequencies** come from the NAV RADIO page of the first officer's CDU, brought up through
  `Bbs757CduPages` (see CDU) and left there. The page as measured on CDU 2 on 2026-10-26: row 0 the title, row
  1 `VOR L … VOR R`, row 2 the tunings, row 3 `CRS RADIAL CRS`, row 4 the courses. The sides are mirrored:
  VOR L is `freq[mode][ident]` flush left (`116.90AGSU`, `113.90R`), VOR R `[ident][mode]freq` flush right
  (`GSUR116.90`); the mode letter is A (the FMC tuned it), R (tuned from the CDU) or M (on the VOR/DME panel);
  `------` is not tuned. `Bbs757NavRad.Parse` splits row 2 at column 12 and reads each side on its own, so a
  side it cannot read is "frequency unavailable", never "not tuned", and the other side is still read.
- **The fallback.** When the page cannot be had (the CDU busy with the pilot's keys, the tablet view
  unreachable), N reads BlueBird's own variables instead: `L:BBS_757_VOR_L_FREQ`, `L:BBS_757_VOR_R_FREQ` and
  the auto-tuning flags `L:B757_MCP_VOR1_MODE_AUTO`, `L:B757_MCP_VOR2_MODE_AUTO` (1 auto, 0 manual), through
  `Bbs757NavRad.TuningFromVariables`. The frequency variables came with BlueBird's 2026-10-31 update and are
  not in its public table; read 2026-11-05 in cruise, FMC-tuned: 114.5 and 115.1, later 116.05 and 116.4 as
  the FMC retuned, both flags 1. A reading of 0 counts as unread (an older build reads an absent L:var as 0);
  a value outside 108.00 to 117.95 is "not tuned" (what a not-tuned receiver reads is unmeasured). The
  variables carry no ident, and the mode is only auto or manual.
- **Courses** are BlueBird's L:vars `BBS_VOR_L_COURSE`, `BBS_VOR_R_COURSE` and `BBS_ILS_COURSE` (whole
  degrees), OnRequest, read at each readout, no Ctrl+M row. A VOR's CRS field exists only while that VOR is
  tuned by hand: in AUTO the CDU blanks it and silently ignores a course entry (measured 2026-10-26: `095` at
  2L did nothing in AUTO, and wrote `BBS_VOR_L_COURSE` 95 after a manual tune). So a VOR's course is spoken
  only when it has a frequency and a mode other than auto.
- **Output N** (`ReadNavRadiosAsync`, the sentence in `Bbs757NavRad.Readout`): "VOR L 116.90 auto, GSU. VOR R
  113.90 remote, course 095. ILS course 095. ILS 110.50." The tuning words are "auto", "remote", "manual",
  "VOR R not tuned", "VOR R frequency unavailable"; frequencies have two decimals and a dot in any culture,
  courses three digits. The last sentence is the ILS control panel's display ("ILS 110.50.", "ILS parked.";
  below). With neither the page nor the variables: "VOR L course 095, VOR R course 000, ILS course 095. ILS
  110.50. VOR frequencies unavailable." A course that was not read is "course unavailable"; a readout never
  goes silent. Nothing is written.

### The ILS control panel

The ILS panel on the aft pedestal is not tuned by the FMC and is in no instrument view.

- **The display** is BlueBird's `L:BBS_757_ILS_FREQ` ([B757-10]): -1 while the panel is parked, its frequency

  anything else (unread, 0, off the channels) is no reading. The variable came with BlueBird's 2026-10-31
  update and is not in its public table. Measured 2026-11-05 in cruise at FL320, each read about 1 s after
  the write: parked -1; whole knob +1 108.1; fraction +1 108.15; put back, -1. Whether MSFS 2020 installs
  carry it is unmeasured. No picture of the panel is read: an earlier reader that captured the panel's gauge
  and recognized its digits is gone from the code, and must not come back.
- **The knobs** (`Bbs757IlsPanel`, measured on the ground 2026-10-26, each step read off the panel's gauge).
  They are step requests, `L:B757_ILS_FREQ_WHOLE_INC` and `L:B757_ILS_FREQ_FRAC_INC`, written +1 or -1 and
  cleared by BlueBird within a frame. The whole knob is a ring of five with no end stop: 108, 109, 110, 111,
  PARK, 108 (+1; the reverse for -1), and it keeps the fraction. The fraction knob steps through the ten ILS
  channels only, .10 .15 .30 .35 .50 .55 .70 .75 .90 .95, wrapping .95 to .10 with no carry; while parked it
  does nothing, and PARK remembers the fraction (111.75, PARK, +1: 108.75). `Bbs757IlsDial` is that model;
  `PlanSteps` gives the fewest clicks, with one rule: the ILS is parked only where a plan starts or ends,
  never on the way between two frequencies (the manual warns that parking it with approach guidance selected
  can raise an RW/ILS alert), so 108 to 111 is three clicks, not two through PARK.
- **One click, one write, paced** ([B757-59]). Measured 2026-10-26 with a harness sending the app's own
  calculator strings, the sim at about 30 frames a second (median frame 33 ms, one frame of 192 ms seen): a
  request is consumed within one frame; a write of 2 moved one channel (108.35 to 108.50), so clicks cannot
  be batched into one write; and two writes landing in one frame count once (six writes 1 ms apart moved 1
  step, 20 ms apart 4, 50 ms and 150 ms apart all 6). Through SimConnect the request never read non-zero (0
  in all 8,485 frames read), so nothing confirms a click. Each click is therefore one
  `ExecuteCalculatorCodeUnique` write (`StepCode`: "-1 (>L:B757_ILS_FREQ_WHOLE_INC)"; a click repeats the same
  string, and MobiFlight drops an identical repeat), sent only after a fresh read of the ILS course has come
  back (the sim answers in a frame after the last click went out) and `IlsStepGapMs` (250 ms) after the click
  before it, the first click of a set after what is left of that gap since the last click of any set. The gap
  thus follows the sim's frames as well as the clock. A read that checks clicks waits the same way first.
- **A set** (`SetIlsAsync`, a frequency or PARK) reads the display, clicks, and reads it again; short of the
  target it plans once more from that read. What it says is what the display shows: "ILS already 110.50" or
  "ILS already parked" (no click), "ILS 110.50 set", "ILS parked", and after the second try "ILS shows 110.55,
  not 110.50". Never that a station is received. Refused aloud, nothing sent: "ILS unavailable" (no write can
  land), "ILS tuning in progress" (another set still turning the knobs). A read the sim does not answer before
  a click stops the set: "ILS unavailable after 3 of 5 clicks.".
- **The count.** The definition also keeps `_ilsDial`, its own tally of the panel: PARK with .10 once a flight
  has loaded and runs (`Bbs757IlsDial.LoadState`; the owner's flight on 2026-10-26 was in its starting panel
  state, and the first step proved the hidden .10: PARK -1 gave 111.10; other start types are unmeasured),
  replaced by every reading of the display, moved by every click sent, and unknown after a dropped connection
  or in a definition made after the flight loaded. It serves two things. The display hides the fraction while
  parked: with no count, a set to a frequency first turns the whole knob +1 out of PARK and reads what the
  display then shows ("ILS display could not be read: the ILS left PARK." if it cannot). And when the display
  cannot be read at all (a BlueBird build without the variable), the set clicks from the count and says so:
  "ILS 110.50 set by count: the ILS display could not be read.", or "ILS tuning unknown: the ILS display
  could not be read." with no count; N and the window's status then say "ILS 110.50 by count." / "ILS parked
  by count." / "ILS tuning unknown.", so a count never sounds like a reading.
- A flight load, a dropped connection or a profile switch stops a set between clicks, silently; after a load
  or a drop the window's status shows the count, unsaid.

## CDU

### How the screens are read and the keys pressed

`SimConnect/BBS757/CoherentBbs757TabletClient.cs` with `Resources/coherent-bbs757-tablet-agent.js`
(`window.__MSFSBA_BBS757`), over the Coherent debugger (127.0.0.1:19999) in BlueBird's hidden helper view
"VCockpitNN - BBSTablet", resolved by title on every connect (its number changes with each aircraft load).

- **Screens.** BlueBird's systems WASM sends each CDU's screen on the simulator's Comm Bus when it changes:
  `BBS_CDU_DISPLAY_1` (captain) and `BBS_CDU_DISPLAY_2` (first officer). Measured 2026-10-25 with a listener
  injected into the view: the payload is MobiFlight's WinCtrl JSON, `{"Target":"Display","Data":[…]}`, 336
  cells for 14 rows of 24 columns, row-major, a cell `[]` (blank) or `[char, color, size, inverse]` (color a
  letter, `g` green; size 1 small; inverse 0 or 1); nothing arrives while a page is static; the two CDUs are
  independent. So the agent registers a `JS_LISTENER_COMM_BUS` listener and keeps the last frame per CDU. The
  captain's current screen can be had at once: BlueBird's own `<bbs-tablet>` element keeps it as
  `lastMobiFlightCduPayload`, which seeds CDU 1 at install. The first officer's has no such cache: after an
  aircraft load it has no frame until its screen first changes (a page key brings it).
- **The frame** (`Bbs757CduFrame.Parse`, pure, never throws) becomes a `Bbs757CduScreen`: 14 lines of exactly
  24 characters (line 0 the title, 1 to 12 the label and data rows of the six line select keys, 13 the
  scratchpad) and the same grid as `Bbs757CduCell`s with color, size and inverse. A short frame is padded, a
  bad cell is blank, bad JSON or another target is a blank screen. The CDU's entry-box glyph `☐` reads as `_`.
- **The loop** scrapes the `ActiveCdu` only (1 or 2; setting it asks for that CDU's screen at once), every
  350 ms while the CDU window is shown (`SetActive`) and every 1000 ms otherwise (every 500 ms while the
  cockpit watch list, which shares this client, is not empty). The agent answers the frame only when its tag
  differs from the caller's, and the client raises `ScreenUpdated` on a change, `ScreenLost` when a new agent
  holds no frame for a CDU that had one. `ScrapeAsync` reads either CDU once on demand, whichever is active,
  waiting at most 4 s; it never connects itself.
- **Keys** are L:vars the cockpit holds at 1 while pressed, `L:B757_CDU_<1|2>_<KEY>`, 69 names per CDU
  (`Bbs757CduKeys.All`, the same list the agent whitelists; a test keeps the two equal). The agent's `press`
  sets 1 and, after the hold, 0. The hold matters (measured 2026-10-25): 1 then 0 held 0.25 s typed a letter
  every time and CLR removed one character; CLR held 1 s cleared the whole scratchpad, a message included, as
  on the aircraft.
- **The queue.** One queue for both CDUs, so presses never overlap. Each key carries its hold (`KeyHoldMs`
  250; clamped to 100 to 1500 here and in the agent) and the pause after its release (`KeyGapMs` 400; clamped
  to `MinGapMs` 50 to `MaxGapMs` 1000); `CycleMs` is hold plus gap, 650 ms for a standard key, and the pump
  waits that long from the press's answer before the next key. Only two callers differ: the long CLR (1300
  ms) and the CDU window's typed entries (below). `MinGapMs` is a floor, not a safe gap. `PendingKeyCount` is
  the keys queued or still in their cycle, on either CDU.
- **Ownership.** One client per view: the definition owns it (`BBS757Definition.EnsureTabletClient`, made and
  started on first use from the UI thread: normally the first connection batch, which hands it the cockpit
  watch list), and the CDU window, the page service and the tablet window's Navigraph read share it; a window only
  subscribes. `OnSwitchedAway` closes the CDU window first, then disposes the client; a late call after that
  gets a disposed client that reads and presses nothing.
- **Reconnects.** A socket still open whose agent went missing (the page re-evaluated), is older than
  `AgentVersion` (an app update over a loaded flight) or cannot hear the Comm Bus (no listener, or one not
  ready for 5 s) gets the agent installed again on the same socket; an install the page answers NOT_READY
  (after an aircraft reload its own scripts have not run yet) is retried. Three evals unanswered drop the
  socket, and the view is resolved again (retried every 2 s while it cannot be found). A re-install over a healthy agent keeps its frames, since
  the first officer's could not be had back. `IsReadable` is true only while the socket is open, the agent
  installed and a scrape was answered in the last 5 s.
- **`KeysDropped`.** Whenever the link is lost, every queued key is thrown away, never sent later to a page
  nobody has checked, and the event is raised once per outage. The CDU window says "CDU connection lost, keys
  not sent", shown or hidden.

### The page service

`Bbs757CduPages` (`BBS757Definition.CduPages`, one per definition, over the tablet client through
`IBbs757CduLink`) is for features that read CDU pages in the background.

- **It presses keys on the first officer's CDU only** (`FirstOfficer` = 2) and reads either: the captain's
  CDU, the one the pilot works, never changes under him (the owner's decision). A call that would press a key
  on CDU 1 refuses.
- **One call at a time**, behind one gate (waited for at most 5 s). A call that would press keys also refuses
  while `PendingKeyCount` is above zero, the pilot's own keys from the CDU window included, rather than
  interleave with them, and while the tablet view is not readable. Every call answers null (false) instead of
  throwing, and stops as soon as the view is lost.
- **`ShowPageAsync(cdu, pageKey, isWanted)`** reads the screen and returns it when the caller's predicate
  already accepts it (the page is identified by its title, `Bbs757CduTitle`); otherwise it presses the page
  key and reads every 250 ms for up to 3 s (by the sleeps and by the clock, since one read can take seconds)
  until the predicate does. A screen that reads null is "not the page wanted", because the first officer's
  CDU has no frame until a key changes it. `PressKeysAsync` presses a sequence, waits for the queue to drain
  and 1200 ms more, and reads once.
- **`EnterAsync(cdu, text, lineKey)`** wipes the scratchpad, types the text, and presses the line key only
  when the scratchpad shows exactly the typed text once the keys have gone out; a CDU message, a lost key or
  keys still queued get the scratchpad wiped again and null, never a wrong entry.
- **The wipe** (`WipeScratchpadAsync`): CLR held 1300 ms, the scratchpad read 1800 ms later, and, if anything
  is left, CLR held 1300 ms again. Measured 2026-10-26 on the first officer's CDU, 60 runs typing
  `KATL1100.5`: one CLR held 1300 ms cleared the whole scratchpad 45 times and removed only the last character
  the other 15, where a second long CLR cleared the rest every time (15 of 15). A short CLR as the second
  press would remove one more character and leave the rest. A CLR on an empty scratchpad does nothing
  (measured 2026-10-28), so the second hold is harmless.
- **Who uses it.** Output N and the Ctrl+N window (NAV RADIO, APPROACH REF; see Radios), and output D and
  Shift+D, which read PROGRESS page 1 on the first officer's CDU (`Bbs757Prog.ReadPageOneAsync`: PROG, then
  PREV until the counter reads 1) and leave it there. All of these only bring pages up and read them;
  `EnterAsync` and the wipe have no caller in the app today. The flap speeds (Shift+1 to Shift+6) do not use
  the CDU ([B757-9]).

### The CDU window (Shift+M)

`Forms/BBS757/BBS757CduForm.cs`, the HS787 FMC window's layout and keys, fed by the tablet client's pushes. It
needs no SimConnect connection. The window is made hidden when the 757 becomes the aircraft (for the message
watch, below); `MainForm.ShowBBS757CduDialog` shows it on Shift+M, making it first if it is not there. Escape
or close hides it; it is disposed on a profile switch.

- **The rows** (`Bbs757CduRows.Build`), the shape the other Boeing CDU windows list: "Title: " and the page
  name, then three spaces and the counter ("Title: ACT RTE 1 LEGS   1/7"); for each line select key its label
  row, indented three spaces and left out when blank, and its data row "n: …" ("n:" alone when blank); last
  "Scratchpad: …" ("Scratchpad:" when empty). A label row of 20 or more dashes and nothing else is the page's
  separator rule and is left out; dashes with text among them stay. Trailing spaces are dropped and interior
  ones kept, so a right-hand field stays in its column on a braille display; no row passes 36 cells. A screen
  with nothing on it is one row, "Captain CDU screen blank" or "First officer CDU screen blank". With no
  screen yet the list says "Waiting for the 757's CDU. Is the aircraft powered?", or for the first officer's
  "Waiting for the first officer's CDU. It shows once its screen changes: press a page key, such as Alt+R for
  RTE.".
- **The cursor follows the row's identity, never its index** ([B757-57]). A row is its kind (title, label,
  value, scratchpad) and line (1 to 6). A label row is listed only when it has text, so a constraint deleted
  above the cursor removes a row and shifts every index below it. `Bbs757CduRows.Restore` puts the cursor on
  the row of the same kind and line, else the first row of that line, else the same index clamped.
- **Page change against title change.** `IsPageChange` compares the page's identity (`Bbs757CduTitle.Identity`:
  the title without its counter and without a leading "ACT " or "MOD ") and the page number. Another page
  speaks its title (`Bbs757CduTitle.Spoken`, the whole title with its spaces collapsed: "ACT RTE 1 LEGS 1/7")
  and moves the cursor to line 1's data row. A new title on the same page (ACT turning into MOD after an
  entry, 1/2 becoming 1/3 when a waypoint adds a page) is spoken too, as on every other aircraft's CDU window
  (the owner's decision of 2026-10-27), but the cursor stays.
- **The VNAV pages share one identity.** Their titles change with the speed mode (ACT ECON CLB becomes MOD
  250KT CLB when a speed is entered), so any title ending CLB, CRZ or DES is the identity "VNAV" and the three
  are told apart by page number alone (CLB 1/3, CRZ 2/3, DES 3/3, read live 2026-10-27).
- **Selection markers** ([B757-56], `Bbs757CduMarkers.Mark`). A run of inverse cells in a label or data row
  reads with "X " in front of it, as on the other Boeing CDU windows. The marker never moves a later column:
  it takes the two blanks in front of the run when they are free, else the cells it inserts are paid back by
  the next gap with a blank to spare (a gap always keeps one blank, so words never merge). A marked row may be
  37 cells, which with the three-cell row prefix is the 40 cells of a braille line; markers are dropped,
  rightmost first, only when a row would pass that. Color and size mark nothing. What BlueBird sends was
  measured 2026-10-28 in cruise: 62 page reads, about 55 distinct pages on the first officer's CDU (the
  INIT/REF tree, RTE, LEGS, DEP/ARR, VNAV, PROGRESS, FIX, NAV RADIO, FMC COMM, ATC, MENU and the ACARS menus,
  a modified LEGS page among them) showed only the color `g` and never an inverse cell; small size marked
  label rows, units and the page counter. A selection is shown as the CDU's own text, `<ACT>` after `<FMC` on
  MENU, `<ACT>` beside the active SID and runway, `RTE 1 (ACT)`, which the window reads as it stands. So the
  marker is there only in case a page not read uses inverse.
- **Keys to the CDU.** Ctrl+1 to 6 and Alt+1 to 6 the left and right line select keys (F1 to F6 and F7 to F12
  with the alternate layout setting); PageUp / PageDown or Alt+Up / Alt+Down PREV / NEXT; Ctrl+Enter or Alt+E
  EXEC; Alt+letter the page keys (`Bbs757CduKeys.ForAltLetter`); Backspace CLR and Delete DEL on the display
  or in an empty scratchpad box; the same keys as buttons. One physical press is one key (auto-repeat is
  ignored). A key goes out at once behind any already queued; with the link down it is refused aloud: "The
  757's CDU is not reachable.".
- **Typing** (Alt+S focuses the scratchpad box, Enter sends; `Bbs757CduTyping`). Characters map through
  `Bbs757CduKeys.ForChar` (letters, digits, ".", "/", space, "-" one press of +/-, "+" two; a character with
  no key is skipped). Typed keys go out held 100 ms with `GapMs` 300 ms after the release, 0.4 s a key against
  the standard 0.65 s. Measured on the first officer's CDU typing `KATL1100.5`, whose repeated characters fail
  first: on 2026-10-26 every pair down to 100 / 50 landed 5 of 5; on 2026-10-27, pressed through the agent as
  the app does and with the sim busier, 100 / 100 landed 6 of 10 (a repeated digit lost: "KATL100.5"), 100 /
  200 15 of 15 and 100 / 300 10 of 10. 300 keeps one step over the fastest pair that never missed. Never
  shorten it on one quiet measurement ([B757-58]): a repeated character needs the key released long enough to
  count twice, and a busier sim needs longer.
- **The read-back after every typed entry** (`Bbs757TypedEntryCheck`). Once the entry's keys have gone out
  and 300 ms have passed, the scratchpad is judged once. Holding the entry (on its own, or after what the
  scratchpad held before the typing) it is read back as it shows ("KATL"); otherwise the check waits up to 2
  s for a screen newer than the last key and then says `Bbs757CduTyping.Mismatch`'s words at once: "Scratchpad
  shows KAT" (a CDU message is said the same way, "Scratchpad shows INVALID ENTRY") or "Scratchpad is empty".
  Any other key, a CDU switch, hiding the window or dropped keys end the check unjudged, and an entry typed
  behind other queued keys is not checked; the ordinary scratchpad read-back then speaks
  (`CduScratchpadAnnouncer`: the scratchpad's new text, or "Cleared", 300 ms after the last key's cycle).
  Keys are never held back for the check.
- **Alt+C** clears the scratchpad (`Bbs757CduKeys.ClearScratchpad`): two CLRs held 1300 ms (the wipe's
  measurement above), or one DEL only when the last screen shows the scratchpad empty and no key is queued on
  either CDU, as the iFly window's Alt+C. The window says nothing itself; the read-back says "Cleared" or
  "DELETE".
- **Two CDUs.** Ctrl+Tab and the Switch CDU button show the other CDU, Ctrl+Shift+L the captain's, Ctrl+Shift+R
  the first officer's (`Bbs757CduKeys.SideFor`); each says only "Captain CDU" or "First officer CDU", the one
  already shown included. The window's title names the side, "BlueBird 757 CDU (Captain)" / "BlueBird 757 CDU
  (First officer)" (`TitleFor`), since a screen reader reads a window's title as it comes forward. The switch
  sets `ActiveCdu`, and the page title is spoken from the fresh push that follows, never from the older copy
  the window holds.
- **The EXEC light** is not in the window: it is the announced row `BBS757_EXEC_LIGHT` (`L:FMC_EXEC_ACTIVE_1`,
  "EXEC light on" / "EXEC light off", Ctrl+M row "EXEC light"; see Flight-control readouts), so it is heard
  with the window open or closed.
- **CDU messages while the window is closed** ([B757-55]). On hiding, the window points the client at the
  captain's CDU (`ActiveCdu = 1`, whichever CDU it was left on; `OnVisibleChanged`), so the idle scrape keeps
  delivering the captain's screen, and `Bbs757CduMessageWatch` judges each new scratchpad
  (`Bbs757CduRows.NewMessage`): text the FMC put there is spoken as a background announcement, "CDU: TAKEOFF
  DATA UPLINK", "CDU: INVALID ENTRY". Not spoken: a first reading, a cleared scratchpad, the same text, and
  typing (the new text grew from the old one, or is the start of it). The window's own captain keys open a
  settle window of their queue time plus `SettleMs` (2000 ms), inside which no change is a message, because
  the last key of an entry can land between two scrapes; first officer keys do not, as they never touch the
  captain's scratchpad. The watch starts from what the pilot last saw in the open window, so a message heard
  there is not said again; while the window is shown the scratchpad read-back speaks messages instead. Never
  stop the hidden scrape or speak inside the settle window, or messages go unheard or the pilot's typing is
  read out as one. The Ctrl+M row "CDU Messages While Closed" (`Bbs757CduRows.MessagesMonitorKey`, added by
  `AddCduMonitorRows`) turns it off, and so does the window's check box "Speak CDU messages when closed",
  which edits the same entry; the speech comes from the client's push, outside MainForm's mute wrap, so the
  window checks the key itself ([VAR-8]).
- **The watch runs from the moment the 757 is the aircraft.** `MainForm.StartBbs757CduMessageWatch`, run with
  the display readers' start, makes the window without showing it and calls `BBS757CduForm.StartHidden`: the
  client's pushes are marshalled with `BeginInvoke`, which needs the window's handle, so the handle is made
  there; the watch is seeded with nothing (what the scratchpad holds at load is no news) and the client is
  pointed at the captain's CDU. A window already shown, or shown before, is left as it is. So a CDU message is
  spoken before the first Shift+M, and while the window is hidden, until a profile switch disposes it.

## The 757 EFB (Shift+T)

BlueBird's tablet ("BBOS") is drawn and clicked inside the aircraft's WASM, `BBS752.wasm`: no HTML, no
text behind the picture. The app reads its control tree from the module's memory and presses it with the
mouse handlers of the tablet's own canvas. No screenshot, no text recognition, no popped-out display and
no table of measured positions is involved; all of those were earlier approaches and are gone.

### What Shift+T opens

`MainForm.ShowBBS757EfbDialog` asks `Bbs757SimGuard.Check` on every press and opens the window
`Bbs757EfbWindowChoice.For` names:

- **The tablet window**, titled "757 EFB", while a simulator process runs (`FlightSimulator2024` or
  `FlightSimulator`) or the process list could not be read (`Bbs757SimState.Unknown`, which the guard
  treats as running). It reads and presses the tablet and never writes BlueBird's files.
- **The settings window**, titled "757 EFB settings", only for `NotRunning`: BlueBird's settings files,
  changed in place ([B757-17]). The 757 is not loaded then, so the tablet has nothing to show.

Why two windows, measured 2026-10-27 (MSFS 2024 1.9.21.0, package 0.1.0, BBS Nest running; tablet taps
through the EFB agent, both settings files read in full after each): BlueBird reads its settings files
once, when the 757 loads. While it is loaded it ignores an edit and writes its own copy back over the
file when its Settings app or a Settings section opens and on every change made on the tablet (each tap
was in the file when read 1.3 s later). A write made with no aircraft loaded takes at the next load:
`loading_speed` 2 and `irs_align_time` 2, written at the main menu, showed as QUICK and 2 MIN on
Settings > Aircraft after the load. An aircraft can stay loaded behind the simulator's main menu, so the
only moment known to be safe is with no simulator process at all.

### The tablet window

**The window** is the shared accessible EFB window, `Forms/FBWA380/FbwEfbForm` (the flyPad's and the
PMDG tablets' shell: a semantic HTML document in a WebView2, with a native list as its fallback), made
by `MainForm.ShowBBS757TabletWindow` over `Bbs757EfbBridge`, an `IMcduBridge`. The window sends three
commands (`get_display_elements`, which F5 also sends, `click_display_element` and `set_element_value`)
and renders what the bridge pushes. Closing it hides it; `DisposeBBS757Forms` disposes the window, then
the bridge, then the Coherent client, on every profile switch and at exit. `Bbs757EfbBridge.SetActive`
follows the window's visibility: hidden, nothing is read, and commands sent before it hid are dropped.

**The read.** While the window shows, the bridge's loop reads the tablet about every 700 ms (`TickMs`)
through `BBS757Definition.ReadEfbModelAsync`, which uses the definition's one module session
(`DisplaySession`, [B757-32]): the build whose layout file carries a `Bbs757EfbMemLayout`
(`MSFSBlindAssist.DisplayLayouts/Bbs757/Bbs757EfbMemLayout.cs`), walked read-only ([WASM-1], [WASM-2]).
The layout record holds every BlueBird-specific address and offset: the EFB object's vtable pointer in
the gauge manager, the path from it to BBOS and BBOS's app map, each control's name, rectangle, visible
byte, children and text, the vtable pointer of each control class, and the fields named below. The
`std::map`, `std::vector` and `std::string` shapes are Emscripten libc++'s and are the reader's own
(`ModuleEfbMemory`: a 12-byte string whose byte +11 carries the long flag, validated 2026-11-06).

- `Bbs757EfbMemory.ReadFrontApps` walks each drawn app's roots and its current page, keeping the
  controls whose own visible byte and whose ancestors' are set. An app is drawn while its front flag is
  set, with two exceptions measured 2026-11-07: the top bar's app (class `overlay`) is always read,
  though its front flag reads 0 on every page, and the dialog app (class `modal`) only while BBOS's
  dialog byte is 1, since an answered question kept its front flag and page for hours.
- `Bbs757EfbModelReader` turns the walk into a `Bbs757EfbScreenModel`: the app and section, the side
  menu, the page's items in reading order (`Bbs757EfbItem`, kinds in `Bbs757EfbKind`), the top bar, the
  notifications, a question over the page, the notification panel's rectangle, the keyboard's keys and
  the keyboard's state.
- With no model, the window shows a status in the page's place (`Bbs757EfbModelRead.Unreadable`): "The
  BlueBird tablet could not be read: {reason}. Is the 757 loaded? Press F5 to try again.", or, for a
  build no layout file matches, "… This copy of MSFS Blind Assist cannot read this version of the 757;
  check for an update." (the session keeps its analysis until a switch away or a simulator change, so
  F5 cannot cure that one). While SimConnect is not connected the session is not asked at all. The
  display readers' once-per-session line (`Bbs757DisplayFilesNotice`) is not used here.

Measured on the BlueBird build of 2026-10-31 (`BBS752.wasm`, 29,765,919 bytes), read-only memory reads
with the app closed, a tap only where one is named:

- **Memory holds the whole page**, on and off screen, and a control's rectangle never moves when its
  page scrolls. A scrollbox keeps its scroll as a content offset, which the reader subtracts
  ([B757-26]; 2026-11-06 and 2026-11-07, proven by taps that landed exactly).
- **The selected state** (2026-11-07, read before and after taps on three side menus and three tab
  rows): the current side-menu entry or tab is the button whose selectable byte is 1 and whose
  unselected byte is 0 (`ButtonSelectable`, `ButtonUnselected`). The section a page names and a tab
  row's current tab come from this and from nothing else: none marked, or two (a torn read), names
  none ([B757-22]). An earlier rule that picked the side-menu band whose color stands out is gone with
  the picture reader. The Checklist's RESET ALL sits in the side column and reads selected; it is never
  the current entry.
- **Text boxes, multi-line boxes and drop-downs** (2026-11-07): a text box's text is its text label's
  (`TextboxLabel`); a multi-line box holds its whole text with `\n` between lines (`MultilineText`; the
  Operating FP measured 91,869 characters, so that one string is read up to `LongTextCap`, 1 MiB, every
  other up to 4,096); a drop-down has a face, a list and an entries vector (`PulldownFace`,
  `PulldownList`, `PulldownEntries`, `PulldownOpen`) and no index: its current entry is the one whose
  text is its face's. These give the window the Operating FP, Weather & NOTAM's report and the ACARS
  route as long texts, PERF calc's boxes as fields and its runway, flap and surface lists as choice
  lists, and the Charts page's request box, source and type rows. BlueBird's list box class has no
  instance on any page reached, so none is read.
- **The top bar** is the window's "Status bar": the top bar app's visible labels (the time line), then
  two things the app draws from its own fields and not as controls. The flight-time text
  (`OverlayFlightTimeText`, "DEP 00:28") reads as written. The boarding box shows while its rectangle
  (`OverlayBoardingRect`) has a width, and its words are chosen as BlueBird's draw chooses them, decoded
  from the module's code on 2026-11-07 and read live the same day (`Bbs757EfbTopBar.BoardingWords` over
  BBOS's loading state, deboarding and flown bytes and remaining times): "START BOARDING" or "START
  DEBOARDING" as a button, "BOARDING... N MIN", "BOARDING PAUSED" and the deboarding words as text. The
  paused and done states were read from the code only.
- **Notifications** are BBOS's own records (`BbosNotices`: id, title, text, time), listed newest first
  under "Notifications" (`Bbs757EfbNotices.From`). The pop-up and the open list are drawn by the top bar
  app over the top right of the page, not as controls, so the controls under them still read; the
  panel's rectangle is read for the presses (`OverlayPanelShown`, `OverlayPanelRect`; about
  [1039.75,38 349.25x118] under a pop-up, 480 tall with the list open).
- **The keyboard** (`kb_grid`) reads visible on every page whether it shows or not (2026-11-06), so its
  keys are only places to tap and never elements of the window. Whether it is up is the keyboard app's
  own bytes ([B757-23], below).

**From a tree to elements.** `Bbs757EfbElements.Build` turns a model into the window's `items.N.*`
keys. The order the pilot meets: the alert; a question's words, its text boxes and its answers; the
page; the app's extras; "Status bar" with the top bar and "Notifications"; "Sections" with the side
menu; and Home last. Names are sentence case (`Bbs757EfbVocabulary.Pretty`, which keeps GPU, ACARS, OFP
and the like spelled); values and long texts are as BlueBird writes them.

- **Naming** comes only from BlueBird's structure ([B757-22]): the parts of the control names, a row's
  label, the one label touching a control whose own words are a state or an action ("Left FWD: Open"),
  and `Bbs757EfbPageRules` where a page draws no name of its own (which apps have sections, the names
  that make a tab row, the pictures that show a state such as the chocks tile's, row grids, reading
  orders). A wrong name would send a press to another control, so a page that reads wrongly is fixed
  with a table entry, never a guess from capitals or widths.
- **What each kind becomes:** a button, tile or tab a button (a current tab ends "(current)", the
  current side-menu entry "(current page)"); a switch or checklist line a check box; a slider with
  catalog choices a choice list, any other a 0 to 100 slider from its knob (`SliderKnob`); a drop-down a
  choice list of its entries; a text box whose caret was read an edit box that sends its text on Enter
  alone; a value box (BlueBird's word-less button holding a number, such as the left tank's quantity) a
  button whose tap opens BlueBird's input dialog; a multi-line box preformatted text.
- **Two-choice settings** (nosewheel steering, CPDLC network, units, EHSI up reference) are choice lists
  of their two words when the word was read (`ShowsAsChoiceList`); else a check box.
- **Under a question** the tablet dims its page and takes no tap on it, so the page's controls are text
  until it is answered; the answers and the top bar still press.
- **The EFB colors theme** is never a control ([B757-21], the owner's decisions of 2026-10-30): its row
  is the note "EFB colors theme: Dark blue. Non-default color schemes are not supported."
  (`ThemeNoteFor`). The measurement behind it (2026-10-30: under Light blue the reader of that time,
  which read the tablet's picture, found no control on Settings, General) predates the memory reader
  and has not been repeated with it; the rule stands until the owner lifts it.
- **Home** is the one tap at a point measured once, `Bbs757EfbScreen.HomeButton` (19,62): the reader
  offers no control for the home icon.

**Pushes.** A read is pushed only when its fingerprint changed (`Bbs757EfbPress.Fingerprint`), so a
still tablet costs one memory read per tick. `Bbs757EfbPushes` numbers each element by the page it is on
and its identity there, keeps the number while the element stays, and keeps the last 32 pushes: a press
names an element by number, and is resolved against the newest push that has it, with the page that
push showed. A number no kept push gave out taps nothing.

**What a read says by itself** (`Bbs757EfbReadNews`, as the window's alert): a question that was not in
the read before, and BlueBird's notifications whose ids are newer than every id of the last whole read
(`Bbs757EfbNotices.ToSpeak`), oldest first. Nothing is said of notifications for
`QuietAfterPressMs` (4 s) after the pilot's own tap, whose outcome says enough. The first read of each
showing takes the list as it is (the backlog is listed, not spoken); a torn list says nothing and is
not compared against.

### Pressing

Nothing refuses a press (the owner's decision of 2026-10-29, [B757-19]): REMOVE ALL, the cockpit
presets, SAVE and LOAD, and the AIRAC page's UPDATE and REMOVE are tapped as a sighted pilot taps them.
The decision followed a measurement of that day: 176 taps at the places the reader gave, 159 landed on
the named control, 17 did nothing (each explained) and none changed anything else. What may stop a tap
is only a precision check: where the control is now, and whether its tap is still wanted.

**The tap itself.** `CoherentBbs757EfbClient` (one client on the Coherent view whose title holds
`BBSNavigraphMap`, resolved by title on every connect) installs `Resources/coherent-bbs757-efb-agent.js`
there (`window.__MSFSBA_BBS757EFB`, version 11; an older agent is replaced). Measured 2026-10-25 through
the Coherent debugger: the tablet is the gauge `efb_l`, drawn into a `<wasm-sim-canvas>` whose own four
handlers (`onMouseMove`, `OnMouseDown`, `OnMouseUp`, `onClick`) forward the mouse to the WASM; calling
them with the canvas origin plus a tablet-local point clicks the tablet exactly as the mouse does, with
no camera move and no real mouse. Memory coordinates are that same 1397-wide space, so a rectangle read
from memory is a click point as it is.

- `clickSeq` runs `[[x, y, delayAfterMs], …]` in the page, one run at a time (at most 40 steps);
  `status` and `cancel` follow a run. The agent judges no click by its place. It refuses only what it
  cannot run: a canvas that is not 1397 wide and 1048 to 1070 high, a bad sequence, a run still going.
- `drag` scrolls: this build does not scroll on the wheel (2026-11-06: nine wheel calls changed no byte
  of the scrollbox). It eases out to a stop, or the page flings on ([B757-25]).
- `readVars` reads L:vars in the page (`SimVar.GetSimVarValue`), costing no SimConnect definition.
- The agent's `mirror` and the client's `SetMirrorAsync` are leftovers of the popped-out display and
  have no caller.
- While the window is hidden the client sends nothing; shown, it pings every 3 s, and a ping or a run's
  start that goes unanswered drops the socket at once (a half-open socket after a flight reload).

**The pipeline** ([B757-18]). Commands run one at a time on the bridge's loop through
`Bbs757EfbPressRunner`, with the pure decisions in `Bbs757EfbPress`:

1. A fresh read, then `Relocate` finds the pressed control in it, starting from the page the press was
   made on: by key, else by overlap and words (a tile whose words changed in place). Gone, or turned
   into text: "{name} is no longer on the tablet."
2. `TapPoint` clips the control to the scrollbox it sits in. With under 6 px showing, `DragFor` drags
   the page (at most `MaxScrollSteps`, 8), each drag followed by a read; never in view: "{name} could
   not be brought into view, not pressed."
3. Precision stops, each said once: "{name} is under a BlueBird notification, not pressed." (the pop-up
   stays about 10 s), "{name} is under the open {list} list, not pressed.", and a press point under
   BlueBird's keyboard, which is put down first and stops the press only if it stays up ("{name} is
   under the tablet's keyboard, not pressed."). A question that came up meanwhile holds back every page
   press silently. No link: "The tablet cannot be reached, so nothing was tapped."
4. The tap, the press's hook (below), then reads until the page changes (`PageUnchanged`, which ignores
   the top bar and the notices; at most `ChangeMaxMs`, 3 s: a read 700 ms after a tap caught the old
   page on 4 of 5 app taps, measured 2026-10-27).

**What a press says** (CORE-7: the screen reader read the control; the app says only the result, once,
as the window's alert):

- A navigation (Home, a side-menu entry, a home-screen app) is read until the page is the one asked for
  (`NavigateMaxMs`, 4 s) and says nothing when it arrives. "The tablet did not show {page}. Try again,
  or press F5 to read the tablet again." is said only when the read names another app or section; a
  section that was not read says nothing. An entry whose page shows already taps nothing.
- A tab that became current: "{name} (current)". Any other button: its new words when it has other
  words now ("Req fuel truck" becoming "Requesting…"), or "{name}: no change on the tablet."
- A switch or check box is tapped only when it does not show the wish (`NeedsTap`). A row of a Settings
  page that is a known setting is judged by BlueBird's file ([B757-20]):
  `Bbs757EfbSettingsMatch.SettingFor` matches it to the `Bbs757EfbSettings` catalog by page and label,
  and the file is read for up to `FileMaxMs` (2 s). A row that matches nothing is judged by the page
  (`FollowMaxMs`, 4 s), never by the nearest label's key. Failure: "{label} did not change." Success is
  silent, except a two-word switch shown as a check box, which says its new word once, and a callout
  the press switched off with it ("{label} turned off").
- A slider with choices takes the catalog's choices in the catalog's order, taps, reads back and steps
  toward the choice (at most `MaxSliderTaps`, 4), since the places are not evenly spread (EFB
  background, measured); else "{label} could not be set to {value}."
- **Drop-downs** ([B757-27], `ChooseAsync`): the face is tapped unless the list is open, then the
  entry's row where the list shows it. An open list scrolls by no input (measured 2026-11-07 on PERF
  calc's Surface list), so a row it does not show is "{name} could not be set to {entry}: the tablet's
  list does not show it." A choice that took says nothing.
- **The set settle** ([B757-28]): in WebView2 a closed choice list sends a set on every arrow key, and
  each set is a whole press on the tablet. `Bbs757EfbCommandQueue` holds a set for `SetSettleMs`
  (300 ms) and lets a newer set for the same element replace it; any other command is a barrier, so a
  set never moves past a click made after it.
- **Ground service and GPU tiles** open the definition's echo for their row before the tap and close it
  with the state read after it (below).

**Typing** ([B757-29], `TypeAsync` with the pure planner `Bbs757EfbTyping`). An edit box sends the
pilot's text on Enter alone; leaving it with unsent text says "{name} not changed" (the shared window's
words). Measured 2026-11-07 at a gate, taps on PERF calc's Airport box, the Charts request box and the
fuel and weight dialogs, each change put back:

- The keyboard app keeps a shown byte, a ready byte, a keypad byte, the text box it types into and its
  layer bytes (`KeyboardShown`, `KeyboardReady`, `KeyboardKeypad`, `KeyboardTarget`, `KeyboardNumeric`,
  `KeyboardShift`, `KeyboardCaps`). Ready comes 1.12 to 1.16 s after the box's tap; a key tapped 100,
  300 or 700 ms after it landed on the page beneath and the keyboard slid away. So no key is tapped
  until a fresh read shows the keyboard shown, ready and typing into that box (at most
  `KeyboardReadyMaxMs`, 5 s; else "{name}: the tablet's keyboard did not come up.").
- A text box keeps its caret, its maximum length and whether it opens the numeric keypad
  (`TextboxCaret`, `TextboxMaxLength`, `TextboxKeypad`). A tap puts the caret at the nearest character
  boundary; backspace deletes before it and `btn_delete` after it. The plan clears exactly: caret
  backspaces, then length minus caret deletes, then the text from the layer the state shows. Maximum
  lengths measured: Airport 4, runway length 5, Charts 4, the fuel dialog 8, Hoppie 24, SayIntentions
  64; a full box drops the key.
- The numeric keypad has no controls in any tree: its keys are placed from its rectangle (`KeypadRect`;
  key centers at x0 + 60 + 120 × column and y0 + 87.5 + 75 × row, rows `7 8 9`, `4 5 6`, `1 2 3`,
  `- 0 .`, `BKSP DEL OK`).
- Taps need no pacing: runs of ten keyboard taps at 300, 200, 150, 100, 50, 20 and 0 ms were all exact.
  `TapGapMs` is 100, in agent runs of at most 40 taps.
- A character on no key stops the typing before any tap: "{name}: the tablet's keyboard has no
  {character}." The keyboard is put down with `btn_keyboard_down`, which keeps the text on every box
  measured (`btn_enter` committed nothing that showed on the Airport box); a keypad box ends with the
  keypad's OK.
- The box is read back and said once: "{name}: {value}" when it holds the text, case aside; "{name}
  reads {value}." otherwise (boxes filter: Airport takes letters only and upper-cases them, the fuel
  dialog digits only); "{name} is empty."; "{name} not typed." when a run did not go out. Neither the
  text nor anything that gives away its length is logged.
- A switch's own byte (`ToggleOn`) was found the same day: the only word that changed when TOD pause
  was switched, matching all 16 switches of Settings > Aircraft. The reader takes it as the switch's
  state before the row's value label.

### What the app adds around a press

`Bbs757EfbExtras.HookFor` names the presses the app also acts on, by page and the control's own words.
Each only listens or reads: the tap was the pilot's and went out first.

**The load watch** (`BBS757Definition.LoadWatch.cs`, judged by `Bbs757LoadWatch`, targets from
`Bbs757Loadsheet`). BlueBird fuels and boards at its own pace with only a picture to show it.

- **When it starts** (`PartsFor`): IMPORT FROM SIMBRIEF on the Fuel page watches the fueling; the top
  bar's START BOARDING the boarding; FETCH or REFRESH SIMBRIEF OFP on the ACARS dashboard both, but
  only when BlueBird's `automatic_loading` reads true in its settings file. A press made while a watch
  runs adds its part to that watch, judged from its own start.
- **The plan.** `MainForm.StartBbs757TabletLoadWatchAsync` fetches the latest OFP for BlueBird's stored
  `simbrief_id` (`SimBriefService.FetchLatestOfpXmlAsync`, off the UI thread), `ParsePlan` reads it
  (`fuel/plan_ramp`, `weights/pax_count_actual` else `pax_count`, `pax_weight`, `payload` else
  passengers × weight + `cargo`, `params/units`, `aircraft/icaocode`; kilograms converted as read) and
  `Compute` gives the targets. No ID, no plan, a plan that is not a `B752` or one that does not fit:
  "The SimBrief plan could not be read, so the app won't say when fueling and boarding are complete.",
  once, and nothing is watched. The ID is never logged or spoken.
- **The targets** are how BlueBird spreads a plan, measured 2026-10-25 by loading SimBrief plans through
  BlueBird's own EFB and reading the tanks and stations: the block over both wings up to 2 × 14,579 lb
  (2,176 gal each), the right wing `floor(block / 2)` and the left the rest, the center the remainder
  (refused past 46,390 lb); passengers `min(pax, 176)` × the plan's passenger weight (a plan of 224
  boarded 176: 30,800 lb at 175 lb); cargo the payload less that, the forward hold first up to
  10,300 lb and the aft the rest (20,659 lb went 10,300 / 10,359; 3,990 lb all forward; refused past
  25,000 lb).
- **Each read**, every 15 s: `FUEL TANK LEFT MAIN/RIGHT MAIN/CENTER QUANTITY` (gallons) ×
  `FUEL WEIGHT PER GALLON`, and `PAYLOAD STATION WEIGHT:3` and `:4` (cabin), `:5` and `:6` (holds), all
  eight OnRequest with no Ctrl+M row. The first read only seeds; a group with a value unread is skipped.
- **"Fueling complete."** with the fuel, once: the total within the larger of 1% and 100 lb of the
  block (BlueBird converts at about 6.72 lb/gal and the simulator reports 6.70: a 16,400 lb plan read
  16,346) and every tank moved under 20 lb since the last read (the APU burns fuel, so the tanks never
  read unchanged).
- **"Boarding complete."** with the passengers and the cargo, once: the cabin and the holds' total each
  within the larger of 0.5% and 20 lb and moved under 1 lb since the last read; the split between the
  holds is not judged. A plan with more passengers than seats adds that they were capped. Nothing is
  said about the ACARS weight and balance: the aircraft requests it by itself (the owner's decision of
  2026-10-30).
- **Three minutes** after a part's start, a part whose tanks (by 100 lb) or stations (by 1 lb) have not
  moved since its first read is given up: "BlueBird has not started loading. Is BBS Nest running? Check
  the fuel with F and the weight with W." for both, or "BlueBird has not started fueling. Check the
  fuel with F." / "BlueBird has not started boarding. Check the weight with W." Fueling took about two
  minutes and a REALISTIC boarding of 114 passengers under 40 minutes (2026-10-25), and both start at
  once.
- **After an hour** it says what has not finished ("Boarding has not finished after an hour. Check the
  weight with W.") and stops. A flight load, a lost connection or a profile switch ends it silently.
- Weights are spoken rounded to 10, each total the sum of its spoken parts, in the aircraft's units
  read from BlueBird's file when each sentence is said, never once per watch: a fetch's units question
  can switch them after the watch began (seen 2026-10-30). debug.log gets numbers only
  (`Bbs757Loadsheet.LogLine`).

**The nav data watch** (`Bbs757EfbExtras.WatchNavDataAsync`). The AIRAC page's UPDATE and REMOVE share
one spot, and BlueBird chooses which to show from a check it runs inside the WASM when the flight
loads. The bridge reads the installed cycle (`NavigationData\cycle.json`) right before the tap; after
it the file is read every second for 20 s. UPDATE: "Nav data cycle {n} installed. Reload the flight to
use it." (measured 2026-10-25: after an update and before the reload the APU shut down and would not
restart), "BlueBird removed the installed nav data instead of updating it. With an active Navigraph
subscription, reload the flight and update again." or "The update did not finish. Try again after
reloading the flight." REMOVE: "BlueBird removed the installed nav data." or "BlueBird did not remove
the nav data."

**The Navigraph sign-in** (`Bbs757NavigraphSignIn`). While the pilot is known to be signed out, the
bridge adds a "Sign in to Navigraph" button to the AIRAC page. BlueBird shows a device sign-in; its
code and address are read from the hidden `BBSTablet` helper view (`CoherentBbs757TabletClient`), never
from the tablet. The line "Navigraph code: {code}" goes on the page first, then the code is spoken
letter by letter ("Navigraph code A B 1 2. The sign-in page opens in your browser in a moment."), and
the browser opens 2 to 6 s later (`CodeSpeechMs`), because opening it moves focus and would cut the
code off. Only an https address on `navigraph.com` or `identity.api.navigraph.com` is opened. The code
and its address are never logged.

**Ground power and ground services** (`BBS757Definition.Efb.cs`, `Bbs757GroundPower`,
`Bbs757GroundServices`). These rows speak whoever caused the change:

- `L:BBS_757_GPU_AC_PWR_CONNECTED` (0 or 1; the Ground Services page's GPU tile toggles it, measured
  2026-10-25 and 2026-10-26) is the "Ground Power" row on the Overhead's Electrical panel status
  display, "Connected" / "Not connected", spoken as "Ground power connected" / "Ground power
  disconnected". Connecting only makes it available: EXT PWR on that panel puts it on line.
- Four tiles have announced rows on their `BBS757_vis_*` variables, the ones a reversible tap in the
  simulator showed to follow the tile: `stairsaft` ("Aft stairs attached" / "removed"), `fueltruck`,
  `catertruck` and `baggage1` ("Fuel truck called" / "removed", and so for Catering and Cargo service).
  The variable names come from an offline survey of the module's strings and the cockpit XML. The
  forward stairs and ground air conditioning have no row; the chocks' `BBS757_vis_chocks` is already
  the control map's Status row, and a second key on one L:var would break the batch ([VAR-7]).
- All ride the 1 Hz batch through `Bbs757ChangeTracker`: a first reading is a silent baseline, and
  MainForm's mute wrap gates them ([VAR-8]).
- **The echo.** A tap on one of these tiles from the tablet window arms the row's echo first
  (`ArmServiceEcho`, `ArmGroundPowerEcho`; at most 60 s) and settles it with the state read after the
  press, so the change is said once, by the press. The GPU's echo covers the EXT PWR AVAIL row too: the
  tap changes that light about 0.17 s later.

### The settings window

`Forms/BBS757/BBS757EfbForm.cs` and `.Settings.cs`: a status box (a read-only `TextBox`, VAT-13), a
Section list (General, Aircraft, AIRAC data, ACARS, Failures, Livery options, Callouts, Cabin audio)
and the chosen section's rows, built by `Bbs757SettingsRows` from the `Bbs757EfbSettings` catalog. It
needs no simulator, no Coherent client and no SimConnect.

- **The files** are `efb_settings.json` and one `liveries\<registration>-opt.json` per registration
  flown, in BlueBird's `work` folder; `Bbs757WorkFolder.Find` picks the candidate whose settings file
  was written last, among the MSFS 2024 and 2020 locations. A registration setting is saved in every
  registration's file.
- **The catalog** lists only what the tablet shows and the value BlueBird stores for each word, each
  measured by changing the setting on the tablet and reading both files (2026-10-27).
- **A write** ([B757-17]) goes through `Bbs757SettingsSave.Run` and `Bbs757SettingsFile.Save`: only
  while `Bbs757SimGuard.SettingsWritable` holds, asked again just before the read and the write; one
  value's bytes replaced, verified, moved over the file atomically; a file is never created; a safety
  copy is made before the window's first write to each file. The tablet's own three side effects are
  repeated (units write two keys; an exclusive callout switches its group's others off; the
  announcement categories wait for Announcements).
- **Read-only state.** The guard is asked when the window opens and every second while it shows. With a
  simulator running every input stays focusable and readable but does not change, and an attempt says
  why at once ("Close the simulator to change BlueBird's settings."). `Bbs757LockableComboBox` and
  `Bbs757LockableSlider` hold a control at its value without taking it out of the tab order, which a
  disabled control would leave; a held key's repeats are one attempt. A simulator starting or closing
  while the window shows is said once.
- **Speech** (CORE-7): a check box, choice list or slider that saved says nothing; a number or text box
  says "{label} saved"; every failure speaks ("Couldn't save {label}: {reason}").
- **The EFB colors theme** is a read-only note here too, with one "Set to Dark blue" button while the
  file holds another theme ([B757-21]).
- **Credentials.** The files hold the pilot's SimBrief ID, Hoppie logon code and SayIntentions ACARS
  key. Both windows show them in plain text; no log line carries them.

## Displays read from memory

The FMA, the upper EICAS (Alt+E), the lower EICAS (Alt+S) and the Captain's EHSI (Alt+N; Ctrl+W says the
active waypoint) are read from `BBS752.wasm`'s memory in the running simulator, read-only ([WASM-1]). BlueBird
draws these screens inside its WASM module with no text behind them, so the only other way to read them is AI
vision on a camera capture ([AI display reads](#ai-display-reads)), which is slow and only on demand. The
groundwork (the layout file, the layout store, the module session, the safety model) is the PMDG 737's and is
described in [wasm-memory.md](wasm-memory.md); this section is what the 757 adds.

**No address in the app.** Every address, field offset, vtable pointer and word table comes from a layout file
written for the installed `BBS752.wasm` ([WASM-2]): the records in `MSFSBlindAssist.DisplayLayouts/Bbs757/`
(`Bbs757FmaLayout`, `Bbs757UpperEicasLayout`, `Bbs757LowerEicasLayout`, `Bbs757EhsiLayout` and, for the tablet
window, `Bbs757EfbMemLayout`), listed by `Bbs757Module.Description` (module id `bbs757`) and loaded by
`LayoutStore` from `layouts\bbs757\` beside the exe or under `%APPDATA%\MSFSBlindAssist\`. This build of the
module has no name section, so every reader finds its object the same way: the gauge manager's static address
(`ManagerBase`, `ManagerSpan` bytes of pointers) is searched for the pointer whose target starts with the
display class's vtable pointer, and everything else hangs off that object. Every read is bounds-checked against
the module's committed memory ([WASM-4]).

**One session, owned by the definition** ([B757-32]). `BBS757Definition.DisplaySession`
(`BBS757Definition.Displays.cs`) is the one `ModuleSession` for `BBS752.wasm`: one load of the layouts and one
memory search for every reader, the tablet window's EFB read included (`ReadEfbModelAsync`, called from
`MainForm.BBS757.cs`). A reader never opens the simulator, reads the file or runs the generator itself.
`MainForm.StartBbs757Displays` makes the `ModuleHost` and the `LayoutStore` and calls `StartDisplays` at startup,
after a switch to the 757 and when a flight loads in the other simulator
(`RestartBbs757DisplaysIfSimulatorChanged`); `ResetDisplays` (from `OnSimContextReset`: a flight reload or a
dropped connection) invalidates the session and restarts every monitor; `StopDisplays` (from `OnSwitchedAway`)
closes the readers' windows for good, stops the monitors and disposes the session, and the readers never start
again on that definition instance.

**The registry.** `Bbs757DisplayRegistry` (`BBS757Definition.Displays`, built on first use) holds every reader's
monitor, its Ctrl+M rows, its hotkeys, its simulator inputs and the windows it owns. The FMA registers itself;
each later reader registers through a partial method of its own (`RegisterUpperEicas`, `RegisterLowerEicas`,
`RegisterEhsi`; `RegisterAdi` has no implementation, as no ADI reader was built). `HandleHotkeyAction` offers a
key to the registry before anything else (`HandleDisplayKey`), and `MonitorRows` lists the readers' rows last. Two
readers on one key, or one input key naming two variables, throw at registration.

**The shared monitor.** `Bbs757DisplayMonitor<TLayout, TReading>` is the PMDG 737 FMA monitor's state machine made
generic over an `IBbs757DisplayReader<TLayout, TReading>`, which supplies only what differs per display: its
name, Ctrl+M key, log channel and tick, its layouts and samplers (`LayoutsIn`, `SamplerFor`), its simulator inputs,
its power state (`Lit`), its spoken lines (`Changes`) and its window rows (`Rows`). The monitor ticks on a WinForms
timer on the UI thread (FMA 100 ms, both EICAS screens 250 ms, EHSI 500 ms) and polls the session's two
background jobs, never waiting on them:

- **Waiting for the simulator**, silently, while `Bbs757DisplayEnvironment.ReadSimulator` returns null: SimConnect
  disconnected, no flight running, a loaded title without "757" (`TitleMark`), or a reader input with no cached
  value yet. The connection is checked first, since a closed simulator leaves the last title and values in place.
- **Analyzing and locating.** The session loads the layouts and searches for the module's memory. Attempts are at
  least 5 s apart inside a 120 s window; when the window runs out the reason is spoken once and the search goes on
  every 30 s, silently. Memory not found is never final.
- **Verifying.** Each candidate (a sampler per layout per located build, on its own lease of the shared handle) has
  2 s to give one reading that is not `Corrupt`; the first that does runs, the others are disposed.
- **Running.** A failed read (the memory moved or went away) starts a new search, silently at first; not found
  again within 10 s, the pilot hears "stopped".

**How a reading is trusted** ([B757-30]). On structure alone: the layout derived for this exact file, the object
found by its vtable pointer with every read inside the module, and the reading not `Corrupt` (a torn list or
vector, a pointer outside the module, a value that is not a number or far out of range). No reader compares
memory with a simulator value. The first three readers shipped with such a comparison (the FMA against the F/D
switches and the MCP altitude and heading, the upper EICAS against N1, the lower EICAS against N2 and the page
variable), and on the owner's flight of 2026-11-10 the lower EICAS's N2 comparison failed at both engine starts,
so he heard "stopped" twice while the display was right: N2 spools faster than SimConnect's value follows (an
earlier level-change spool-down had already tripped it: N2 fell 76.2 to 64.4 % in 8 s by the app's log). The
owner removed every comparison on 2026-11-11; do not add one back. A simulator variable is still an INPUT where
BlueBird's own draw takes one (`Bbs757SimInput`, declared by the reader in `SimInputs`). The definition gives each
input no batched variable already carries a hidden copy, `BBS757_DISPLAY_INPUT_<key>` (`AddDisplayVariables`:
Continuous, no Ctrl+M row, off the batch when another batched variable has its name, [VAR-7]), and the
environment reads it from SimConnect's cache (`DisplayCacheKeys`).

**What is spoken, and when.**
- **`Lit` and the 10 s.** A reader with a power state (`Lit` true or false: both EICAS screens and the EHSI;
  the FMA returns null always) says nothing while the display is dark or for 10 s after it powers up
  (`LitQuietMs`), so power-up is never read out; the window shows "<name> display not powered" or
  "<name> reader starting" meanwhile.
- **The silent baseline.** The first good reading after a start, a flight reload, a wait for the simulator, or
  the dark or powering-up state is the baseline and is never spoken as a change.
- **The settle.** A difference from what was last spoken is said once it has stood for 300 ms (`SettleMs`), as it
  is then; a change and back inside the window says nothing. The window is not restarted by later changes.
- **`Corrupt`.** A corrupt reading is never shown, spoken or kept as a baseline. Ten in a row
  (`CorruptTickLimit`) stop the reader, "<name> announcements stopped: unexpected values", until a flight reload.
- **Status lines** (`Bbs757DisplaySpeech`, with the reader's name: "FMA", "EICAS", "Lower EICAS", "EHSI"):
  "<name> announcements unavailable: <reason>", "<name> announcements stopped: <reason>" (once the reader has run
  in this session) and "<name> announcements resumed", which carries whatever changed meanwhile. A stop line is
  said once per reason; one heard before a flight reload is answered by "resumed" on the new flight's first
  reading. The reasons are `Bbs757DisplayReasons`: "BlueBird file not recognised", "BlueBird 757 files not found",
  "aircraft memory not found", "no access to the simulator", "unexpected values", "internal error, see the log";
  `FromSession` rewords the session's own reasons, which are worded for the PMDG 737.
- **No layout file.** When the analysis loaded no layout file at all, no reader says a line of its own:
  `Bbs757DisplayFilesNotice` says "BlueBird display files could not be loaded; the display keys fall back to AI
  reading." once per module session, through the first reader whose row is not muted. A file that loaded without
  one reader's layout gives that reader's own "unavailable: BlueBird file not recognised".
- **The speech path** ([B757-31]). Everything a reader says by itself goes through
  `Bbs757DisplayEnvironment.Speak`, the announcer's non-interrupting `Announce`, gated by the line's Ctrl+M row
  (`BBS757DisabledMonitorVariablesSet`; the monitor speaks from its own timer, so it checks the mute itself). A
  mute silences speech, never a window. No reader suppresses, delays or rewords the MCP-light lines, the cockpit
  light and annunciator lines or BlueBird's own callouts: a sighted crew sees both instruments.

**The window.** `Forms/BBS757/BBS757DisplayForm.cs` is the one window the readers open: a named `DisplayListBox`
of the monitor's `View()` (the reader's rows while it runs, else one status row), refreshed every second and
rewritten only when the rows differ, so the screen reader's cursor stays put; then an optional controls area in
the tab order. Escape hides it and returns to the previous window; only the switch away (`CloseForGood`) ends it.
A display key opens the window while the reader runs, starts or waits, and goes to the AI read only when the
reader cannot work (`KeyFallsBackToAi`, see [AI display reads](#ai-display-reads)).

**Logs.** `bbs757-module.log` (the layout store, each file's layouts, the memory search) and one per reader:
`bbs757-fma.log`, `bbs757-upper-eicas.log`, `bbs757-lower-eicas.log`, `bbs757-ehsi.log` (state changes with
their reasons, a value with no word, a corrupt reading's cause).

### FMA

`Bbs757FmaReader` (the sampler), `Bbs757FmaDisplay` (the reader) and `Bbs757FmaSpeech` (the words, pure). The
sampler finds the Captain's primary flight display object, follows it to the autoflight and thrust objects and
from the autoflight object to the MCP, and reads the autothrottle mode, pitch, pitch armed, roll, roll armed and
status values, the two F/D switch bytes, and the MCP's selected altitude and heading. The words are BlueBird's
own, from the layout's `Bbs757WordTable`s: 0 is blank, a value with no word reads "unrecognised" (logged once per
column and value, never dropped).

- **BlueBird's draw rules** (`Bbs757FmaReader.Decode`). The AFDS column shows the status value's word when it has
  one ("CMD"), else the layout's F/D word ("FD") while the Captain's F/D is on, else nothing. The pitch and roll
  strip, armed modes included, is drawn only while the Captain's F/D is on or the status has its word; otherwise
  all four read blank whatever memory holds. The A/T column is always drawn.
- **`Corrupt`**: a mode value below 0 or above 255, or an MCP altitude outside 0 to 50,000 ft or heading outside
  0 to 360. The MCP values are range checks of the reading only; nothing compares them with the simulator.
- **Spoken** on the Ctrl+M row "Flight Mode Annunciator" (`MSFSBA_BBS757_FMA`): the changed columns in the order
  A/T, Roll, Roll armed, Pitch, Pitch armed, AFDS, in one line after "FMA: ": "FMA: Roll: LOC, Pitch: G/S". A
  column going blank is "none". An armed mode that clears as the active column takes its value is said once, as
  active; BlueBird keys most armed and active modes alike (LOC, G/S, FLARE), but not VNAV (armed 5, active VNAV PTH
  6 or VNAV SPD 7), so VNAV engaging says both parts: "Pitch: VNAV PTH, Pitch armed: none". The wording is the PMDG
  737 FMA's, word for word.
- **The FMA has no power state**, so it has no dark state and no 10 s quiet: with the F/D off and no autopilot
  the strip simply reads blank.
- **Listed** at the top of the autopilot window (Ctrl+P), in a list before the buttons, fed by `Fma.View`:
  "A/T: SPD", "Roll: LNAV, armed LOC", "Pitch: VNAV PTH, armed G/S", "AFDS: CMD", or the monitor's one status row
  ("FMA reader starting", "FMA announcements unavailable: …"). The FMA has no key and no window of its own.
- The MCP-light lines ("LNAV on") stay beside it ([B757-31]): never de-duplicate one against the other.

### Upper EICAS (Alt+E)

`Bbs757UpperEicasReader` (the sampler, `Decode` holding BlueBird's draw rules), `Bbs757UpperEicasReading`,
`Bbs757UpperEicasDisplay` (the reader) and `Bbs757UpperEicasSpeech` (rows and lines, pure);
`BBS757Definition.UpperEicas.cs` registers them. The reader's name in the status lines is "EICAS".

- **What is read.** The object's own power, failed, timed-blank and compact bytes, the EGT and N1 limits and
  max-exceedance memories, the in-flight start rows; through its pointers the EICAS computer (page, recall time,
  blank), both engines, the reversers, the fire switches, the thrust management computer, TAT, the FMS's
  on-ground flag, the lower EICAS's mode and the pneumatic components (for the anti-ice valves); and the two
  message lists (the main list and the communication list), which are static vectors of entries with a text, an
  id, a level and a cancelled byte. `Lit` is the screen's own power: powered, not failed, not timed blank, and the
  computer not blanking it.
- **The lists are read all or nothing** ([B757-35]). BlueBird reallocates and shifts these vectors while the
  reader walks them, so each header is read before and after the walk; a torn list makes the reading `Corrupt`
  with both lists empty, never a partial list that would be heard as "EICAS gone" and then the message again.
- **The one simulator input** is `L:BBS757_THRREF_PULL`, BlueBird's manual thrust reference flag, which the draw
  itself reads: above 0.5 the thrust reference shows the layout's manual word (MAN) and the manual reference EPRs.
  It is an input, never a check ([B757-30]).
- **The window** ("Upper EICAS"), rows in this order, each only while BlueBird draws it: "EPR: 1.03, 1.03",
  "N1: 19.9, 19.9", "EGT: 358, 360" (left then right; a blanked value "blank"; a color after its value, "EGT: 800
  amber, 360"); "TAI: L, R" and "REV: L amber" (only the sides drawn; REV amber in transit, green deployed); "N1
  max: …" and "EGT max: …" while a memory is set; "Thrust reference: TO 1" (the word, its number and the derate as
  drawn, or "none"); "EPR reference: …"; "TAT: +11c"; the in-flight start block's lines; then every message in
  screen order as "Warning: …", "Caution: …", "Advisory: …" or "Communication: …" (a cancelled one with
  " (cancelled)"), or "Messages: none"; then "PAGE 2" and the RECALL word while they show. Numbers are formatted
  as the draw formats them (EPR two decimals from the float, N1 one decimal, EGT truncated), invariant.
- **Spoken**, each kind on its own Ctrl+M row:
  - "EICAS messages" (`MSFSBA_BBS757_EICAS_MESSAGES`, which also carries the status lines): new messages, one line
    per level, "EICAS warning: L ENGINE FIRE, R ENGINE FIRE", "EICAS caution: …", "EICAS: …" for advisories and
    communication messages; "EICAS gone: A, B" for messages leaving. A message's text is BlueBird's exactly, its
    leading indent space dropped; a message off the first page counts as the ones on it do.
  - "Thrust reference" (`MSFSBA_BBS757_THRUST_REFERENCE`): "Thrust reference: CLB", "Thrust reference: none".
  - "Engine gauge colors" (`MSFSBA_BBS757_ENGINE_COLORS`): "EICAS: L EGT amber, R EGT amber", back to "normal",
    because a sighted pilot sees the readout change color. No gauge value, TAT, TAI, REV, page or start block is
    ever spoken.
- **CANC and RECALL** ([B757-34]). BlueBird keeps a cancelled message in its list with a mark, and RECALL clears
  every mark and stamps the computer's recall time (measured live 2026-11-09: five advisories cancelled and
  recalled). So "EICAS gone" is said only for an uncancelled message leaving the list, never for one CANC hid.
  CANC is read back once as a count, "EICAS: 3 messages cancelled"; RECALL, detected by the recall time changing,
  once as "EICAS recall: A, B" or "EICAS recall: no cancelled messages", and a recalled message is never also
  said as new.
- **FMC MESSAGE is never announced.** The advisory that says the FMC has a scratchpad message is left out of the
  new and gone lines (`FmcMessageText`): the CDU window's "CDU Messages While Closed" already speaks the FMC's
  message itself (the owner's decision after the flight of 2026-11-10). The window lists it, CANC counts it and
  RECALL reads it back.
- **The buttons** after the list: Cancel (Alt+C), Recall (Alt+R) and Max Ind (Alt+M), which press the control
  map's `B757_MAIN_CANCEL_BUTTON`, `B757_MAIN_RECALL_BUTTON` and `B757_EICAS_MAX-IND_BUTTON` exactly as the panel
  does (`PressFromPanelAsync`: "<label> unavailable" when nothing can land, else "<label> pressed"), followed by
  the reader's own read-back line. A node missing from the map leaves its button out with a warning in the log.
- **Alt+E** opens the window, saying nothing itself (the title and the list are the screen reader's, CORE-7), or
  falls back to the AI read when the reader cannot work.

Checked in the simulator on the PW2000 variant and on the owner's flight of 2026-11-10 (cold and dark to shutdown,
FL390).

### Lower EICAS (Alt+S)

`Bbs757LowerEicasReader` (the sampler), `Bbs757LowerEicasReading`, `Bbs757LowerEicasText` (BlueBird's label words
and number formats, the rows and the lines, pure) and `Bbs757LowerEicasDisplay` (the reader);
`BBS757Definition.LowerEicas.cs` registers them. It takes no simulator input.

- **The page.** The object's page field holds one of the layout's page values, shown by kind (BlueBird prints no
  page title): "engine", "STATUS", "engine off" (the engine page switched off, where the FF dials stay drawn) and
  "blank" for anything else. The display draws while its power byte is set and its two blanking bytes are clear;
  that is `Lit`.
- **Each page is an optional part of the layout** (`Bbs757LowerEicasLayout.Engine`, `.Status`, each null with its
  reason). A page whose part is missing costs only its rows: "engine page: not read: <reason>".
- **The engine page's rows**, left engine first: "N2: 82, 82", "N2 max: …" while a max box is drawn, "N3: …" and
  its max on the RR only, "FF: 3.7, 3.7", "OIL PRESS: 92, 90", "STATUS" (the cue BlueBird draws while the status
  list is not empty), "OIL TEMP: 114, 109", "OIL QTY: 12, 14", "VIB: 1.8, 1.7". Engine page off: the FF row, and
  the N2 (and N3) rows with their max boxes only while the exceedance latch is set.
- **The STATUS page's rows**: "HYD QTY: L 0.98, C 0.97, R 1.00" (with " RF" below 75 % and " OF" above 122 %),
  "HYD PRESS: L 3000, C 2880, R 2950", "APU EGT: …", "RPM: …", "OIL Q: 0.75" (quarters, "FULL" from 0.99),
  "OXY PRESS: 1760" while BlueBird draws it, the four flight control pointers in words, since the screen prints
  no digits for them ("RUD: 25 % right", "AIL left: centered", "ELEV: 10 % up", "AIL right: …"), "FF: …", every
  status message on a row of its own, newest first, and "BRAKE TEMP: 1: 0, 2: 0, …" by wheel 1 to 8.
- **The formats are BlueBird's draw code's**, read from the module on 2026-11-09 (no screen capture was possible
  that day, so the values were checked against a memory snapshot in cruise and then by the owner in the
  simulator): every whole number is truncated toward zero, never rounded (81.99 draws 81), and N2, N3 and their
  max boxes are demoted to a 32-bit float first, so a value within about 4e-6 below a whole number reads that
  number; an invalid engine's cells read "blank"; OIL TEMP between −10 and 0 prints "- 5", and is blank while
  that engine's N2 is under 5; OIL QTY is the stored fraction × 21 in whole quarts; VIB is the absolute value to
  one decimal; FF is thousands to one decimal, in pounds while BlueBird's settings flag is set, else kilograms
  (÷ 2.205). While an engine starts the engine page shows 600 lb/h during the start's hold and then ramps to
  1,200 as the HP spool goes from 25 to 60 %, and the STATUS page shows 600 during the hold and 0 after it. Not
  read: the X-BLD cue, the STATUS page's own page number and the dial colors. The PW's engine page was not
  measured (an RR was loaded).
- **`Corrupt`**: the status list walk is all or nothing (a bad count, pointer, length or character); while the
  display draws, a value that is not a number or beyond ±1e9, or a brake digit above 9. The cause is logged once
  per change on the reader's channel.
- **Spoken**, all on the one Ctrl+M row "EICAS status messages" (`MSFSBA_BBS757_STATUS_MESSAGES`): the page
  change, "Lower EICAS: engine page", "Lower EICAS: STATUS page", "Lower EICAS: engine page off", "Lower EICAS:
  blank"; and the status messages, "Status: A, B" and "Status gone: A, B", only when BOTH the heard and the new
  reading show the STATUS page ([B757-33]). The messages present when STATUS opens are the page's content, which
  the window lists, and one that comes or goes under another page is not news, as BlueBird shows the messages
  only on STATUS. No value is spoken.
- **The window** ("Lower EICAS"): "Page: STATUS" and the page's rows, or the one row "Lower EICAS: blank". After
  the list, the Engine and Status buttons press BlueBird's ENGINE and STATUS display keys (the control map's
  `B757_EICAS_L_STATUS_BUTTON`, labeled "EICAS L Status", and `B757_EICAS_R_STATUS_BUTTON`). While the reader shows
  a reading its own page line is the press's one confirmation; otherwise the press says "<label> pressed", as the
  panel does (CORE-7).
- **Alt+S** opens the window or falls back to the AI read when the reader cannot work.

### EHSI (Alt+N, Ctrl+W)

The Captain's EHSI. `Bbs757EhsiReader` is the sampler, split by mechanism into partials: the core (the screen's
fields, the route, the points), `.Approach` (VOR and ILS, the bearing pointers), `.Tcas`, `.MapOptions`,
`.MapExtras` (TERR, wind, runways, deceleration points, the leg position rule), `.MapGuides` (FIX pages, off-path
circles, the altitude range arc, the VNAV deviation), `.Parts` (what is read in which mode) and `.Tears` (the
per-part tear count and the layout checks). `Bbs757EhsiReading` and its partials are the reading;
`Bbs757EhsiGeometry` is BlueBird's projection, clip, top-line distance and ETA and the place words;
`Bbs757EhsiMapOptionsLoop` replays BlueBird's map-options draw loop; `Bbs757EhsiText` and its partials build the
rows, the spoken lines and the Ctrl+W line; `Bbs757EhsiDisplay` is the reader; `BBS757Definition.Ehsi.cs`
registers it and builds the window's controls. Rules: `.claude/rules/b757-ehsi.md`.

- **Light and full readings.** Every tick reads the light set: the screen's own fields (power, mode, range,
  centered, heading or track and its validity, the flags' inputs) and the active leg. The route, a pending
  modification, the map's points and the parts' lists are read only while the window is opening or showing
  (`Bbs757EhsiDisplay.FullWanted`), so a closed window costs a few reads twice a second. Alt+N ticks the monitor
  once before it shows the window, so the first rows already hold the map; a light reading's map is the one row
  "Map: reading".
- **The route is read all or nothing** ([B757-36]): the flown legs, the legs, a pending modification and the
  points. A torn vector, a leg or label outside the module, a count over the layout's cap or a position out of
  range makes the reading `Corrupt`, never a partial route. A discontinuity is a leg of its own with no row, and
  no leg is ever drawn across it. Three cases look torn and are not: a path registry walk that reaches its cycle
  guard finds no path (no T/C, T/D or E/D), an E/D index past the route's leg count draws no E/D, and a null
  selected-IRS pointer is the dark reading.
- **Listed only where the EHSI draws it** ([B757-37]). Every map item is projected with
  `Bbs757EhsiGeometry.Project` from the map center and rotation the display object itself holds, and listed only
  inside `OnScreen`'s clip: a circle around the aircraft's screen point at 88.7 % of the range in this build, in
  PLAN too, plus the screen's own edges. Measured 2026-11-11: KOLM at 37.5 NM, 86.5° right, is not on the screen
  in MAP at range 40 but is at 160. A plain distance-against-range test would list items a sighted pilot does
  not see. The clip's constants are the layout's and travel in the reading.
- **Two positions, never swapped** ([B757-39]). The top line's distance is computed from `PLANE LATITUDE` and
  `PLANE LONGITUDE`, because BlueBird's top-line draw reads those simulator variables fresh on each call; the map
  rows use the display object's own center, copied each frame from the selected IRS. Parked they agree to the
  sixth decimal; in a turn they can differ.
- **Simulator inputs** (`Bbs757EhsiDisplay.SimInputs`, [B757-44]): only what the draw takes from the simulator with
  no copy in memory, in the draw's own units: the position (degrees), `AMBIENT WIND VELOCITY` (knots) and
  `AMBIENT WIND DIRECTION` (degrees) for the wind, and `GEAR POSITION` (enum) for TERR's amber threshold. An L:var
  the draw reads (the TERR button, the two bearing pointer selectors `L:BBS_DDRMI_LEFT` and `L:BBS_DDRMI_RIGHT`)
  is taken from the value its handle caches in memory, never from SimConnect: it is the very value the draw uses,
  in the same reading. All are inputs, never compared with memory.
- **The rows** (`Bbs757EhsiText.Rows`), top to bottom, in BlueBird's printed words:
  - Dark: "EHSI: dark", alone. Else "EHSI: MAP, range 160" (", centered"; a centered VOR or ILS rose draws no
    range), "Top: HDG 119 M" (TRK with track up, the true reference's word), or while the heading is not valid
    "Top: ---", "Flag: HDG" and in MAP "Flag: MAP".
  - **MAP and PLAN**: "Top left: 37.5 NM" (or "no distance"), "Top right: 1533.3z" (or "no ETA": BlueBird draws
    dashes under its minimum ground speed), then the map's rows by their place on the screen, top to bottom, left
    to right: each route leg with a symbol ("Map: KOLM, active, 37.5 NM, 87° right"; "Map, inactive route: …";
    "Map, modification: …"; with DATA on, its constraint and ETA as drawn, "2300A", "1518Z"), T/C, T/D and E/D,
    the origin and destination ("Map: KSEA airport, …"). In PLAN a place is from the leg at the map's center
    ("13.4 NM north-east of KOLM"). Then "Heading bug: 147, 28° right" and "Message: EXCESS DATA" or "Messages:
    none".
  - **VOR and ILS**: "Top left: DME 12.3" (or the screen's dashes), the ETA when not centered, "Center: course
    pointer 187, 68° right", "Center: deviation 0.5 dots right" ("centered", "at full scale, left", "no deviation
    bar"), in ILS "Right side: glideslope 1.2 dots above" (or "no glideslope pointer"), the G/S and LOC flags in
    place, VOR's "Bottom right: TO" or "FROM", the receiver's label ("Bottom left: VOR L", "ILS") and ILS's
    frequency.
  - **Bearing pointers**, every mode but PLAN while the IRS is valid: "Bearing pointer 1: VOR L, SEA, 74° right";
    an ADF with no position in the layout is named without an angle.
  - **TCAS**: the left block ("Left side: TFC", "TCAS OFF", "TCAS FAIL", "TEST", "TA ONLY"), "Right side:
    TRAFFIC, amber" (red for an RA), and in MAP each symbol among the map's items, "Map: proximate traffic, 8.7
    NM, 38° left, +10 climbing" (other and proximate traffic only while TFC is on; the self-test's four symbols as
    "Map: TCAS test pattern").
  - **Map options** (NAV AID, APRT, WPT): the tuned stations ("Map: VORTAC SEA, tuned, …") and the items
    BlueBird's loop draws ("Map: VOR/DME PAE, …", "Map: airport KBFI, …", "Map: waypoint HAVHO, …", "Map: NDB FHR,
    …"; the kind words are the app's names for the symbols), then the VOR course lines ("Map: VOR L course 187
    through SEA").
  - **TERR**: "Top right: TERR", "Top right: terrain 031 red, 004 amber" (the highest and lowest elevations as
    drawn) and, where the terrain picture is drawn, "Map: terrain shown, not read". The picture itself cannot be
    listed.
  - **Wind**, in MAP, VOR and ILS: "Bottom left: wind 70 kt from 30° left", or the screen's dashes.
  - **Runways and deceleration points**: "Map: runway 16L, 2.0 NM, 15° left" (by its nearer end), "Map:
    deceleration starts, …", "Map: deceleration ends, …".
  - **FIX guides**: "Map: fix TCM, 19.1 NM, 160° left", "Map: fix TCM, circle 15 NM", "Map: fix TCM, radial 300",
    each while some of it is inside the clip; "Map: off-path descent circles, 45 NM and 38 NM around …"; in MAP
    "Map: altitude range arc, 12.3 NM, ahead" and "Right side: VNAV path deviation 120 ft above the path".
  - The weather radar's returns are not read: the window has the WXR switch, and no row lists a return.
- **Map options replay BlueBird's loop** ([B757-42]). BlueBird draws them by a loop over the FMS's nearest-first
  lists that takes one item per switched-on list a round, skips the tuned stations and the route's own points,
  counts each item within the range plus a margin and stops at the layout's count limit (100) or round limit
  (500). `Bbs757EhsiMapOptionsLoop` replays it, and only its drawn items inside the clip are listed. A range
  filter would list far more: measured 2026-11-12 at the KSEA gate at range 20, the screen drew 2 navaids, 6
  airports and 92 waypoints and stopped.
- **The parts degrade one by one.** The five later parts of the layout (`Approach`, `Tcas`, `MapOptions`,
  `MapExtras`, `MapGuides`) are optional ([B757-41]): missing from an older layout file, not derived for a build,
  or holding a value the reads cannot use (`LayoutProblems`, checked once when the reader is built), a part costs
  only its rows, one "<part>: not read: <reason>" row ("TCAS: not read: not in this layout file"), never the
  reader. Each part's walk is all or nothing like the route's ([B757-40]), so a torn part makes the reading
  `Corrupt`; but several tear conditions follow state that can last, and ten corrupt readings stop a reader for
  the flight, so a part that has torn `TearLimit` (4) readings in a row is dropped alone, "not read: unexpected
  values", until its next good read. A part's values are read only in the modes that draw them ([B757-49]): a
  value no row can show could only add a way to turn the reading corrupt.
- **Positions of navaid legs** ([B757-45]). A navaid leg holds two positions and BlueBird picks one by the leg's
  capability set (`CapabilityChoices`, applied by `LegPositionOffsets` to route legs and FIX fixes). Never the
  primary alone: a TACAN-only station's primary position reads 0, 0 (measured 2026-11-12 on TCM). Without the
  map extras part the rule is unknown, and a navaid fix is listed as "position not read" rather than misplaced.
- **The draw's own conditions, even where they look wrong** ([B757-46]): TCAS FAIL is drawn, and hides the left
  block's other words, only while the display's message gate byte is set; TERR's amber threshold compares the
  gear input as the draw does; the wind row shows dashes exactly when BlueBird's show flag is clear. The pilot
  must hear what a sighted pilot sees.
- **Magnetic against true** ([B757-47]). The course pointer, the FIX radials and the VOR course lines turn
  against the screen's own heading number (`Bbs757EhsiReading.Number`, magnetic or true); the bearing pointers,
  the wind, traffic and every map item against the map's rotation (`Bbs757EhsiMap.Rotation`, true). Swapping
  them is off by the variation, about 15° at KSEA.
- **The measured signs** ([B757-48]), each settled against a live capture or in flight, never by instinct: a
  positive VOR or localizer deviation is right of the course, a positive glideslope is above, traffic trend 1 is
  climbing, the traffic tag's sign is the relative altitude's, and a positive VNAV path deviation is above the
  path (KDEN to CYVR, 2026-11-12: level at 5,000 ft the stored value ran from −1,108 through 0 to +175 as the
  descent path came down through the aircraft).
- **Spoken**, all on the Ctrl+M row "EHSI messages" (`MSFSBA_BBS757_EHSI_MESSAGES`), once after the settle
  ([B757-43]): "EHSI message: EXCESS DATA" and "EHSI message gone: …", the same for the TCAS words TCAS FAIL, TA
  ONLY, TCAS OFF and TRAFFIC; "EHSI flag: HDG, MAP" and "EHSI flag gone: …", the same for ILS mode's LOC and
  G/S; and the active waypoint changing, "EHSI: KOLM, 37 NM" or "EHSI: no active waypoint". Everything else is
  rows only: no mode, range, heading, bug, route edit, map item, traffic, wind or guide is spoken, nor TFC and
  TEST, which are the pilot's own switch and test. A flag or word that comes or goes only because the pilot
  turned the EFIS selector, or because the message gate changed with the mode, is not spoken, and a part's words
  are compared only while that part is read in both readings, so a part dropping out and back says nothing.
- **Ctrl+W** ([B757-38]) says `Bbs757EhsiDisplay.WaypointLine`, interrupting, with the window open or closed and
  never muted by the Ctrl+M row: the active leg's name (a pending modification's leg 0, else the route's; the
  EHSI's top line itself draws no name), then the top line's distance and ETA as drawn: "KOLM, 37.5 NM, 1533.3z",
  "KOLM, 37.5 NM, no ETA", "KOLM, no distance, no ETA", "No active waypoint", in VOR and ILS "KOLM, EHSI in VOR
  mode". With no reading it says why: "EHSI waypoint unavailable: display dark", or the monitor's own reason
  (`NoReadingReason`: "starting" in the 10 s after power-up, a stop reason, "waiting for the simulator").
- **The window** ("Captain EHSI") holds, under the list, the Captain's EFIS controls that change what the EHSI
  shows: the Mode (Alt+M) and Range (Alt+R) drop-downs, the CTR (Alt+C) and TFC (Alt+T) buttons, and the six map
  switches as check boxes, WXR (Alt+W), TERR (Alt+E), NAV AID (Alt+N), APRT (Alt+A), DATA (Alt+D) and WPT (Alt+P).
  Each shows the cockpit's state, not a fixed caption: set from the cached value and read again on every Alt+N,
  then followed on every delivery of its node and every change the cockpit watch reports. A pilot's change goes
  through the main panel's own write entry (`HandleUIVariableSet`), so it settles, refuses aloud and reads back
  exactly as the same pick on the panel does, and the reader speaks nothing for a mode, range or switch change.
- **Alt+N** opens the window or falls back to the AI read when the reader cannot work.

## AI display reads

`Aircraft/BBS757/Bbs757DisplayReads.cs` is the 757's table of AI vision reads (`BBS757Definition.DisplayReads`,
dispatched by `BaseAircraftDefinition.TryReadDisplayFor`, as on the MD-11): each row is a hotkey, a prompt
(`GeminiService.GetPromptForDisplay`), a spoken name and the instrument camera view to capture.

| Key | Display | Prompt | Today |
| --- | --- | --- | --- |
| Alt+P | ADI | `Adi757` | always the AI read: no ADI reader was built |
| Alt+I | Standby instruments | `Standby757` | always the AI read |
| Alt+E | Upper EICAS | `UpperEicas757` | the memory-read window; the AI read only as the fallback |
| Alt+S | Lower EICAS | `LowerEicas757` | the memory-read window; the AI read only as the fallback |
| Alt+N | EHSI | `Ehsi757` | the memory-read window; the AI read only as the fallback |

**The fallback.** A reader's key handler asks its monitor `KeyFallsBackToAi()` and, when true, runs the same key's
AI read (the `AiRead` of `Bbs757KeyContext`, the base class's handling of that key) saying nothing of its own
first. It is true when the monitor was never started, is unavailable (no layout for this build, no access to the
simulator, ten corrupt readings, an internal error), when its 120 s search window has run out, or when the
memory has been lost for 10 s or longer. It is false while the reader waits for the simulator, starts, or has
been searching again for less than 10 s: the window then opens and its one row says so. With no layout file at
all the pilot has already heard "BlueBird display files could not be loaded; the display keys fall back to AI
reading." once.

**The camera views.** The view indices are 0-based into the aircraft's `cameras.cfg` instrument cameras
(ADI/EHSI, EICAS, Overhead, IRS, Engines, FMC, Circuit Breakers), so the simulator's "instrument view 1" is
index 0. Measured on the live aircraft on 2026-10-25 from window captures:
- **Index 0** ("ADI/EHSI", `Bbs757DisplayReads.AdiEhsiView`) frames the Captain's EHSI: a picture laid over the
  EHSI's screen was readable in a capture of this view cropped at full resolution. That the ADI is legible in it
  has not been confirmed in the simulator.
- **Index 1** ("EICAS", `EicasView`) is the EICAS view, and frames far more than the two EICAS CRTs: the whole
  MCP, the standby instruments, the autobrake, the flap gauge, the gear lever and the first officer's airspeed.
  The upper EICAS's messages were legible in a capture 1,600 px wide ("R ENG SHUTDOWN", "PAGE 1", TAT, EPR). So
  every prompt for this view names the one display to describe and says to ignore the rest.
- **Index 2** is the overhead (the camera variable read back 2) and frames no display.

The ADI prompt reads the flight mode annunciations first, then speed, altitude and heading only if the ADI itself
shows them, never a separate gauge beside it, with one exception: the AUTOLAND STATUS annunciator beside the ADI
(LAND 3, LAND 2, NO LAND 3, NO AUTOLAND), read after the flight modes when it shows a message. Every prompt keeps
the display's own words and units.

## First Officer

The 757 has the screen-reader First Officer every other profile has (Shift+C; the shared window, flow
runner and checklist engine are described in [first-officer.md](first-officer.md)): twelve flows, twenty
checklist groups, the altitude-crossing calls and two opt-in automations. Its code is
`FirstOfficer/BBS757/` and `Aircraft/BBS757Definition.FirstOfficer.cs`. Flown on both engine variants
on 2026-10-27 and 2026-10-28 (the flows started from the real window, their step lists read back,
`debug.log` and spot reads over SimConnect), and passed by the owner in the sim and in flight on
2026-11-13.

The First Officer never moves the flap lever, the gear lever or the thrust levers, never sets the landing
autobrake, never programs the FMC and never releases the parking brake: those are Captain reminders or
read-only checks.

### How it is wired

- **Registration.** `Forms/FirstOfficer/FirstOfficerWindows.cs` holds the one row, keyed by the aircraft
  code `BBS_757`: the window's name "BlueBird 757 First Officer" and a `Bbs757FoProfile` built from the
  live `BBS757Definition` and the announcer. Nothing else in the app names the profile.
- **`Bbs757FoProfile`** (`IFoProfile<Bbs757FoActionExecutor, Bbs757FoStateEvaluator>`, title "First
  Officer — BlueBird 757"). The evaluator is created once and is also the executor's state, so the
  executor's safety rules read what the window reads. `SetExecutorSimConnect` gives the executor a
  `Bbs757DefinitionFoTransport` (null when the connection goes) and the announcer's `AnnounceImmediate`
  for the one thing the executor says itself, an aborted engine start. The auto manager reads its two
  settings live from `SettingsManager.Current`, so a change applies at once.
- **In shared First Officer code** the 757 appears in two places only: `CenterPumpGate.IsCenterOnEvent`
  lists the map's two center pump nodes, and `PMDG737/LnavVnavPushHeight` (the 400 ft rules) is reused
  from the 737's namespace. The settings checkbox reads "Auto-manage center fuel pumps (PMDG 737/777,
  iFly MAX8 and BlueBird 757)".
- **The one variable it registers** is `BBS757_FO_ENG_VARIANT` (`L:B757_ENG_VARIANT`, OnRequest,
  `AddFirstOfficerVariables`). Everything else it reads is a map control by its node, a status row or a
  streamed row the definition already registers (`Bbs757FoKeys`; `Bbs757FoChecklistStructureTests` pins
  that every name is registered). The exterior light keys are named by what the control drives, not by
  its node: the node `B757_OVHD_LOGO` is the beacon, `B757_OVHD_BEACON` the position lights and
  `B757_OVHD_NAV` the strobes.

### The write path

A flow step must know whether its switch landed, and the flow speaks for itself. The panel's path
(`HandleUIVariableSet`) is fire-and-forget and speaks its own refusals, so the First Officer does not
call it. `BBS757Definition.FirstOfficer.cs` is a second, silent and awaitable path that reuses the
panel's own decisions and sim access: `Bbs757Write.ToPosition` and `Bbs757Write.PressFor` for what to
send, `Bbs757Guarded.Plan` for a guarded control ([B757-12]; the guard and the switch are read together
and the plan's calls are spaced by `Bbs757Guarded.StepGapMs`), and `WriteIoFor` for the writes and fresh
reads. `Bbs757DefinitionFoTransport` (`IBbs757FoTransport`, faked in the tests) is the thin adapter over
it; `Ready` is `IsConnected && CalcWriteCanLand`.

- **`FoSetAsync`** sets a positional control. It runs as a pick (`BeginPick`), so the control's
  deliveries are consumed while it is in flight (an open panel's combo is not moved under the pilot) and
  a pilot's pick of the same control supersedes it (the write then reports false). True when the control
  already reads the target or reads it afterwards; false for an unknown control, a button, an unread
  control or guard, a target that is none of its positions, or a write that cannot land. A linked status
  row (the parking brake, EXT PWR) has its change taken as the write's echo, as for a panel pick.
- **The pace.** After the write it waits `FoSettleMs` (150 ms), reads, then reads every `FoPollMs`
  (250 ms) and reports landed once TWO reads in a row show the target, giving up at `FoLandMaxMs` (3 s;
  the budget counts the waits asked or the real time, whichever is larger). So a switch that lands at
  once costs about 400 ms, not a fixed read-back delay. Two reads, because BlueBird writes some states
  back: the logs of 2026-11-06 and 2026-11-07 show the parking brake going 1, 0, 1 for about 2 s after a
  set, so one read of the target can lie.
- **`FoPressAsync`** presses a momentary button, or holds a held one for the map's hold or the hold the
  caller gives, and always lets it go (the hold waits on `CancellationToken.None`). True when the press
  was sent: a button has no position, so the caller confirms by the state it drives.
- **`FoSpringTestAsync`** runs a P61 test: its spring switch held to the test's side for
  `Bbs757SpringControls.TestHoldMs` (3 s) and released with the panel's verified release ([B757-15]),
  with nothing said. True when the switch rests afterwards; a switch still off rest is released again in
  the background and keeps its hold until then. One hold per switch, shared with the panel's presses.
- **`FoSetParkingBrakeAsync`** sets the brake (never releases it). First the lever's own toggle, judged
  by one read after 1.5 s rather than the two-read poll; that is all a brake in BlueBird's EASY mode
  needs. If the brake did not move, the read is known and BlueBird's `parking_brake_realistic` setting
  does not say EASY (`Bbs757ParkingBrake.ShouldRetry`), it sends full braking, `K:BRAKES` and the lever's
  value in ONE calculator string, lets the pedals go 1.5 s later and reads again. Measured 2026-10-28
  (MSFS 2020, the RR, REALISTIC mode): the toggle alone left `L:B757_FC_PARK_BRAKE` at 0, so did full
  pedals in one write and the lever in a second, and only the one-string form set it; it stayed set with
  the pedals released. The brake is read from `L:B757_FC_PARK_BRAKE` ([B757-1]).
- **`FoSetAltimetersStandardAsync`** is the Ctrl+B window's own set (one `KOHLSMAN_SET` 16212, its echo
  armed so the altimeter watch stays silent), true when all three read standard.
- **`FoWriteNow`** plans a positional write from the cache and sends it with no read-back. It exists for
  one case, the window closing (below).

### The executor

`Bbs757FoActionExecutor` serializes every write on one gate and reports success only when the control
reads its target afterwards: a refused write is never reported done, so a flow says it skipped the step
and a hand tick does not stay ticked.

**`DispatchAsync` is the single chokepoint.** A flow step, each tuple of a multi-switch step, a checklist
tick (`Set`) and the automation all pass through `SetCoreAsync` into it. It drops a write the flow's
Stop overtook while it waited for the gate, applies the center pump gate (below), then routes: one of
the First Officer's own keys, a preflight test, or a map node (a button or a step with no target is
pressed, anything else set). A key the map does not know is logged and nothing is sent.

Most steps are plain map nodes. The `FO_*` keys are where one pilot action is several writes or depends
on the engine variant:

- **`FO_EXT_POWER`.** EXT PWR is a momentary button that toggles, so it is pressed only when the ON light
  reads the other way (unread: never), ON only with AVAIL lit, and confirmed on the ON light for up to
  4.5 s.
- **`FO_APU_START`.** The selector to START, held `ApuStartHoldMs` (3 s), then ON; done once
  `B757_APU_STATE` reads starting or running within 10 s. Refused on an unread state or an APU shutting
  down; an APU already running only gets its selector put to ON. Measured 2026-10-28 (PW, from cold):
  BlueBird can spring the selector from START back to ON before the read-back, and the APU still starts,
  so a START write that reads ON afterwards counts and only a selector below ON fails. The APU runs 58 to
  80 s after START (measured 2026-10-27 and 2026-10-28). A flow waits for it in a step of its own, so
  Stop and Pause reach the wait; a checklist tick waits inside `StartApuAndWaitAsync` (up to 150 s),
  outside the gate, so other ticks are not held behind it.
- **`FO_FUEL_CONTROL_1` / `_2`.** Target 0 CUTOFF, 1 RUN, `FuelForStart` RUN for a start. The switch pair
  follows the variant: PW `BBS_fuelcut_PW1/2` (0 CUTOFF, 2 RUN), RR `BBS_fuelcut_RR1/2` (0 RUN, 1 RICH,
  2 CUTOFF). A Rolls-Royce start takes RICH when the EGT reads 0 °C or below (the manual's cold start).
  An unknown variant, or a cold-start choice on an unread EGT, sends nothing.
- **`FO_ENGINE_CONTROLS`.** The two engine limiter switches on both variants and the two EEC switches on
  a Rolls-Royce. The manual lists the limiters as Rolls-Royce only, but the PW cockpit has the same
  switches and BlueBird loads them ON on both, so ON on a PW only restores what BlueBird loads.
- **`FO_AT_ARM`.** Judged by BlueBird's armed flag (`L:BBS_AUTO_THROTTLE`), never the switch alone: armed
  already, nothing; the switch at ARM over a disarmed A/T, OFF then ARM (the ARM edge is what arms it);
  done once the flag reads armed within 3 s. Flag unread: refused.
- **`FO_SPEEDBRAKE_ARM` / `FO_SPEEDBRAKE_DOWN`.** The lever's ARMED and DOWN click spots, pressed only
  when the lever reads otherwise and confirmed on the lever. ARM is refused over an extended lever (it
  would snap a deployed speedbrake back).
- **`FO_PARKING_BRAKE`**, **`FO_ALTIMETERS_STD`**: the two definition methods above.
- **`FO_ENGn_LIGHT_OFF` / `FO_ENGn_CUTOUT`**: an engine start's watches (below), flow steps only.
- **`FO_TEST_*`**: the preflight tests (below).

**Engine start safety.**
- A start selector goes to GND only on a READ N2 below 20 % (`MayEngageStarter`; the manual re-engages a
  starter only below 20 % N2, N3 on a Rolls-Royce): never on an unread value, a running engine or a rotor
  still spooling down.
- A GND a FLOW made is remembered with that run's Stop. When the run stops before that engine's fuel is
  on (`OnFlowStoppedAsync`), a selector over a fuel control still reading CUTOFF goes back to AUTO: a
  starter motoring a dry engine. An engine on fuel is left to run, and a GND the pilot or a checklist
  tick made is never undone. When the window closes instead (an aircraft switch, app exit),
  `ReleaseHeldPresses` does the same at once through `FoWriteNow`, from the cache, because by the time
  the stopped flow's clean-up runs there is no aircraft to write to.
- The watches only read, once a second, outside the gate, and hold on the flow's Pause. Light-off is the
  EGT 30 °C over its value at the fuel within 30 s (or N2 already past the starter); cut-out is the start
  selector back in AUTO within 90 s. One timing out on a start THIS run engaged and fuelled aborts it by
  the manual's procedure, never cut short by a Stop: fuel control to CUTOFF, the starter kept at GND
  motoring 30 s (a Rolls-Royce at least 30 s and until the EGT is 100 °C or less, at most 120 s), then
  the selector to AUTO. The Captain hears it at once, for example "Right engine start aborted: no
  light-off within 30 seconds of the fuel. Fuel control to cutoff, motoring 30 seconds, then the start
  selector to AUTO." On anyone else's start nothing is touched: "… The start is not the First Officer's;
  it is left to you." Either way the flow stops. A failed start has not been provoked in the sim.

**[B757-62] The center pump gate.** At the top of `DispatchAsync`,
`CenterPumpGate.ShouldSuppressCenterOn` turns an ON write to `B757_OVHD_C_PUMPS_L_BUTTON` or
`B757_OVHD_C_PUMPS_R_BUTTON` into a success with nothing sent while the center tank reads at or below
`CenterFuelPumpAutomation.OffThresholdLbs` (1,000 lb): the other Boeings' rule that a center pump never
runs on an empty tank, placed where a flow tuple, a tick and the automation all meet it. An OFF is never
gated. The tank is `FO_CENTER_FUEL_LBS`: the center tank's gallons times BlueBird's fuel density, or 6.7
lb/gal (`FallbackPoundsPerGallon`) until the density reads, so an unread density never leaves the tank
unknown. An unread tank is passed as NaN and is NOT gated (NaN compares false). That is safe because
nothing asks for a center pump ON over an unread tank: the automation decides nothing until the tank and
every pump switch read and its policy rejects NaN, and the Before Start step and tick take their target
from `FO_CENTER_FUEL_FOR_PUMPS`, which is unread then and sends nothing.

### The state evaluator

`Bbs757FoStateEvaluator` (an `LVarStateEvaluator`) reads the SimConnect cache by the definition's own
keys. The map controls are OnRequest, so it lists them in `OnRequestPollFields` and the window polls
them each second; status rows and streamed rows ride the 1 Hz batch; the window feeds both engines' N2
(`FO_ENG1_N2`, `FO_ENG2_N2`) as it does for every profile. A synthetic field is NaN until every input it
needs has been read, never 0: an unread switch must not tick a line, untick one or pass a guard.

- **The engine variant.** `TitleVariant` reads it from the aircraft title first: 1 for a title with the
  word PW, 0 for RR, NaN for neither or both. Every title the package ships names one (checked against
  the installed package's `aircraft.cfg` files on 2026-10-28, and pinned by a test). Without one it
  falls back to `L:B757_ENG_VARIANT`, but believes only a 1: it read 1 on the PW (measured 2026-10-27)
  and 0 on the RR (2026-10-28), and an L:var nobody has written reads 0 too, so 0 is unknown, never
  Rolls-Royce. A Rolls-Royce is therefore known by its title alone, and with neither, every
  variant-dependent field is NaN and the executor refuses.
- **What follows the variant.** The fuel control pair and positions; the EEC switches; "running", N2 at
  or above 55 % on a PW and 48 % on a Rolls-Royce (idle measured 59.5 % and 50.5 to 50.8 %; the
  Rolls-Royce's stock N2 stands for its N3); the fuel point, N2 at 25 % on both and, on a Rolls-Royce,
  the EGT below 100 °C (a hot core is motored first).
- **Shared thresholds.** Stopped is N2 below 10 % (measured on the PW: 43 s after CUTOFF). The start
  selector lines latch at 47 %, below both idles and at the starter cut-out (measured about 52 % on the
  PW). The isolation switch reads 1 open (measured 2026-10-27: 1 brought the right duct up to the left's
  pressure).
- **`FO_APU_OFF` is the APU switch** ([B757-60], below); `FO_APU_RUNNING` is `B757_APU_STATE` 2;
  `FO_APU_ON_LINE` adds the APU generator control ON; `FO_IRS_ALIGNED` is all three selectors at NAV with
  every ALIGN light out and the battery ON (unpowered, every light reads out).
- **Gear.** `FO_GEAR_DOWN` is the lever down and every leg above 95 %; `FO_GEAR_UP_OFF` the lever at OFF
  and every leg below 5 %.
- **Flaps.** `FO_FLAPS_TAKEOFF` is the handle at a takeoff detent (1, 5, 15 or 20) and, with a SimBrief
  plan loaded, at the plan's own; `FO_FLAPS_LANDING` is 25 or 30.
- **Fuel.** `FO_FUEL_PANEL_SET` is the four wing pumps ON, both crossfeeds OFF and the two center pumps
  ON exactly when the center tank is above 1,000 lb, the gate's own threshold, so no step ever asks for
  what the gate would drop.

### Flows

`Bbs757FoFlowDefinitions`, in the order of BlueBird's simplified procedures. Every switch step is
skipped as already set when its own state already reads the target, and the executor reads again before
acting. A flow that would be wrong in the aircraft's present state opens with a guard that stops it:
on the ground, and for Power Up, Preflight and Final Securing, both engines stopped (unread fails the
guard). A step refused for a stated reason is left alone with a sentence.

1. **Power Up.** Gear lever down (read), fuel controls CUTOFF, electric hydraulic pumps off, battery,
   standby power AUTO, the bus ties, generator and utility bus controls, then power: external power when
   the GPU is connected (AVAIL lit), else the APU and a wait for it; with neither, the Captain is asked
   to connect the GPU on the EFB or start the APU. IRS selectors to NAV, position lights on.
2. **Preflight.** The overhead left to right (engine limiters and EEC, yaw dampers, engine hydraulic
   pumps, emergency lights ARMED, ignition, start selectors AUTO, crossfeed and fuel pumps off, anti-ice
   and wipers off, window heat, no smoking signs, pressurization AUTO 1, trim air and recirculation fans,
   isolation open, bleeds on), the MCP (flight directors, A/T ARM, bank limit AUTO), autobrake RTO, then
   the eleven tests. Lights: anti-collision red and white, wing, landing, runway turnoff and taxi OFF.
   Reminders: the landing altitude, the FMS, the altimeters.
3. **Before Start.** Doors closed (read), the electric hydraulic pumps R, C, then L, then the parking
   brake ([B757-61]), wing pumps on and each center pump on or off by the center fuel, seat belts on, the
   APU started and waited for (a start that never runs stops the flow: no APU, no start air), external
   power off only with the APU on line, APU bleed on, transponder TA/RA, and the IRS alignment last
   before the Captain's items, waited for up to 10 minutes (a 5 s check there failed every start from
   cold on 2026-10-28; an alignment takes about 10 minutes). Lights: beacon and logo ON. Reminders:
   disconnect the GPU (only after a transfer this run made), "Set the MCP speed, heading and initial
   altitude.", "Start ACARS: on the CDU, MENU, then ACARS.", the pushback and start clearance.
4. **Engine Start.** Packs off, bleeds on, isolation open, the APU running, then each engine, the right
   one first: start selector GND, a wait for the fuel point (up to 90 s), fuel control RUN (RICH on a
   cold Rolls-Royce), the light-off watch, the cut-out watch, then the engine running. A selector or a
   fuel control that does not land stops the flow. Measured on the PW (2026-10-27): N2 reaches 25 %
   about 25 s after GND and the selector releases at about 52 % N2; both engines took 135 s on the PW
   and 113 s on the RR (2026-10-28).
5. **After Start.** Start selectors in AUTO (read), a Rolls-Royce started RICH back to RUN (only from
   RICH, only on the ground), packs AUTO, isolation closed, APU bleed off, APU off (only with both
   engines running or external power on), speedbrake down, autobrake RTO. Lights: taxi ON. Reminders:
   takeoff flaps (then a read-only wait of up to 2 minutes for them) and the trims.
6. **Before Takeoff.** Both engines running, flaps and autobrake RTO (read), seat belts on, the takeoff
   cabin call. Lights: landing, strobe, wing, runway turnoff and taxi ON. Reminder: the CONFIG button.
7. **After Takeoff.** The gear lever to OFF is the Captain's; then flaps up and gear up and off, read
   only (the gear check last). Lights: runway turnoff and taxi OFF.
8. **Descent.** Seat belts on, the landing preparation cabin call. Lights: landing ON. Reminders: "Set
   the landing autobrake on the main panel.", "Set the ILS frequency and course in the NAV radios
   window, Input Ctrl+N.", "Check the landing data and approach speeds, and set the minimums."
9. **Before Landing.** Speedbrake ARMED (left alone over an extended lever: "Speedbrake extended, not
   armed. Left as it is."), seat belts on (read), landing flaps 25 or 30 (read, up to 2 minutes), then
   gear down, three green, read only and last. Lights: taxi and runway turnoff ON. Reminder: "Set the
   missed approach altitude."
10. **After Landing.** Speedbrake down, autobrake OFF, weather radar and terrain off, wing anti-ice off,
    flight directors off, then the APU started and waited for, last. Lights: landing, strobe, wing and
    runway turnoff OFF, taxi ON. Reminders: flaps up, and "Trims: rudder and aileron zero, stabilizer 4
    units."
11. **Shutdown.** Parking brake ([B757-61]), a stop unless the APU or external power is on line, engine
    anti-ice off, fuel controls CUTOFF, a wait for the engines to stop, seat belts off, the stabilizer
    trim reminder (it needs pressure to move), electric hydraulic pumps off L, C, then R, fuel pumps off,
    wing anti-ice and wipers off, window heat off, isolation open, APU bleed on while the APU runs,
    flight directors and the foot and shoulder heaters off, transponder STBY. Lights: beacon OFF, runway
    turnoff, wing, logo and taxi OFF, leaving the position lights.
12. **Final Securing.** IRS off, emergency lights off, APU off with its cool-down and stop
    ([B757-60]), external power off (if it will not go: "External power did not switch off. Remove the
    GPU on the EFB."), then the battery.

**The arrival is two flows**, Descent and Before Landing, as on the MD-11 (the owner's decision of
2026-11-08; the PMDG 737, the iFly and the 777 have three). There is no Approach flow or group, and no
step sets the Captain's EHSI mode or range.

**The cabin chime.** `B757_OVHD_FWD_CABIN_CALL_BUTTON`, a momentary button, pressed in Before Takeoff
("Cabin call: advise the cabin crew for takeoff") and in Descent ("Cabin call: landing preparation";
BlueBird's descent procedure asks for the hi-lo chime). A press has no state, so the step is never
skipped as already set and every hand tick rings it again.

**A check only read is said once.** Doors closed, engines running, flaps up and the gear lines are the
read-back checklist's lines alone; the flow's read-only step delivers that line and the action group
does not repeat it. A write step that also satisfies a read-back line ticks both.

### [B757-60] APU off, the cool-down and the battery

BlueBird keeps the APU running through a cool-down after its switch goes OFF: `B757_APU_STATE` took
about 110 s to come down on 2026-10-27, and read 0 after 18 s and after 80 s of Final Securing's wait on
2026-10-28. So "APU: OFF" (After Start's and Final Securing's steps and lines) is judged by the switch,
`FO_APU_OFF`, the selector at 0, as on the 737s, never by `B757_APU_STATE`. Judged by the state, a hand
tick was unticked as failed while the APU was simply on its way off.

Whether the APU has STOPPED is read where it matters. Final Securing switches the APU off, waits
`ApuCooldownSeconds` (120 s, the 737s' cool-down, the owner's decision of 2026-11-08; a fixed wait, run
only after a switch-off this run sent, so an APU already off costs nothing), then waits up to 150 s for
`B757_APU_STATE` to read 0 and stops the flow if it does not. The battery goes OFF only when
`BatteryMustStay` is false: on the ground, both engines read stopped, the APU state 0 and external power
off; anything unread keeps it ("Battery left on: not read on the ground, an engine or the APU not read
stopped, or external power on."). The manual keeps battery power until the APU has stopped, and the
battery is never the way to stop it. How long the APU takes to stop after the 2 minutes was not
recorded.

One known gap: `FO_APU_RUNNING` reads a cooling APU as running, so a Before Start run within the
cool-down of a hand switch-off skips its APU start.

### [B757-61] The parking brake needs brake pressure

The brake does not set without hydraulic pressure (the owner's report of 2026-11-08; a failed set logged
on 2026-11-07 was the brake sent with no pump on). `Bbs757FoChecklistDefinitions.NoBrakePressure` is
true unless the left or the right electric hydraulic pump reads ON (the 757's alternate and normal brake
systems; the center pumps feed no brakes) or an engine reads running; unread counts as no pressure. While
it is true, the parking brake step of Before Start and Shutdown and both hand ticks send nothing and say
"Parking brake left released: no hydraulic pressure. Turn on the electric hydraulic pumps first." The
First Officer never turns a pump on just to set the brake. Before Start therefore turns the electric
hydraulic pumps on BEFORE the brake step, the reverse of the usual order.

### Preflight tests

`Bbs757FoTests.Preflight`, BlueBird's own preflight tests, run as Preflight steps where a "system tests"
reminder would otherwise stand, shortest first so the long ones come last (the owner's decision of
2026-11-08). The label is what the flow speaks as the step's progress. A test is a held map button
pressed for its hold, or a P61 test switch held 3 s, released either way (a Stop never cuts a hold
short), then a wait (`AfterMs`) so the aircraft's own sound and the cockpit's light announcements, which
keep speaking during the tests, are heard before the next step. The waits are first values, not measured.

| Order | Label | How | Hold | Wait after |
|---|---|---|---|---|
| 1 | "Left stall warning test — listen for the stick shaker" | P61 switch | 3 s | 1 s |
| 2 | "Right stall warning test — listen for the stick shaker" | P61 switch | 3 s | 1 s |
| 3 | "CVR test" | held button | 3 s | 1 s |
| 4 | "Takeoff config test — listen for the configuration warning" | P61 switch | 3 s | 2 s |
| 5 | "Wheel well fire test — listen for the fire bell" | held button | 3 s | 3 s |
| 6 | "Engine fire test — listen for the fire bell" | held button | 3 s | 3 s |
| 7 | "Engine, APU and cargo fire test — listen for the fire bell" | held button | 3 s | 3 s |
| 8 | "Captain oxygen test — listen for the oxygen flow" | held button | 10 s | 1 s |
| 9 | "First officer oxygen test — listen for the oxygen flow" | held button | 10 s | 1 s |
| 10 | "TCAS test — listen for TCAS test pass" | held button | 3 s | 8 s |
| 11 | "Ground proximity test — listen for the callouts" | P61 switch | 3 s | 15 s |

The held buttons' 3 s is the control map's own hold; the oxygen tests replace it with 10 s. A test whose
press did not go out, or whose P61 switch did not come to rest, fails at once with no wait, and the flow
skips it aloud and goes on. Left out on purpose: the battery test, the squib test and the landing
configuration test; the pilot can still press them on their panels.

Each test is also a line of the Preflight action group. A self-test has no state, so the line is never
auto-ticked and **every hand tick runs the test again**, but only parked: on the ground with both
engines read stopped, as the flow's guards have it. Otherwise nothing is pressed: "Tests left alone: not
read on the ground with the engines stopped." (never a TCAS test, a stick shaker or a fire bell in
flight or during an engine start).

### Checklists

`Bbs757FoChecklistDefinitions`, the two layers every profile has.

- **Action groups**, one per flow with the flow's id (Power Up, Preflight, Before Start, Engine Start,
  After Start, Before Takeoff, After Takeoff, Descent, Before Landing, After Landing, Shutdown, Final
  Securing): a tick sets the switch through the executor and the line auto-detects from the cockpit. A
  line refused in the present state says why instead of acting: fuel controls, hydraulic pumps, fuel
  pumps, the IRS and the tests only when parked; the fuel CUTOFF of Shutdown only on the ground with the
  APU or external power on line; a fuel control to RUN by hand only at that engine's fuel point ("Left
  fuel control switch left at cutoff: the engine is not at the fuel point."); the APU off only with both
  engines running or external power on. The two start selector lines latch on the engine's N2 passing
  47 % and stay complete, because the selector itself returns to AUTO at cut-out.
- **Read-back groups**, BlueBird's one-page Normal Checklist in its order and words, action-free: Before
  Start, After Start, Before Takeoff, After Takeoff, Descent and Approach, Before Landing, After Landing
  and Shutdown Checklist. A line the app can read ticks itself from BlueBird's own variables; a line
  that needs the pilot's judgment or a figure (fuel against the plan, the briefing, the altimeters,
  Recall) is a Captain reminder. BlueBird has no Preflight or securing read-back page, so those two
  flows have an action group only.
- **The Descent and Approach Checklist** (`DESCENT_CL`) is BlueBird's In Range and Approach cards as one
  list, in the cards' order, completed by the Descent flow; the Approach card's "Altimeters: SET" is the
  In Range card's, said once.
- **One line is not on BlueBird's card**: "Start ACARS" ends the Before Start Checklist, as on every
  profile.

### Altitude crossings

`Bbs757FoFlightPhaseMonitor` does what the other profiles' monitors do, and says what happened, never
what was asked. Every call is queued, since one sample can produce several.

- **10,000 ft** (300 ft of hysteresis, gated on `FOAutoLights10kEnabled`): climbing, both landing lights
  off, "Above ten thousand. Landing lights off."; descending, on, "Below ten thousand. Landing lights
  on."; a write that did not land says "… did not switch off." / "… did not switch on."
- **Transition altitude, climbing**: with `FOAutoAltimetersEnabled` on, all three altimeters to standard
  by value, "Transition altitude. Altimeters standard."; off, or when the set did not land, the shared
  reminder. **Transition level, descending**: always the shared reminder only (the local setting is the
  Captain's). The thresholds come from SimBrief; with none loaded there is one reminder passing 18,300 ft.
- **Seat belt signs** follow the shared `SeatbeltAutomation` through `SetSeatbeltSign`.

### Automation

`Bbs757FoAutoManager`. `Update` runs on the SimConnect message thread, so a write runs as a task and
never blocks it. The flap lever stays the Captain's (BlueBird publishes no flap schedule), so the
auto-flaps setting is stored and never acted on; gear and autopilot engagement are the universal
automation service's, as on every aircraft.

**LNAV and VNAV at 400 ft AGL**, gated on the auto-autopilot setting (`FOAutoApEnabled`, "Auto-engage
autopilot on climbout"), as on both 737s. The height is fixed (`LnavVnavPushHeight.Feet`), not the
configurable autopilot height. The push is armed on the ground or by an airborne sample below 400 ft
(`LnavVnavPushHeight.Armed`), so a window first opened in the climb, or the setting switched on there,
never presses anything. Climbing (above 200 ft/min) at or above 400 ft, each mode whose MCP light
(`BBS757_MCP_LIGHT_LNAV`, `_VNAV`) reads OUT is pushed; the leg's single attempt is spent once a push
went out or both lights were read (`ShouldBurnLatch`), and a touchdown gives the next takeoff its own.

`PushMcpAsync` does the press, on the gate: it reads the light FRESH, presses only over a light read
out (the buttons toggle: lit means armed or engaged, and a press would turn the mode off), then reads
the light every 500 ms for up to 3 s. **[B757-63] The words say only what a press did.** `McpPush` has
three results, and a light found lit or unread on the fresh read, or a press that was not sent, is
`NotPressed`: not pressed and not reported. Only `PressedLit` and `PressedNotLit` are spoken, in one
queued line built by `PushWords`: "400 feet. LNAV and VNAV on.", "400 feet. LNAV on. VNAV did not come
on.", "400 feet. LNAV and VNAV did not come on." Saying "did not come on" over a mode that was already
lit would send the pilot to press it, which turns it off. The word is "on", never "engaged": a lit light
is armed or engaged. Both presses not made says nothing at all.

**Center fuel pumps**, opt-in (`FOAutoCenterPumpsEnabled`), through the other Boeings' shared
`CenterFuelPumpAutomation` policy and its `center_pumps.log` (described in first-officer.md): ON during
ground setup with the wing pumps on and the center tank above 1,500 lb, OFF in any phase once it reads
below 1,000 lb for 2 s. The manager passes the tank as `FO_CENTER_FUEL_LBS` and decides nothing until
the tank, both center pump switches and all four wing pump switches read. Unlike the 737s, it speaks
once the write has landed: "Center fuel pumps on." or "Center fuel pumps did not switch on.", "Center
tank low. Center fuel pumps off." or "Center tank low. Center fuel pumps did not switch off." Its ON
write passes the gate of [B757-62] like any other.

## Thrust levers

The app has no thrust lever control: the 757 is flown with the simulator's own throttle keys, a controller
or a hardware throttle. On 2026-10-25 BlueBird ignored every stock throttle event (`K:THROTTLE_CUT`,
`K:THROTTLE_SET`, `K:AXIS_THROTTLE_SET`, `K:THROTTLE_AXIS_SET_EX1`, `K:THROTTLE_INCR`) while a hardware
throttle moved both levers, and a direct write of `L:BBS757_THRUST_LEVER_L` / `_R` (percent) moved them. A
Pedestal panel writing those two variables was planned for pilots without hardware and dropped on
2026-11-13, when the owner reported that the keyboard and an Xbox controller now move the levers. The
definition's thrust hooks (below) are declared and unimplemented.

## BBS Nest

BlueBird's systems run only while BBS Nest (`C:\BBS Nest\bbs_nest.exe`, its own SimConnect client)
runs: without it the cockpit takes every switch and no system reacts. Measured on 2026-10-25, cold and
dark at a gate for a whole session: battery ON, standby power to BAT and APU START were all taken by the
cockpit model while the battery bus stayed at 0 V and the APU never turned; once Nest ran and the flight
was reloaded, the same writes worked. The aircraft's own warning is on a display, so the app checks for
the process itself (`Bbs757Nest.IsRunning`; when Windows cannot be asked the answer is "running", since a
false warning would send the pilot after a problem that is not there). About a second after connecting,
switching to the profile or loading a flight, the app looks for the `bbs_nest` process once and, when it is
missing, says once: "BBS Nest is not running. The 757's systems will not respond until it runs and the
flight is reloaded." The check rides the end of the 1 Hz continuous batch (`DeferredFlushWatchVariable` on
`SIM_ON_GROUND`), which is delivered whether or not a value changed, so a quiet cold-and-dark cockpit is
not a reason to wait. The warning is no Ctrl+M row's: a delivery MainForm has wrapped in
`announcer.Suppressed` does not use it up, and it is said on the next delivery instead. Settling the check
is also what starts the cockpit-wide watch (`OnConnectionBatch`).

## Take-off callouts

The 757 plays its own pilot-monitoring 80 knots, V1 and rotate (BlueBird's settings switch each on or off
per registration, `options.pilot_callouts.*`, beside its EGPWS altitude callouts), so
`BBS757Definition.PlaysOwnTakeoffSpeedCallouts` is true and Takeoff Assist speaks none of its speed
callouts ("80 knots", "100 knots") on it: a roll must never hear two "80 knots". `MainForm.Announcers`
passes the flag to `TakeoffAssistManager.ProcessSpeedUpdate` with every IAS sample, so it always follows
the aircraft loaded now; every other aircraft keeps the callouts (`TakeoffAssistSpeedCalloutTests`).
Takeoff Assist's centerline tone and pitch calls are unchanged.

## Seams

- **`BBS757Definition.Hooks.cs`** declares the `partial void` hooks through which each feature area of the
  definition lives in a partial file of its own without editing the main files. A hook nobody implements
  compiles away with its calls. They are called at fixed places: variables (`BuildVariables`, after the
  readouts: `AddOverheadVariables`, `AddRadioVariables`, `AddEfbVariables`, `AddThrustVariables`,
  `AddFirstOfficerVariables`); panels (`BuildPanelsOnce`: the matching `Add…Panels`); display text
  (`TryGetDisplayOverride`, first: `Format…Display`, the first to set the text wins); panel sets and typed
  text (`HandleUIVariableSet` and `HandleUITypedText`, before the squawk: `Handle…Set`,
  `Handle…TypedText`); deliveries (`ProcessSimVarUpdate`, after a pending pick: `ProcessRadioUpdate`,
  `ProcessAutoflightUpdate`, `ProcessEfbUpdate`, then the readouts); hotkeys (`HandleRadioHotkey`,
  `HandleReadoutHotkey`, before the definition's own switch); a flight load or dropped connection
  (`ResetRadios`, `ResetAutoflight`, `ResetThrust`, `ResetAnnouncements`); a switch away
  (`CloseRadioWindows`); the BBS Nest check settling, once per connection and flight load
  (`OnConnectionBatch`, whose announcer may be suppressed); the app's own writes (`OnOwnWrite` for a panel
  press or pick, `OnOwnSquawkSet`, `OnOwnAltimeterSet`); and Ctrl+M rows for speech that is no variable's
  (`AddCduMonitorRows`, `AddCockpitMonitorRows`). The six thrust hooks have no implementation.
  `Bbs757SeamsTests` lists every hook by name and pins the Ctrl+M rows and shared keys.
- **`Bbs757SharedKeys`** holds the variable keys more than one partial names, each registered by exactly
  one: `ExtPwrOn` and `ExtPwrAvail` (the readouts), `GpuConnected` (the EFB partial).
- **`BBS757Definition.Announcements.cs`** is the cockpit-wide watch's wiring: `CockpitWatched`,
  `SpokenByOtherRows`, and the implementations of `OnConnectionBatch`, `OnOwnWrite`, `ResetAnnouncements`
  and `AddCockpitMonitorRows`.
- **Test seams** on the definition are delegates a test replaces, most of them `init`-only: `NowMs` (the
  clock of every echo window and rest), `CanWrite`, `McpSetIo`, `ReadoutIo`, `WriteIo` (the sim access,
  since a `SimConnectManager` cannot read in a test), `IsMonitorMuted`, `NestRunning`, `UseRestTimer` and
  `UseAltimeterTimer` (off, with `ReleaseRestedAutoflight` and `ReleaseRestedAltimeter` called by hand).

## Calculator strings

Each write's string stays under 900 characters: MobiFlight's command buffer is 1024 and cuts longer
ones silently. `Bbs757Rpn.Burst` splits by length as well as by count, and
`Bbs757RpnTests.Every_string_a_757_control_can_produce_stays_under_900_characters` walks the whole map.
