# BlueBird 757-200

BlueBird Simulations' 757-200, package `bluebirdsim-aircraft-757-200` (release 0.1.0). Profile
"BlueBird 757-200", code `BBS_757`, chosen from the Aircraft menu like every profile. Rules:
`.claude/rules/b757.md`. The investigation, the spec and the plans are under `docs/b757/`.

  (panel writes, the BBS Nest warning, hotkeys); `.Mcp.cs` (the MCP value windows and readouts),

  `Bbs757AutopilotLayout`, `Bbs757McpWindowLayout` (all pure), `Bbs757DisplayReads`.

- `HotkeyGuides/BBS757_Hotkeys.txt`.

## The control map

`MSFSBlindAssist/Resources/bbs757_control_map.json` is generated from the installed package by
`tools/b757-gen/generate_b757_map.py` (`python -I tools/b757-gen/generate_b757_map.py`, which finds the
package in the Community folder; curation in `tools/b757-gen/curation.json`): every regular control's
node, section, panel, label, named positions and the vendor's click code, plus the read-only status
rows. Regenerate it after a BlueBird update, never hand-edit it. It is embedded and loaded once.
A control taken in from an excluded vendor banner (`include_nodes`) must be placed by a `node_panels`
rule, or the generator stops (it would otherwise land on a panel named after the excluded banner).

**The map's order is the order the pilot tabs through** (task 11d, ruling R37). The definition builds its
sections, panels and controls in map order, so the generator sorts them, and two curation keys say how:
- `panel_order` (section → panel names): those panels come first in their section, in that order, BlueBird's
  preflight flow from the manual. The panels it does not list follow alphabetically, and the run names them
  (a panel BlueBird adds later turns up in that note). The sections keep their fixed order: Overhead,
  Glareshield, Forward panel, Pedestal, Other; the Status section is added by the app, last.
- `control_order` (panel → **node** names): those controls come first in their panel, the most used first; the
  rest follow in cockpit order (the vendor file's order). Labels are made in cockpit order before either order
  is applied, so an order never renames or renumbers a control.
- These stop the run (`CurationError`): a section the map does not have, a panel the section has none of, a
  panel with no controls, a node that is not in the panel it is listed under, a repeat, an empty list, and a
  `control_order` panel name that two sections share.

The three overhead start selectors (Ignition, L ENG Start, R ENG Start) and the four fuel control switches
share one Pedestal panel, **Engines**, in start order: Ignition, L ENG Start, L Fuel Control (PW), R ENG Start,
R Fuel Control (PW), then the RR pair. Their `node_panels` rules name the section Pedestal, because a
`B757_OVHD_` node would otherwise land in the Overhead by its prefix. The app's own Squawk Code field joins
TCAS and transponder right after its first control, TCAS Mode (`BBS757Definition.TransponderModeNode`).
Panels are keyed by name in the definition, so no panel name may be in two sections or shared with an app
panel (`Bbs757DefinitionTests` pins it: a second panel of the same name replaces the first one's controls
with an empty list). The engine values are not a panel of their own: they are the Engines panel's status
display (ruling R45), so an engine start (selector GND, watch N2, fuel control RUN, EGT) happens in one
panel.

Each control becomes one OnRequest L:var keyed by its node; buttons and held buttons render as
buttons, everything else as a combo of its positions. Positions are named only where evidence backs
the name (the vendor's tooltips, its nine panel states, the manual, a live read); the rest read
"Position n". Ruling R32 named the flow switches this way: Seatbelts and No Smoking OFF / ON, the
pack selectors OFF / AUTO, the pressurization Mode Select AUTO 1, the overhead Ignition selector (the
node says ENG START) 1, Bank Limit AUTO, the EICAS thrust reference BOTH, the wiper OFF; each name and
its evidence is in the curation's `_notes`. The status rows (APU state, master warning and caution, the
AC bus power sources, APU speed, cabin altitude, the chocks) are the Status section's display; the
announced ones have Ctrl+M rows.

## How it writes

Every write replays the control's own click code through the MobiFlight calculator with a unique
prefix: a toggle, guard or select presses once when it is not at the pick; a switch steps by position;
a switch with no click code is written through its state var. A pick is acted on 300 ms after the
last row the pilot arrows onto, from a fresh read of the control; an unread or unknown reading sends
nothing. Before writing, the definition asks `CalcWriteCanLand` (it registers `MSFSBA_BRIDGE_PROBE`,
so the calc-path probe gives a verdict) and says "{label} unavailable" when nothing could land. A
button is pressed, held 200 ms (a held button its own time) and released, then "{label} pressed" is
spoken. 1.5 s after any write the control is read again, so its combo shows where it really is.

A button whose result can be read says that instead of "pressed" (CORE-7): the 14 MCP mode and CMD
buttons read back their light ("CMD R on") and the three speedbrake spots the lever ("Speedbrake
armed"), each about 1.5 s after the release (`LinkedStatusKey`, `PressAsync`). The press arms an
echo window on that row (`Bbs757ChangeTracker`, 5 s), so the row's own change announcement does not
say it a second time; the read-back closes the window and becomes the row's baseline, so a later
change (a CMD that engages slowly) still speaks. A parking brake pick arms the same window (the
screen reader read the combo) and reads the row back with its re-read, about 1.8 s after the pick,
closing the window then: a snap-back after it (the brake set again in REALISTIC mode) is spoken.
The writes reach the sim through `Bbs757SimIo` (`WriteIoFor`), which the tests replace.

## Flight-control readouts and call-outs

Plan 01 task 10 (from `docs/b757/evidence/flight-readiness.md`). What is read, and why
(`docs/b757/evidence/live-findings.md`, session 6):
- **Flaps**: stock `FLAPS HANDLE INDEX` (follows BlueBird's lever, measured 0 to 1), detents UP, 1,
  5, 15, 20, 25, 30; surfaces `TRAILING EDGE FLAPS LEFT ANGLE`. Each detent's angle is BlueBird's
  `flight_model.cfg` ([FLAPS.0] 0, 1, 5, 11, 20, 25, 34 degrees: flaps 15 is 11 degrees, 30 is 34), so
  the surfaces are "at" the detent within 0.4 degree of that angle (below half the smallest gap: UP
  and 1 are a degree apart, so the lever on 1 with the surfaces at 0 is never "Flaps 1"). Output L
  reads the angle twice 500 ms apart when it is off: "Flaps 5, moving, 3 degrees" or "Flaps 1,
  surfaces at 0 degrees" ("1 degree" in the singular).
- **Gear**: stock `GEAR CENTER/LEFT/RIGHT POSITION` (0 up, 1 down) and `GEAR HANDLE POSITION`. The
  plan named `GEAR POSITION:n`, documented as an enum (unknown, up, down) with no "in transit", so
  the leg positions are read instead (unmeasured on BlueBird either way). "Gear down" when all three are 0.99 or more, "Gear
  up" at 0.01 or less, else "Gear in transit"; Shift+G adds the lever when it disagrees.
- **Speedbrake**: `L:B757_FC_SPOILER_LEVER` (0 down, 10 armed measured; 100 is the UP click):
  below 5 down, to 15 armed, from 95 up, between "up N percent" to the nearest ten.
- **Parking brake**: `L:B757_FC_PARK_BRAKE`. Never the stock `BRAKE PARKING POSITION`, which read 0
  with BlueBird's brake set ([B757-1]).
- **MCP lights**: `L:B757_MCP_<THR|SPD|LNAV|VNAV|FLCH|HOLD_1|VS|HOLD_2|BCRS_1|LOC|APP|CMD_1|CMD_2|CMD_3>_BUTTON`
  (each button's decal lights from it), read under keys `BBS757_MCP_LIGHT_<name>` because the light
  var has the button node's own name. HOLD_1 is HDG HOLD, HOLD_2 ALT HOLD (stage 10a's evidence);
  CMD 1 to 3 are CMD L, C and R (curation labels).
- **EXEC light** (task 11c, ruling R36): `L:FMC_EXEC_ACTIVE_1`, the captain's CDU light, read under
  `BBS757_EXEC_LIGHT`; both CDUs lit together after ACTIVATE and went out after EXEC (session 7), so
  the first officer's `_2` is not read. "EXEC light on" / "EXEC light off" (the iFly CDU window's
  words), Ctrl+M row "EXEC light", on no panel and no status display.

These rows ride the 1 Hz batch and speak their changes from `ProcessSimVarUpdate`
(`Bbs757ChangeTracker`): the first reading after a connection or a flight load is a silent baseline,
an unchanged phrase is silent. Each has a Ctrl+M row; MainForm's mute wrap gates them ([VAR-8]). The
three gear legs speak the one "Gear" row's call-out (the nose leg's row; the main legs have none), so
they are `IsMuteWrapExempt` and check that row's mute themselves. They show on the Status panel
(flaps with the flap angle, gear, speedbrake, parking brake) and the MCP panel's status display
(the lights); the EXEC light is on neither.

**Trim** (task 11c, ruling R35). The shared trim call-out (`MON_ElevatorTrim`, the stock `ELEVATOR
TRIM POSITION` in degrees on the 1 Hz batch) speaks BlueBird's indicator units: the definition
overrides `DescribeElevatorTrim` with `Bbs757Readouts.StabTrimUnits`, `max(0.436, -0.002148·d² +
0.803152·d + 1.11308)`, the strip's own code in the cockpit XML (2.3 degrees at load is 2.95 units),
keyed on the tenth it speaks: "Trim 5.3", the 737s' words (`StabTrimUnitsCallout`), invariant. The
stock trim events reach the stabilizer (session 7), so the setting is heard about once a second while
it moves. The base class's first-reading baseline, hysteresis and Shift+T toggle apply as on every
aircraft; it keeps the shared Ctrl+M row and has no key and no status row.

Output mode, read at once (`ReadoutAsync`; a batch-covered row from the cache, anything else fresh):
L flaps, Shift+G gear, B the three altimeters and the decision height ("Altimeter: 1018, 30.05. DH
200"), F and Shift+F fuel (the loadsheet's tank gallons × `FUEL WEIGHT PER GALLON`, pounds or
kilograms, rounded to 10, the total the sum of the spoken tanks), W and Shift+W `TOTAL WEIGHT`
(whole pounds or kilograms, the other Boeings' words).

## Altimeters, minimums and squawk

- **Ctrl+B, "Altimeter and minimums"** (`Forms/BBS757/BBS757AltimeterForm.cs`). The altimeter box
  takes inches (27.00 to 32.00) or hectopascals (940 to 1090), typed in any culture (CORE-17), and
  sends `K:KOHLSMAN_SET` with 16 × hPa (measured: sets all three altimeters, `KOHLSMAN SETTING
  MB:1..3`); Standard sends 16212 (1013.25 hPa), and so does a typed standard value (29.92 inches, or
  1013 or 1013.25 hPa; 29.92 inches alone would be 16211). The three are read every second for up to 6 s (the
  reads lag a few seconds) and spoken: once when they agree (`AltimeterPhrase.Sentence`, the words
  every aircraft uses), else one by one, numbered as the simulator numbers them (which is the
  captain's, the first officer's or the standby is unmeasured).
- **Radio minimums** in the same window: the stock `DECISION HEIGHT` (the ADI's DH) is read-only and
  steps 10 ft per `K:INCREASE_DECISION_HEIGHT` / `DECREASE_DECISION_HEIGHT` (measured). A set reads it,
  sends the difference (at most 250 steps a round, bursts of 25 per call), then, as the MCP speed set
  does, reads until it settles and re-sends the remainder up to three times; a read outside 0 to 2500 ft
  sends nothing ("DH unavailable"). Spoken: "DH 200".
- Both ride the MCP sets' machinery (`RunMcpSetAsync`): refused aloud when the calculator cannot land
  a write, a repeat of the same value ignored while one is in flight, canceled on a flight load or a
  profile switch. The window's status box opens on the current values and keeps the last result.
- **Squawk**: the TCAS and transponder panel's "Squawk Code" field (`Bbs757Squawk`), four digits 0 to
  7, sent as `K:XPNDR_SET` in BCD (measured: 0x4743 set 4743), `TRANSPONDER CODE:1` read back 1.5 s
  later and spoken as one number, "Squawk 4743" (the owner's rule). The panel's status display shows
  the code. The definition takes the box's raw text (`HandleUITypedText`, offered by MainForm before it
  parses the number; every other aircraft keeps the default, not handled), so an empty box says "Type a
  four-digit squawk first." and letters or an 8 or 9 say "Squawk must be four digits, each 0 to 7."
  (both parse to NaN). 0000 is a real code.

## The MCP value windows (Ctrl+H, S, A, V)

`BBS757Definition.Mcp.cs`, the sets and phrases in `Bbs757Mcp` (pure). Each is the HS787's modeless
`ValueInputForm`: Enter sets the value and the window stays open. Heading and altitude are direct
writes of `L:BBS_AP_TARGET_HEADING` and `L:BBS_AP_TARGET_ALTITUDE`; the vertical speed is written
directly, then stepped by `K:AP_VS_VAR_INC/DEC` if the window did not take it. What is spoken is the
value read back, never the request ("Speed 250"). A repeat of the speed being set is ignored while it
is in flight; a different value supersedes it.

**The speed** (`SetSpeedAsync`, [B757-3]). The target `L:BBS757_ORANGE_AIRSPEED_BUGS` is read-only and
moves only by `K:AP_SPD_VAR_INC/DEC`, which BlueBird speeds up within a burst, as a knob turned fast:
events 1-10 move 1 kt each, 11-25 2 kt, from the 26th 5 kt. A burst is one calculator call or several
back to back; a pause of about 0.3 s starts a new one (session 7, after the first flight, whose sets
sent one event per knot: 53 events moved the target 180 kt and 47 drove it to the 100 kt floor). A set
reads the target, sends one planned burst (`SpeedBursts`: the most events whose tiered sum does not
pass the change), waits `SpeedBurstGapMs` (600 ms, twice the reset) and sends the 0-4 kt left as a
burst of its own. Each burst is one RPN loop, `N sp0 :1 l0 0 > if{ (>K:AP_SPD_VAR_INC) l0 1 - sp0 g1 }`
(`SpeedBurstCode`), short for any count. It then reads until the target settles and, while the
remainder shrinks, corrects it up to three times in bursts of at most 10 events (`LinearBurstMax`),
each followed by the same pause, so every correction event moves 1 kt. 200 to 153 is 26 events (45 kt)
and 2; 100 to 280 is 53 events; every speed from 100 to 399 lands with no correction on the measured
tiers (`Bbs757McpTests`). A newer speed set that supersedes one just after its burst first waits out the
rest of that pause from the last speed write, whichever set sent it (`SetSpeedSpacedAsync`), so its burst
is not counted into the old one's.

**The mode buttons** (`McpWindowButtons`, ruling R34), laid out by `Bbs757McpWindowLayout`, as the PMDG
737's windows carry theirs: Heading HDG SEL, HDG HOLD, LNAV; Speed SPD, THR, FLCH, IAS/MACH; Altitude
ALT HOLD, VNAV, FLCH; Vertical Speed V/S. Labels come from the map, each with an access key on the
first letter of its last word (Alt+S HDG SEL, Alt+H HDG HOLD, Alt+L LNAV; two buttons of one window
that would share a letter get none). A button's state is its cached MCP light, "On" or "Off" ("LNAV:
On"); HDG SEL and IAS/MACH have no light and show none. A press is the panel's
(`PressFromPanelAsync`): refused aloud when nothing can land, else the click, then the light read back
once ("LNAV on") or "HDG SEL pressed". The window's own read-out 1.2 s after a press is suppressed
(`SuppressStateAnnounce`), or the press would be said twice (CORE-7). A node missing from the map is
left out with a warning in the log.

## The autopilot window (Ctrl+P)

`Forms/BBS757/BBS757AutopilotWindow.cs`, laid out by `Bbs757AutopilotLayout`: CMD L, C, R, A/T Arm,
Captain F/D, F/O F/D, THR, SPD, LNAV, VNAV, FLCH, HDG HOLD, ALT HOLD, V/S, LOC, APP, each captioned
"Label: State" and refreshed twice a second, rewritten only on change. A light button's state is its
MCP light. A/T Arm shows `L:BBS_AUTO_THROTTLE`, BlueBird's armed flag (1 On, 0 Off; ruling R40: the
A/T's real state, which the switch's click code sets with the switch; every panel state loads it 1
with the switch ON, session 7); the two F/D switches show their map position. These are read on
request about once a second while the window is shown (`RequestedKeys`; the flag is registered
OnRequest, no Ctrl+M row). A press is the panel's: a button replays its click without speaking when its
light changes (the caption change is the feedback, as in the iFly, HS787 and MD-11 windows); when the
light reads back as it was before the press (the cached value), the caption cannot change, so it says
"CMD L did not engage" or "… did not disengage" once (the iFly window's words). A switch moves to its
other position from the read value (never on an unknown one: a toggle's press flips it). Since A/T
Arm's caption is the flag but its press flips the switch, the flag is read fresh after the pick wrote
(`SetPositionAsync` says whether it did): unchanged from the cached value the caption showed, it says
"A/T Arm did not arm" or "… did not disarm" once (`AutothrottleRefusedPhrase`); changed, nothing. That
is heard when the switch and the flag disagreed (a second press then sets it).

## Engine values

The Pedestal's Engines panel (from the map: the ignition, the start selectors and the fuel control
switches) has a status display with `TURB ENG N1:n`, `TURB ENG N2:n`, `GENERAL ENG EXHAUST GAS
TEMPERATURE:n` (celsius), `ENG FUEL FLOW PPH:n` and `TURB ENG PRESSURE RATIO:n` for each engine, read
while the panel is shown, never announced (ruling R45; until then they were an "Engine values" panel
under Status). The status display's 1-second refresh skips while a combo has focus, so with the
cursor on a start selector or a fuel control switch the values wait for F5 (or Ctrl+3). Unmeasured on
BlueBird: compare them with an Alt+E read of the upper EICAS at the first engine start (the in-sim
plan).

## BBS Nest

BlueBird's systems run only while BBS Nest (`C:\BBS Nest\bbs_nest.exe`, its own SimConnect client)
runs: without it the cockpit takes every switch and no system reacts. About a second after
connecting, switching to the profile or loading a flight, the app looks for the `bbs_nest` process
once and, when it is missing, says once: "BBS Nest is not running. The 757's systems will not
respond until it runs and the flight is reloaded." The check rides the end of the 1 Hz continuous
batch (`DeferredFlushWatchVariable` on `SIM_ON_GROUND`), which is delivered whether or not a value
changed, so a quiet cold-and-dark cockpit is not a reason to wait.

## CDU and EFB

Both CDUs' screens arrive as text on the simulator's Comm Bus (`BBS_CDU_DISPLAY_1`, `_2`), read
through the Coherent debugger in the hidden `BBSTablet` view; keys are held L:vars
(`L:B757_CDU_<1|2>_<KEY>`). Details in `docs/b757/spec.md` §3.3.

### The 757 EFB window (Shift+T)

BlueBird's tablet is drawn and clicked inside the aircraft's WASM, so the window
(`Forms/BBS757/BBS757EfbForm.cs`) operates it by scripted clicks and checks each result where it can
be read.
- **The clicks.** `CoherentBbs757EfbClient` and `Resources/coherent-bbs757-efb-agent.js` work in the
  `BBSNavigraphMap` view. The agent calls the `efb_l` canvas's own mouse handlers.
- **The positions.** All in `SimConnect/BBS757/Bbs757EfbLayout.cs`, with the unmeasured ones marked
  "est.". The agent refuses a canvas that is not the measured 1397 × 1058, and the window then says
  "The 757's EFB layout is not the one this version knows".
- **What it reads.**
  - BlueBird's work folder, `Bbs757WorkFolder`: the candidate whose `efb_settings.json` was written
    last. It reads only `simbrief_id`, `units`, `tiller_realistic` and `NavigationData\cycle.json`,
    never logs them, and never writes them.
  - The Navigraph sign-in, through the tablet client.
  - `SIM ON GROUND`, read fresh, for the preset gate and the fuel and payload load.
  - `L:BBS757_vis_chocks`, read fresh through its Status row's registration, for the chocks.
- **One run at a time.** A run given up on is canceled in the page; one still going when the client
  is disposed (a profile switch, app exit) is canceled first, waiting at most half a second.
- **Stale links.** While the window is hidden the client sends nothing. Showing it pings at once, and
  that ping or a run's start going unanswered drops the socket at once (a half-open socket after a
  reload).
- **Navigraph code.** Spoken letter by letter first; the browser opens 2 to 6 seconds later, so the
  focus change does not cut the code off.
- **SimBrief ID.** The entry presses keypad BKSP ten times before the digits. It is judged from the
  stored ID before and after: saved, not saved, or "BlueBird stored a different SimBrief ID".
- **Units.** BlueBird asks to switch the aircraft's unit system only when the plan's weight units
  differ, and the question cannot be seen. After a fetch the window says the aircraft's units now and
  what each answer does. Accept units and Keep units are pressed only right after a finished fetch,
  on the same page; the window reads `units` before and after the click (0 METRIC, kilograms; 1
  IMPERIAL, pounds: read 1 live after a YES on 2026-10-25, and the module lists METRIC, IMPERIAL,
  INVALID in that order) and says "Weight units now pounds", "Weight units unchanged, pounds" or that
  they could not be read.
- **Presets and quick starts.** Home, Aircraft, the COCKPIT PRESETS menu item (127,178), then the tile
  (ruling R39): the Aircraft app reopens on the page it was left on (GROUND SERVICES after a chocks
  tap, measured 2026-10-25; the FUEL page after a load), so the menu item is always tapped first.
  Ready for taxi (433,369), Ready for takeoff (433,421), Engine quick start (822,524) and IRS rapid
  align (1209,519) were measured the same evening. Cold and dark, Turnaround, Before start, Ready for
  taxi and Ready for takeoff load only on the ground; After takeoff, Cruise, Approach and Final
  approach only airborne ("That preset is for the ground." / "That preset is for flight."). With no
  ground reading, nothing is clicked.
- **Set steering to rudder.** Home, Settings (1073,190), AIRCRAFT (98,244), then the NOSEWHEEL
  STEERING switch (1154,249), all measured on 2026-10-25 (session 6). The switch TOGGLES between
  REALISTIC (the tiller) and RUDDER, so it is clicked only while `tiller_realistic` reads true
  (`Bbs757EfbLayout.MayClickSteering`); false says "Steering is already rudder" and clicks nothing, and
  an unreadable setting refuses. After the click the setting is watched for up to 3 s (BlueBird wrote
  it at once, measured) and the result said: "Steering set to rudder", or that it did not change or
  could not be read. A run that started and did not report finishing is judged from the setting; it
  is never run again. The switch is far from the UPDATE/REMOVE spot (the agent's guard does not
  apply). [B757-2].
- **Remove chocks / Set chocks** (ruling R31: the owner's INITIAL CHOCKS IN PLACE puts the chocks on at
  every load, and the aircraft will not move with them). Home, Aircraft (320,190), the GROUND SERVICES
  menu item (128,368), then the CHOCKS tile (404,556), measured 2026-10-25. The tile TOGGLES
  `L:BBS757_vis_chocks` (0 removed, 1 in place, measured 0 → 1 → 0), so the variable is read fresh
  first (`Bbs757EfbLayout.MayClickChocks`, [B757-2]): already where wanted says "Chocks are already
  removed" (or "in place") and taps nothing; unreadable refuses ("The chocks cannot be read, so nothing
  was clicked."). Otherwise one run, the variable read about 1.5 s later, and "Chocks removed", "Chocks
  in place" or "BlueBird did not move the chocks". Not limited to the ground: BlueBird shows the tile in
  flight too. The Status display's "Chocks" row (In place / Removed, never announced, no Ctrl+M row)
  comes from the generator's `status` curation.
- **Fuel and payload from SimBrief** (task 11e: the owner asked that the load go through BlueBird's
  EFB rather than its setter variables). BlueBird loads the plan itself: the window taps
  `Bbs757EfbLayout.LoadThroughEfb`, measured 2026-10-25 (`docs/b757/evidence/live-findings.md`,
  session 7): FETCH SIMBRIEF OFP on the ACARS dashboard, then Home, Aircraft, FUEL (67,237), IMPORT
  FROM SIMBRIEF (508,962), the defuel question's YES (400,648), START BOARDING (1231,24), YES again,
  and Home, each tap 1.5 s after the one before. IMPORT and START BOARDING each ask "Current fuel
  exceeds the flight plan fuel. Are you sure you want to defuel?" when the fuel is above the plan,
  and (400,648) is empty background on the FUEL page otherwise (a capture during step 0's fueling:
  left of the FUELING IN PROGRESS overlay and the FUEL ADJUSTMENT IS COMPLETE! box, which span about
  x 530-1117, y 581-720), so YES is tapped either way. BlueBird fuels in a few minutes (about two for
  3,300 lb) and boards at its REALISTIC pace (under 40 minutes for 114 passengers); its BOARDING &
  LOAD RATE slider and AUTOMATIC BOARDING switch do not take BA's input (ruling R38). BA taps no OK on
  the FUEL page's "FUEL ADJUSTMENT IS COMPLETE!" box or the boarding notification: neither blocks
  anything (ruling R42). START BOARDING (1231,24) is a top-bar button whose face follows BlueBird's
  state (the same captures): green START BOARDING before boarding, a darker "BOARDING …" status button
  during it, and no button at all after "BOARDING IS COMPLETE". What a press does during a boarding is
  unmeasured, so BA never presses it while its watch runs (a second press is refused), and a run that
  may have pressed something without confirming every press is watched, not offered again ("The EFB
  did not confirm every press. BA is watching the fuel and payload, and says within three minutes if
  BlueBird has not started."; `Bbs757LoadWatch.StartedPhrase`). A run that pressed nothing says why,
  and pressing again is safe.
  - **Before any tap**, in order: no load watch running ("The load is already running."); BBS Nest
    running (`Bbs757Nest.IsRunning`; the Nest warning plus "Nothing was loaded."); BlueBird's
    work folder found and its `simbrief_id` stored ("Set your SimBrief ID first.": BlueBird's own
    fetch uses it, so the app's SimBrief username no longer stands in; the ID is never logged or
    spoken); BA's own fetch of that ID's latest OFP (`SimBriefService.FetchLatestOfpXmlAsync`, off
    the UI thread) parsed by `SimConnect/BBS757/Bbs757Loadsheet.cs` (`fuel/plan_ramp`,
    `weights/pax_count_actual` else `pax_count`, `pax_weight`, `payload` else passengers × weight +
    `cargo`, `params/units`, `aircraft/icaocode`: anything but `B752` refuses); the plan fitting the
    tanks and holds; the plan's weight units the aircraft's (`Bbs757Loadsheet.UnitsRefusal`,
    [B757-4]: BlueBird's fetch asks to switch the units when they differ, and that question's YES is
    14 px from the defuel YES the load taps blind); no units question left up by an earlier Fetch
    SimBrief flight (`Bbs757UnitsQuestion`: that button now fetches the same plan through the app to
    learn its units, says whether BlueBird is asking, and the question counts as up on that tablet page
    until Accept units or Keep units presses its answer; "BlueBird is asking whether to switch the
    weight units. Press Accept units or Keep units first."); and a fresh `SIM ON GROUND` on the ground.
  - **The targets** are how BlueBird spreads the plan (`Bbs757Loadsheet.Compute`, whole pounds, the
    block rounded): up to both wings' 29,158 lb, the right wing `floor(block / 2)` and the left the
    rest, the center empty; past that, both wings 14,579 lb and the center the rest (refused past
    46,390 lb); passengers `round(min(pax, 176) × pax_weight)` (BlueBird seats 176 and puts the rest
    of the payload in the holds); cargo `round(max(0, payload − passengers))`, the forward hold first
    up to 10,300 lb and the aft the rest (measured: 3,990 lb all forward, 20,659 lb 10,300 / 10,359;
    refused past 25,000 lb).
  - **The load watch** (`BBS757Definition.LoadWatch.cs`, judged by `Bbs757LoadWatch`) belongs to the
    definition, so it outlives the window. Every 15 s it reads `FUEL TANK LEFT/RIGHT/CENTER QUANTITY`
    (gallons) × `FUEL WEIGHT PER GALLON` and `PAYLOAD STATION WEIGHT:3`/`:4` (cabin), `:5` and `:6`
    (holds), all eight registered OnRequest with no Ctrl+M row. It says once "Fueling complete." with
    the fuel when the tanks' total is within the larger of 1% and 100 lb of the block (BlueBird
    converts at about 6.72 lb/gal and the sim reports 6.70: the 16,400 lb plan read 16,346) and every
    tank moved less than 20 lb since the last read (the APU burns fuel, so the tanks never read
    unchanged; and on a turnaround BlueBird can move fuel between tanks while the total holds still);
    and once "Boarding complete." with the passengers, the cargo, the cap when the plan had more
    passengers than seats, and "For the ACARS weight and balance, request WGTBAL on the CDU.", when the
    cabin and the cargo's TOTAL (ruling R43: BlueBird's split between the holds is not judged) are each
    within the larger of 0.5% and 20 lb of the targets and moved less than 1 lb since the last read.
    The first read only seeds; a group with a value unread is skipped. At three minutes, a part not done
    whose tanks (by 100 lb) or stations (by 1 lb) have not moved since the first read is said not to
    have started and is no longer watched: "BlueBird has not started loading. Is BBS Nest running?
    Check the fuel with F and the weight with W." when neither moved (fueling and boarding start at
    once, measured), or "BlueBird has not started fueling." / "… boarding." for one. After an hour
    without both it says what has not finished ("Boarding has not finished after an hour. Check the
    weight with W.") and stops. A flight load, a lost connection (`OnSimContextReset`) or a profile
    switch ends it silently. What is said is rounded to 10 in the aircraft's `units` (pounds when unread), each
    total the sum of its spoken parts, as background announcements (CORE-7), queued.

  debug.log gets numbers only: the targets when the load starts, and the targets and what the tanks
  and stations hold at each announcement.

**The nav data update and the reload rule.** On the AIRAC page, the UPDATE button and BlueBird's
REMOVE share one spot. BlueBird chooses between them from its own latest-cycle check. That check runs
inside the WASM when the flight loads, signed in to Navigraph, and nothing outside can read its result.
The update therefore binds the click to the flight load (`Bbs757EfbLayout.MayClickUpdate`). The agent
records when its page loaded (`Date.now() - performance.now()`); the view's document is made anew on
each flight load. The window clicks only when all of these hold:
- the installed cycle is older than the one in force;
- the pilot is signed in, and was not seen signed out since the load (a sign-in after the load needs
  a reload);
- the flight was loaded on or after the current cycle's first full day (the day after it took
  effect, UTC);
- the flight was loaded at least a minute ago.

Otherwise it says "BlueBird checks for new nav data when the flight loads. Reload the flight, then
try again." or "BlueBird is still checking for nav data. Try again in a minute.". On a new cycle's
first day it says to reload after midnight UTC, then update. The agent checks the page conditions
again on the very page the window judged (`SamePageAsMs`), and runs the update at most once per
flight load. The agent (version 3) refuses any sequence with a click within 100 × 40 px of the spot
unless it carries the update's once-key, earliest-load and minimum-age guards, and the client runs a
sequence only on that agent version. It never clicks when the folder, the cycle file, the page or the
sign-in cannot be read, or when the candidate work folders disagree: another one holding the current
cycle or newer, or a cycle file that cannot be read ("More than one BlueBird work folder was found and
they disagree. Update from the EFB in the sim."). After a successful update the window says to reload
the flight: the aircraft misbehaves until then. A run that started but did not report finishing is
judged from the cycle file all the same (the same 20-second wait and removed check).

**Residual risk.** With a lapsed Navigraph subscription, or a cycle Navigraph publishes late,
BlueBird may still show REMOVE where UPDATE was. The click then removes the installed nav data. The
window reports it when `cycle.json` is still missing at the end of its 20-second wait. An UPDATE with
an active subscription, after a reload, restores the data.

## Take-off callouts

The 757 plays its own 80 knots, V1 and rotate (`options.pilot_callouts.*` per registration, spec
§4), so `BBS757Definition.PlaysOwnTakeoffSpeedCallouts` is true and Takeoff Assist speaks none of its
speed callouts ("80 knots", "100 knots") on it. `MainForm.Announcers` passes the flag with every IAS
sample; every other aircraft keeps them (`TakeoffAssistSpeedCalloutTests`). Takeoff Assist's
centerline tone and pitch calls are unchanged.

## Calculator strings

Each write's string stays under 900 characters: MobiFlight's command buffer is 1024 and cuts longer
ones silently. `Bbs757Rpn.Burst` splits by length as well as by count, and
`Bbs757RpnTests.Every_string_a_757_control_can_produce_stays_under_900_characters` walks the whole map.

## AI display reads

The ADI, EHSI and both EICAS CRTs are WASM-drawn with no text behind them, so Alt+P, Alt+N, Alt+E and
Alt+S read them by AI vision on a camera capture, as on the MD-11: `Aircraft/BBS757/Bbs757DisplayReads.cs`
is the table (`BBS757Definition.DisplayReads`, dispatched by `BaseAircraftDefinition`) and the four
prompts are `Adi757`, `Ehsi757`, `UpperEicas757` and `LowerEicas757` in `GeminiService.GetPromptForDisplay`.
The sim's instrument view index 0 ("ADI/EHSI", the sim's "instrument view 1") was measured as framing the
captain's EHSI (a 2026-10-25 window capture, `docs/b757/evidence/efb-and-manual.md`); that the ADI is
legible in it is still to be confirmed in the sim. Index 1 ("EICAS", the sim's "instrument view 2") was
measured as the EICAS view (`docs/b757/evidence/live-findings.md`): it frames both EICAS CRTs and also the
whole MCP, the standby instruments, the autobrake, the flap gauge, the gear lever and the first officer's
airspeed, so the EICAS prompts name their CRT and say to ignore the rest. The ADI prompt reads speed,
altitude and heading only if the ADI itself shows them, never a separate gauge beside it, with one
exception: the AUTOLAND STATUS annunciator beside the ADI (LAND 3, LAND 2, NO LAND 3, NO AUTOLAND),
read after the flight modes when it shows a message, since no variable carries it
(`docs/b757/evidence/wasm-findings.md` §5). The prompts keep the display's own words and units.
