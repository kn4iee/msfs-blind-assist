# Where a new aircraft plugs into MSFSBA (inventory of 2026-10-23, on `main` at 5a48f17c6)

Read before writing the plan index: the "Shared" list is what one plumbing plan must own so the parallel plans never
touch the same file. Paths are repo-relative under `MSFSBlindAssist/` unless they start with `tests/`, `docs/`,
`guide/` or `tools/`. Line numbers drift; grep the named member.

## 1. How an aircraft is chosen

- The app never auto-detects the profile: the pilot picks it from the Aircraft menu. ATC MODEL and TITLE only resolve
  an ICAO type for GSX door side and docking (`SimConnect/SimConnectManager.Dispatch.cs`, `OnAircraftIcaoTypeDetected`
  in `MainForm.AircraftSwitch.cs`). B752 and B753 are already known to `Navigation/Briefing/AircraftSizeClass.cs` and
  `Services/GroundTrafficLogic.Names.cs`.
- `UserSettings.LastAircraft` (default "A320") is restored through `LoadAircraftFromCode` (a switch on the code, falls
  back to the A320) and saved in `SwitchAircraft`.
- Profile codes in use: `A320`, `FENIX_A320CEO`, `PMDG_737`, `PMDG_777`, `FBW_A380`, `HS_787`, `HW_A330`,
  `IFLY_737MAX8`, `TFDI_MD11`. **The 757's code must not start with `PMDG_`, `FENIX_` or `HS_`**: prefix checks exist in
  `UpdateAircraftSpecificMenuItems`, the mute gate in `MainForm.Announcers.cs`, `DefAnnounceMuteSets` and
  `PMDGSdkFamily`. Proposed: `BBS_757`.

## 2. The definition contract

- Abstract: `AircraftName`, `AircraftCode`, `BuildVariables` (start from `GetBaseVariables()`), `GetPanelStructure`,
  `BuildPanelControls`, `GetPanelDisplayVariables`, `GetButtonStateMapping`, the four `Get…ControlType`.

  `TryGetDisplayOverride`, `TryDescribeControlState`, `IsPanelControlVisible`); announcements (`ProcessSimVarUpdate`,
  `IsMuteWrapExempt`, deferred-flush members); take-off calls (`TakeoffCalloutFeedKey`, `TakeoffCalloutFeedNeeded`);

- Helpers: `ShowTrackedWindow<T>` (closed on aircraft switch), `ShowFCUInputDialog`, `PulseMomentaryLVar`.

## 3. How comparable aircraft talk to the sim

| Aircraft | Writes | Reads | Windows |
|---|---|---|---|
| PMDG 737 / 777 | PMDG SDK events | SDK client data area | CDU, Coherent EFB, Ctrl+P, monitor, display reads, First Officer |
| iFly 737 MAX | WM_COPYDATA SDK | shared memory | CDU, EFB (WebView2), autopilot, monitor, First Officer |
| HorizonSim 787 | K: events, `SetLVar`, calc code, **B: input events** (`HS787_INPUT_EVENT_MAP`, `TryFireInputEvent`) | L:vars and stock vars; Coherent DOM for CDU, CAS, IRS | FMC, EICAS, synoptic, autopilot, monitor; no First Officer |
| TFDi MD-11 | `L:CEVENT` over the MobiFlight calc path (`Md11EventBus`), registers `MSFSBA_BRIDGE_PROBE` | L:vars; MCDU text over a client data area | MCDU, autopilot, monitor, Coherent EFB, display reads, First Officer; control map generated by `tools/md11-gen` |
| FBW A32NX | `SetLVar` + unconditional calc code per prefix ([VAR-3]), `SimVarType.HVar` press/release, dotted `A32NX.*` events | L:vars | MCDU, flyPad, FCU, DCDU, E/WD, monitor, First Officer |

MobiFlight-relevant mechanics:

- **B: input events** today go through native SimConnect only: `SimConnectManager.HasInputEvent` / `TrySetInputEvent`
  (`SimConnect/SimConnectManager.Setup.cs`). The catalog is enumerated on every aircraft load (when the connection
  completes, whatever profile is selected) and appended to `%APPDATA%\MSFSBlindAssist\logs\input_events.txt`.
  No `(>B:…)` calculator code exists in the app; `SimVarDefinition.InputEventName` is declared but unused. Nothing
  READS a B: event's value: `SimConnect_GetInputEvent` / `SubscribeInputEvent` are unused, so state must come from an
  L:var or SimVar unless a plan adds that read path. The Fenix
  ACP work (2026-10-16) proved `(>B:…_Set)` also works over the calc path with a unique prefix ([SIM-17]).
- **H: events**: `SendEvent("H:X")` goes to MobiFlight whenever connected; `SendHVar` / `SendButtonPressRelease`.
- **L:vars**: `SetLVar` takes the calc path only once `CalcPathVerified`, which needs the aircraft to register
  `MSFSBA_BRIDGE_PROBE` (plus a row in `tests/MSFSBlindAssist.Tests/CalcPathProbeOptInTests.cs`); otherwise a native
  data-def write. Calc helpers: `ExecuteCalculatorCode`, `ExecuteCalculatorCodeUnique` ([VAR-4]), `CalcWriteCanLand`,
  `CanSendEvent`, `BuildCalcEventCode`. Fresh reads: `ReadFreshAsync`.
- `SimConnectManager` needs no 757 change unless we add a calc-path B: helper or a client data area.

## 4. What a new aircraft owns, and what it must share

Owned by the 757 alone (no other aircraft touches them):

- `Aircraft/BBS757Definition*.cs` (partials) and optionally `Aircraft/BBS757/`; `Aircraft/BBS757DisplayReads.cs`
  (already globbed by `ai-display.md`)
- `Forms/BBS757/` (a `MonitorManagerFormBase` subclass is required; CDU, MCP, EFB windows as needed)
- `MainForm.BBS757.cs` (menu click, window openers, disposal helpers)
- `FirstOfficer/BBS757/` (`FirstOfficer/Generic/LVarActionExecutor.cs` and `LVarStateEvaluator.cs` are reusable)
- `HotkeyGuides/BBS757_Hotkeys.txt` (the `HotkeyGuide*ChordTests` and `ShippedGuidesShiftCTests` scan every guide)
- `Resources/coherent-bbs757*.js` if a Coherent agent is needed
- Its tests, `docs/b757.md` (the aircraft doc, written at integration), `docs/invariants/b757.md`,
  `.claude/rules/b757.md`

Shared files the 757 cannot avoid (one plan should own all of them):

- `MainForm.Designer.cs` (menu item); `MainForm.AircraftSwitch.cs` (`LoadAircraftFromCode`, `UpdateAircraftMenuItems`,
  `SwitchAircraft` teardown, optionally `UpdateAircraftSpecificMenuItems`)
- `MainForm.Hotkeys.cs`: Shift+M (falls through to the Fenix MCDU without a branch) and Shift+T (does nothing without
  one)
- `MainForm.Announcers.cs`: the Ctrl+M mute gate (one `if` per aircraft) and the "announce initial change" set
- `MainForm.cs`: per-aircraft form fields and app-exit teardown, if the 757 owns timers or transports
- `Settings/UserSettings.cs`: `BBS757DisabledMonitorVariables`, its setter, `RebuildDisabledMonitorVariableCaches`
- `Services/DefAnnounceMuteSets.cs` (only if the definition announces from `ProcessSimVarUpdate`, [VAR-8])
- `Forms/HotkeyListForm.cs` (hotkey file map), `Forms/FirstOfficer/FirstOfficerWindows.cs` (one row, [FO-24])
- `MSFSBlindAssist.csproj` (`<None Update>` for the hotkey guide and any agent script)
- `Services/GeminiService.cs` only if the 757 needs its own display prompts (the HS787 reuses the generic PFD/ND/ISIS)
- Take-off calls: wrap `Aircraft/TakeoffVSpeedCallouts.cs` / `TakeoffCalloutKeys.cs` (pattern `A320TakeoffCallouts`,
  `MD11/Md11TakeoffCallouts`) and add a glob to `.claude/rules/takeoff-and-callouts.md`
- Tests with an aircraft list: `ComboLabelCollapseTests.AllAircraft` (feeds `FirstOfficerWindowsTests`,
  `MonitorRowLabelUniquenessTests`, `MonitorRowMuteReachabilityTests`, `VarNameCollisionTests`), `CalcPathProbeOptInTests`,
  `DefAnnounceMuteSetsTests`
- Shared rule files: `autopilot-engage-call-sites.md` (if the 757 overrides `IsAutopilotEngaged`), the
  `first-officer*.md` files if their globs should cover `FirstOfficer/BBS757/`
- `HotkeyManager.cs` needs nothing: its actions are generic and the definition handles them.
- The status display has no per-aircraft hook: it runs on `GetPanelDisplayVariables`, `OnDisplayPanelShown`,
  `TryGetDisplayOverride`.

## 5. Rules, docs and guide plumbing

- `.claude/rules/b757.md` with `paths:` globs for every owned folder and file and the tests; with no rules yet, a
  heading and one line naming its doc. `ClaudeContextBudgetTests` enforces: every shipped file loads a rule file of its
  own (`variable-definitions.md` and `troubleshooting.md` don't count for an aircraft's own folders), every glob matches
  a file, code loads a rule file whenever its test does, size caps, no double loads, every rule names code it loads on.
  It cannot catch a missing glob for a top-level definition file, `MainForm.BBS757.cs` or a top-level SimConnect file:
  check those by hand.
- CLAUDE.md: one row in "Where things live", nothing else.
- Guide ([CORE-19]): a section in `guide/boeing-aircraft-and-the-md-11.md`, `guide/hotkey-reference.md`, the aircraft
  list and MobiFlight note in `guide/getting-started.md`.
- Changelog: `changelog.d/<pr>-<slug>.aircraft.md`, numbered only once the PR exists.

## 6. Probing tools to reuse

- `tools/coherent.ps1 views` lists every Coherent (HTML) view the loaded aircraft has; `scrape`, `eval`, `capture`
  work on any view; `docs/tooling.md` §9.3 adapts a CDU scraper to a new aircraft.
- `input_events.txt` (above): the B: catalog for free.
- simconnect MCP: `msfs_list_lvars`, `msfs_get_lvar`, `msfs_execute_calculator_code`, `msfs_search_hubhop`,
  `msfs_trigger_custom_event`. Its reads register per-frame watches until it reconnects (see the investigation's
  hazards); [DBG-1]: never judge a write by the MCP's `set_lvar`, test through the calc path.
- `docs/troubleshooting-playbook.md`: the write-mechanism decision tree and read-back discipline (DBG-4 to DBG-7).
- `tools/md11-gen` (Python control-map generator from ModelBehaviorDefs) if the 757's controls are numerous and
  regular; `docs/b757/tools/survey_package.py` for the first offline pass.
