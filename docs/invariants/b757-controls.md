# BlueBird 757 control map and panel writes — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/b757-controls.md`, which Claude Code loads when it reads the control map, its generator or the panel write code; the shared 757 rules are in [b757.md](b757.md). Background: [docs/b757.md](../b757.md).

How every measurement below was made, unless a section says otherwise: on the ground, MSFS 2024, BlueBird 757-200, BBS Nest running, MSFS Blind Assist closed; writes through the MobiFlight calculator path, as the app writes, and reads through SimConnect and through the Coherent debugger in BlueBird's tablet view (`SimVar.GetSimVarValue`, all 2,173 BlueBird L:var names in one call, compared before and after each action against a list of the variables that drift on their own). Every value changed was put back.

## B757-6

- A guarded 757 control carries no click code. The curation (`tools/b757-gen/curation.json`, key `guarded`) lists three: the emergency lights switch (`B757_OVHD_PASS_OXY_Toggle_Switch_CLICK`: 0 OFF, 1 ARMED, 2 ON; guard `B757_OVHD_SWITCH_GAURD`, 0 closed and 1 open, whose closing sets 1) and the two stabilizer trim cutout switches (`B757_Stab_trim_C_toggle_switch_CLICK` and `B757_Stab_trim_R_toggle_switch_CLICK`: 0 NORMAL, 1 CUTOUT; guards `B757_AISLE_STAND_STAB_1_GAURD_SWITCH` and `_2_`, whose closing sets 0). For each, the generator (`generate_b757_map.py`, `guarded_control`) emits a switch with its state var, its positions and the guard fields (`guard`, `guard_closed`, `close_sets`; `Bbs757Control.Guard`, `GuardClosed` and `CloseSets` in the app) and leaves press, release, cw and ccw null.
- Why. BlueBird's click on such a switch runs only while its guard is open: the model XML wraps it in a test of the guard, which the extractor writes as an `[if <test>]` note in front of the click code. That note is not RPN, so a replayed click would fail, and with the guard closed the vendor's click does nothing at all. Measured 2026-10-25: the emergency lights switch took a click only with its guard open, and closing the guard wrote ARMED. Before plan 02 the switch was missing from the map (its state is not a plain animation variable) and the cutouts had a write that never landed.
- The gate-note check works in both directions. A control listed under `guarded` gets no click code whatever the extractor read. Any other control whose press, release, cw or ccw still carries the note stops the generator run with a message that names the control and says to list it under `guarded`: a click that only runs behind a guard must never reach the map as something the app replays. `Bbs757ControlMapTests` pins the shipped map (`No_click_code_in_the_map_carries_the_extractors_gate_note`, `Guarded_controls_carry_their_guard`, `Every_guard_a_control_names_is_a_guard_row_of_the_map`, `Each_guard_sits_right_before_the_switch_it_covers_on_its_panel`), and `tools/b757-gen/test_generate_b757_map.py` the generator.
- How the app writes one: [B757-12]. → [b757.md](../b757.md)

## B757-7

- The 757's pressurization landing altitude is set as `Bbs757LandingAltitude.Write` sets it: one calculator string that writes the target less 10 ft to `L:B757_OVHD_LDG_ELEV` and then 1 to `L:B757_OVHD_LDG_ELEV_CHG`, the knob's step input (a 1 adds 10 ft). For 1030 ft: `1020 (>L:B757_OVHD_LDG_ELEV) 1 (>L:B757_OVHD_LDG_ELEV_CHG)`.
- Why. Measured 2026-10-25: `L:B757_OVHD_LDG_ELEV` takes a direct write (1030 written over 1000 held), but the panel's digit drums (`L:B757_OVHD_LDG_ALT_2000`, `_200` and `_20`, the thousands, hundreds and tens digits, which read 1, 0, 0 at 1000 ft) are redrawn only on a knob step, so after the direct write alone the panel still showed 1000. One step of `L:B757_OVHD_LDG_ELEV_CHG` added 10 ft and redrew the drums (1030 to 1040, drums 1, 0, 4). So the exact set is the target less 10, then one step: 990 and a step read 1000 with the drums at 1, 0, 0.
- Measured again 2026-10-26, replaying the strings the code sends: `1020 … 1 …` read 1030 and the step variable read 0 again; `-70 … 1 …` read -60; the range's ends, `-1080 … 1 …` read -1070 and `14090 … 1 …` read 14100, and one more step at 14100 still read 14100 (BlueBird clamps at the top). The owner then typed 1030 and 645 (heard as 650) on the Pressurization panel in the app, and both passed.
- The knob moves in 10 ft steps from -1070 to 14100 ft, so `Bbs757LandingAltitude.TryParseText` rounds the typed feet to the nearest 10 before it checks the range, and reads the text with `NumberParsing.TryParseTyped` ([CORE-17]). The write is invariant and fixed point (`Bbs757Rpn.SetLVar`): under sv-SE a negative number would otherwise carry a U+2212 minus, which the RPN parser rejects. The 757 has no cruise altitude selector; the FMC's cruise level is on the CDU. `Bbs757LandingAltitudeTests` pins the parsing, the string and the phrases. → [b757.md](../b757.md)

## B757-12

- A guarded 757 control (a map row whose `Guard` names another map row, [B757-6]) is written only through `Bbs757Guarded.Plan`, from fresh reads of the control and of its guard. The plan is a list of calculator calls, sent `Bbs757Guarded.StepGapMs` (300 ms) apart by `BBS757Definition.SetGuardedAsync` (the panels) and by the First Officer's transport, which calls the same planner:
  - A pick of the position the guard's closing sets (`CloseSets`: emergency lights ARMED, stab trim NORMAL): with the guard open, close the guard and then write the state var too; with the guard closed, write only when the control reads something else.
  - Any other pick (emergency lights OFF or ON, stab trim CUTOUT): with the guard closed, open it and then write the state var; with the guard open, write only when the control reads something else. The guard is left open, as BlueBird's own panel states leave it.
  - Refused, with nothing sent and "{label} unavailable" said: a control or a guard that was not read or is not a number, a control with no state var or no `GuardClosed` value, a pick that is none of the control's positions, a guard with no press code or no position other than closed.
- Why. The guard is a toggle: its press flips it. So it is pressed only once its state has been read and differs from what the pick needs, and an unread guard presses nothing. A click on the switch behind a closed guard does nothing (measured 2026-10-25), so the app writes the state var directly, which is a real write and not a dead mirror: measured 2026-10-26, `2 (>L:B757_OVHD_PASS_OXY_Toggle_Switch_CLICK)` with the guard open held, lit the cabin emergency lighting (`BBS757_CABIN_EMER_LIGHTING` 0 to 1) and started the emergency battery draining (100 to 97 % over the test). The guard's own press while open closed it and set the switch from 2 to 1 (ARMED), and for the center stab trim cutout from 1 to 0 (NORMAL): BlueBird's close forces `CloseSets`. Opening a guard writes nothing to its switch. After closing, the app writes `CloseSets` itself as well: if BlueBird's close already wrote it the write changes nothing, and if a guard's click ever does not, the control still lands.
- Once the first call of a plan has gone, a newer pick of the same control does not stop the sequence (a half-run one would leave the guard open with no state write behind it); a flight load, a dropped connection or a profile switch does, and nothing more is sent. A pick on a guard row also re-reads every control that guard covers. `Bbs757GuardedTests` pins the planner and the sequence (`Armed_from_off_closes_the_guard_and_writes_one`, `On_with_the_guard_closed_opens_it_first`, `Unread_state_refuses`, `A_newer_pick_does_not_cut_a_sequence_short`, `A_flight_load_in_the_step_gap_stops_the_sequence`). → [b757.md](../b757.md)

## B757-13

- After the app presses a fire handle Unlock button (engine 1, engine 2 or APU), it locks the handle again itself: `Bbs757Write.RelockAfterUnlock` gives the write, an unconditional 0 to the button's state var (`BBS757_FIREUNLOCK1`, `2` or `3`), and the delay, `Bbs757Write.FireHandleRelockMs` (1,500 ms); `BBS757Definition.RelockIfUnlock` sends it that long after the press, for a press from a panel and for one from the First Officer alike.
- Why. In the cockpit, BlueBird's unlock click sets `L:BBS757_FIREUNLOCKn` and starts a timer in the component's own `O:` variables, and the component's update loop clears the unlock 1.5 s later. A calculator write cannot set a component's `O:` variables, so the timer never starts. Measured 2026-10-26: the map's unlock press sent through the calculator left `L:BBS757_FIREUNLOCK1` at 1 four seconds later, where the cockpit would have relocked; `0 (>L:BBS757_FIREUNLOCK1)` relocked it, and the handle stayed in (`L:B757_ENGFIRE_1_SWITCH` 0). Without the relock, one press of Unlock would leave a fire handle free to be pulled for the rest of the flight. The owner checked the relock in the app the same day.
- The three buttons are known by their state var, and only as momentary buttons: a toggle or a switch on the same variable would be flipped by a relock nobody asked for (`A_control_that_is_no_momentary_button_is_never_relocked_even_on_an_unlock_state_var`, and `The_shipped_maps_three_unlock_buttons_are_the_only_controls_that_relock`, which reads the shipped map on purpose: it ties the relock to BlueBird's own identifiers).
- The relock waits on the profile's lifetime and is not stopped by a flight load or a reconnect: the write is the cockpit's resting value, so it is safe in the flight that follows, and skipping it would leave the handle unlocked, the defect it exists to prevent. Only a switch to another aircraft profile drops it (`Switching_away_before_the_relock_sends_nothing_more`). Nothing is spoken for it: the press said "{label} pressed" (CORE-7).
- What the code does not do. A handle's own pick replays BlueBird's click, which pulls only while the handle is unlocked or its fire warning is on, so pulling a handle with no fire warning takes Unlock and then the handle's Pulled within the 1.5 s. A decision of 2026-10-26, that picking Pulled on a locked handle should press Unlock first, was never built; build it as its own change, and keep this relock. → [b757.md](../b757.md)

## B757-14

- A 757 control listed under `direct_write` in the curation keeps no click code in the map: the app writes the picked position's value straight to its state var (`Bbs757Write.ToPosition`'s path for a control with no click code, an absolute `Bbs757Rpn.SetLVar`). Three controls are listed: the captain's and the first officer's chronometer ET levers (`B757_MAIN_CHRONO_ET_SWITCH` and `_FO`) and the flight deck door switch (`B757_OVHD_FLT-DK-DOOR_SWITCH`).
- Why they are there. The chronometer ET lever's vendor code steps the wrong way for the app's stepper (its clockwise code lowers the value) and can step onto 2, which is no position (0 RUN, 1 HOLD, 3 RESET): once the lever read 2, the app refused every later pick. The door switch's codes write 2 and 0 whatever the switch reads, so stepping by position never arrives. Both were found by replaying every control's click code against its positions (plan 02, October 2026).
- Why it is safe only under a check. Leaving a click out loses everything else that click did. So the generator (`check_direct_write`) stops the run unless the control's vendor click exists (else the entry does nothing), carries no gate note (a gated click belongs under `guarded`, [B757-6]), and writes nothing but the state var: another L:var it sets, or a K: or H: event it fires, would no longer run. A write to an `O:` variable is let through: `O:` variables belong to the component, and the sim's calculator cannot set one (that is why the fire handle relock exists, [B757-13]), so the app's replay of the click never ran that write either. The door switch's click stamps `(>O:UpdateTime)` for the component's own spring-back. That an `O:` write through the calculator does nothing is inferred from the fire handle measurement; it was not measured on the door.
- Not checked by the generator: an inline test inside the click that reads another L:var (only the extractor's gate note is seen), and the hand-typed positions of a `direct_write` row. `Bbs757ControlMapTests` pins the shipped rows (`The_chronometer_ET_lever_keeps_no_click_code_and_names_RESET_at_3`, `The_flight_deck_door_switch_keeps_no_click_code_and_goes_straight_to_the_pick`). → [b757.md](../b757.md)

## B757-15

- A spring-loaded switch the app holds (`Bbs757SpringControls`: the rudder trim, the aileron trim, the alternate stabilizer trim, the manual cabin altitude switch, and the seven P61 test switches) is always released, the release is read back, and it is written again while the switch reads off its rest value. `BBS757Definition.HoldSpringAsync` writes the hold, writes it again at the control's re-write gap, and at the end of the hold calls `ReleaseSpringAsync`: the release written, the switch read fresh `ReleaseReadBackMs` (250 ms) later, and the release written again while it does not read rest, `MaxReleaseWrites` (3) in all. A switch still off rest then is read and released in the background every `ReleaseRetryIntervalMs` (2 s) for up to `ReleaseRetryForMs` (60 s), and the pilot hears "{name} switch did not return" and, once it does, that it returned. The waits of a hold are never canceled: a switch to another profile still waits out the hold and releases, and a hold that fails part-way is released at once.
- Why. Measured 2026-10-28. Each trim switch rests on 1; 0 trims left or nose down, 2 right or nose up. The cockpit's switch writes the hold value while the mouse is held and 1 when it is let go; nothing in BlueBird's XML returns it to 1 by itself, and BlueBird's module trims every frame while the switch is off 1. A release that is lost therefore runs the trim to its stop. It happened twice during the measurement, when a tool re-ran a write over and over: the rudder trim ran to -17 units and later to +16.7 (its range is -17 to +17; about 0.85 units a second, so about 20 s from center to the stop). The alternate stabilizer trim moves about 0.27 to 0.3° a second and the aileron trim about 0.06 yoke units a second.
- The manual cabin altitude switch rests on 4 (0 to 3 descend, 5 to 8 climb, only with Mode Select at MAN) and BlueBird's XML writes 4 back within about a second of an outside write, so its hold is written again every 500 ms. A P61 test switch returns to neutral at once by itself, so a test runs only while its position is written again (every 30 ms for 3 s); it gets the same verified release.
- A press made just before the app closes has no release: there is no shutdown seam. `Bbs757SpringControlsTests` pins the hold and the release (`Release_always_runs`, `Release_is_resent_until_the_switch_rests`, `Release_stops_once_the_switch_reads_rest`). → [b757.md](../b757.md)

## B757-16

- The brightness of the two PFDs is the L:vars `B757_PFD_1_SCREEN_KNOB` and `B757_PFD_2_SCREEN_KNOB`. In the map they are the state vars of the ADI knobs' rows (nodes `B757_ADI_1_LCD_KNOB` and `B757_ADI_2_LCD_KNOB`, "PFD Brightness" on each EFIS control panel), taken in through the curation's `direct_positions` with the positions 0 Minimum, 20 Half and 40 Full, and written directly. The model's nodes that are themselves NAMED `B757_PFD_1_SCREEN_KNOB` and `B757_PFD_2_SCREEN_KNOB` stay out of the map: their clicks write `BBS757_RASTER_BRIGHTNESS_CA` and `BBS757_RASTER_BRIGHTNESS_FO`.
- Why. Read from BlueBird's brightness code on 2026-10-28 and measured the same day: the code reads one knob variable for each display and sets the display's output to knob ÷ 40 × 1.5, never below 0.1. Written through the calculator, `B757_PFD_1_SCREEN_KNOB` moved `B757_PFD_BRIGHTNESS_L` at once: 40 gave 1.5, 20 gave 0.75, 0 gave 0.1 (a knob at 0 dims its display to its minimum and does not switch it off, so there is no Off position). The ND, EICAS and CDU knobs measured the same way (30 gave 1.125, 15 gave 0.5625). Nothing in the package reads the raster variables, and they are not among BlueBird's 2,173 L:var names: a row built on them would show a knob that turns and dims nothing.
- Every knob reads 40 on load. The cockpit's mouse stops lower (the vendor's clicks clamp at 30, and at 20 on the first officer's ADI knob), but the code takes 0 to 40, so the positions are not held to that clamp. `Bbs757ControlMapTests` pins it (`Each_display_brightness_knob_writes_the_var_BlueBirds_brightness_code_reads`, and the test that no row's state var is a raster variable). → [b757.md](../b757.md)
