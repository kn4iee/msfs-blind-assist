# BlueBird 757 EHSI reader rules, full text

The rule lines are in `.claude/rules/b757-ehsi.md`; the shared 757 rules are in [b757.md](b757.md). Background: [docs/b757.md](../b757.md).

## B757-36

- `Bbs757EhsiReader` reads the flown legs, the legs, a pending modification and the points all or nothing. The route is built from vectors BlueBird reallocates while the reader walks them, so a torn read could drop a leg or join two across a gap, and the pilot would hear a route that is not flown. A torn vector, a leg or label pointer outside the module, a count over the layout's cap, or a non-finite or out-of-range position makes the whole reading `Corrupt`, with no partial route. A discontinuity (seen live 2026-11-11 in KOLM, discontinuity, OLM, BTG, KPDX: leg type 3, +24 = 0, no label, position 0, 0) is its own leg and gives no row; the reader never draws a leg across it, as BlueBird breaks the line there. Without this a half-read route would be spoken as the route. Three cases look torn but are not, and are never `Corrupt`: the path registry is a list keyed by route id that keeps stale entries (measured live: ids 9, 10, 11 and 12 at once), so a walk that reaches its 4096-node cycle guard finds no path (no T/C, T/D or E/D), while a node outside the module stays corrupt; the path is recomputed apart from the legs and can lag them, so an E/D index at or past the route's own leg count draws no E/D; and a null selected-IRS pointer is the dark reading, as BlueBird's draw returns a black screen then. Making these corrupt would stop the reader for the flight after ten readings. Measured on BlueBird's EHSI draw and memory, 2026-11-11. Plan 26.

## B757-37

- `Bbs757EhsiText` lists a map item only where the EHSI draws it. Each item is projected with `Bbs757EhsiGeometry.Project` from the map center and rotation the nd holds, and is listed only inside `OnScreen`'s clip: a circle around the aircraft's screen point (88.7 % of the range in this build, 516 of 582 pixels; in PLAN too, where the map's center is 291 pixels above the circle's) and the screen's own edges (352 pixels either side, 157 below the aircraft). Measured 2026-11-11: KOLM at 37.5 NM, 86.5° right, is not on the screen in MAP at range 40 (beyond 60.5 % of the range sideways) but is at 160; in PLAN at 80 centered on KOLM, KSEA (37.6 NM at 41°) falls 528 pixels from the circle's center and is cut. A test of distance against the range alone would list items a sighted pilot does not see. The constants come from the layout, carried in the reading. Plan 26.

## B757-38

- On the 757, `HotkeyAction.ReadNDWaypoint` (Ctrl+W) says `Bbs757EhsiDisplay.WaypointLine`: the active waypoint's name, then the top line's distance and ETA as drawn, "no ETA" under 100 kt. The name is the active leg's: the pending modification's leg 0 while one is pending, else the route's leg 0, the leg the top line's distance is drawn to; it is said because the EHSI's top line draws no name (measured 2026-11-11: distance and NM at the left, ETA and z at the right, the heading between). It interrupts (`AnnounceImmediate`), the window open or closed, and is never muted by the Ctrl+M row, as the PMDG 737's ND line does. Without the interrupt a requested line would queue behind the reader's own. Plan 26.

## B757-39

- `Bbs757EhsiDisplay.SimInputs` lists `PLANE LATITUDE` and `PLANE LONGITUDE` because BlueBird's top-line draw reads them fresh on each call (the FMS keeps no copy; measured 2026-11-11), so the spoken distance must come from the same position. They are an input only, never compared with memory ([B757-30]). The map rows use the nd's own center, copied each frame from the selected IRS (`nd+1160`, `nd+1168`), the position the map is drawn from. Parked the two agreed to the sixth decimal; in a turn they can differ. Swapping one for the other would put the top line or the map rows off the screen's own. Plan 26.

## B757-40

- `Bbs757EhsiReader` walks plan 28's parts all or nothing, as it does the route ([B757-36]): the TCAS traffic list (`TryTcas`), the map options' navaid, airport, waypoint and NDB lists and the course lines' stations (`TryMapOptions`, `TryNavaid`, `TryPlace`, `TryCourseLines`), the two runway records (`TryRunway`), the route path's two deceleration vectors (`TryDeceleration`), a navaid leg's capability set (`TryCapabilities`) and the FIX pages' fix objects and entries (`TryFix`, `TryFixEntries`). Each is a structure BlueBird reallocates or rewrites while the reader walks it, so a torn read could drop, duplicate or misplace an item the pilot would then hear about or see listed. A pointer outside the module, a vector whose end is before its begin or that holds no whole number of entries, a count over the layout's cap, a header that changed during the walk, a name that is not text, or a position that is not finite and in range makes the whole reading `Corrupt`, never a partial list; a corrupt reading is never shown or spoken ([B757-30]). Three cases look torn but are not: a null object pointer is none (no FMS, no runway, no fix), an empty list is empty, and a FIX entries vector longer than the layout's `FixEntries` reads its first entries (the draw takes three and stops, so the rest is not on the screen; its storage must still lie inside the module). Pinned by `Bbs757EhsiTcasTests` (`A_torn_traffic_list_is_corrupt`, `More_traffic_than_the_cap_is_corrupt`), `Bbs757EhsiMapOptionsTests` (`A_torn_list_is_corrupt`, `A_list_over_the_cap_is_corrupt`), `Bbs757EhsiMapExtrasTests` (`A_runway_is_listed_by_its_nearer_end`, `Deceleration_points_are_listed_where_drawn`, `A_torn_capability_set_is_corrupt`) and `Bbs757EhsiMapGuidesTests` (`A_torn_fix_object_or_entries_vector_is_corrupt`, `A_fix_entries_vector_longer_than_the_draw_takes_reads_its_first_entries`). Plan 28.

## B757-41

- The five parts plan 28 added to `Bbs757EhsiLayout` (`Approach`, `Tcas`, `MapOptions`, `MapExtras`, `MapGuides`) are optional: a layout file written before plan 28 lacks them, and the recipe can fail to derive one in a later build while the others still derive. Such a part is null with its reason (`ApproachMissing` and the others: "not in this layout file", or the recipe's failing step) and costs only its own rows: `Bbs757EhsiText` lists one "<part>: not read: <reason>" row where the part's rows would start, in the modes where it would show something, and every plan 23 to 26 row still reads; the reader never goes unavailable for it. A part is null exactly when its reason is set: `CheckParts` throws on write and on read otherwise, so a file can never hold both or neither. Only the members marked `[LayoutFileOptional]` (the five parts and their reasons) may be absent from a file; any other member missing still fails the whole file as [WASM-26] says. Without this a file from an older generator, or one build's single failed step, would cost the pilot the whole EHSI. Pinned by `Bbs757EhsiPartsTests.A_missing_part_lists_not_read_with_its_reason` and `Bbs757EhsiLayoutPartsTests` (`A_file_without_the_parts_reads_as_missing`, `A_missing_part_keeps_its_reason`). Plan 28.

## B757-42

- BlueBird draws the map options (NAV AID, ARPT, WPT, and NDBs above range 40) by a loop over the FMS's nearest-first lists (23406, measured 2026-11-12): each round takes the next item of every switched-on list, skips the tuned stations, the undrawn kinds and classes, the origin and destination and the route's own points, counts each item within the range plus 10 NM, and stops at the end of the round where the count reaches the layout's limit (100), after the round limit (500), or when every list is used up; a skipped NDB (or a null waypoint or NDB entry) restarts the round without its end check. `Bbs757EhsiMapOptionsLoop` replays that loop over the lists the reader read, and `Bbs757EhsiText` lists only the items it drew, each inside `OnScreen`'s clip ([B757-37]). Never a plain range filter over the lists: at range 20 the KSEA gate's lists hold far more waypoints within reach than the screen shows (2 navaids, 6 airports and 92 waypoints drawn; the next ones are not), so a filter would list items a sighted pilot does not see. Pinned by `Bbs757EhsiMapOptionsLoopTests` (`Bbs757Ehsi_loop_stops_at_the_count_as_measured_at_range_20`, `Bbs757Ehsi_loop_counts_17_as_measured_at_range_80`, `Bbs757Ehsi_loop_restarts_the_round_without_its_end_check`) and `Bbs757EhsiMapOptionsTests.An_item_counted_but_outside_the_clip_is_not_listed`. Plan 28.

## B757-43

- Of what plan 28 reads, the window lists everything, and the reader says by itself only ILS mode's LOC and G/S flags (`ApproachFlags`) and the TCAS left block's words TCAS FAIL, TA ONLY, TCAS OFF and TRAFFIC (`TcasMessages`), through `Bbs757EhsiText.Changes` on the "EHSI messages" Ctrl+M row, once after the monitor's settle, with the non-interrupting announce ([B757-31]). Traffic, the map options' items, TERR, the wind, the runways, the deceleration points and the guides are rows only; TFC is the pilot's own switch and TEST the pilot's own test, so neither is spoken. A flag or word that comes or goes only because the pilot turned the EFIS selector (LOC and G/S are ILS mode's) or because the nd's gate byte (`nd+1273`) changed with the mode (TCAS FAIL and TCAS OFF are held back in PLAN and the full rose, and a failed TCAS shows TA ONLY there) is not spoken: `Changes` compares those only while the mode, or the gate, is the same in both readings. Without that the pilot would hear "TCAS OFF gone" each time PLAN is selected. Pinned by `Bbs757EhsiApproachTests.A_lost_signal_shows_the_flag_not_the_pointer`, `Bbs757EhsiTcasTests` (`A_tcas_mode_message_is_spoken_once`, `The_nds_message_gate_holds_tfc_off_and_fail_back`, `Traffic_is_listed_in_screen_order_and_not_spoken`) and each part's "never spoken" asserts. Plan 28 (the mode rule is plan 26's).

## B757-44

- Where BlueBird's EHSI draw reads an L:var (the TERR button `L:B757_ADI_1_TERR_BUTTON`, the bearing pointer selectors `L:BBS_DDRMI_LEFT` and `L:BBS_DDRMI_RIGHT`), the reader takes the value the variable's handle caches in memory, at the layout's handle value offset (the nd keeps its own copy of the TERR handle), never a SimConnect read: it is the very value the draw uses, read in the same reading as everything else, where SimConnect would add a variable and a lag. `Bbs757EhsiDisplay.SimInputs` holds only what the draw takes from the simulator through a simulator-variable handle with no value in memory: `PLANE LATITUDE` and `PLANE LONGITUDE` for the top line ([B757-39]), `AMBIENT WIND VELOCITY` and `AMBIENT WIND DIRECTION` for the wind, and `GEAR POSITION` for TERR's amber threshold, each in the units BlueBird registers it in (knots, degrees, enum), so the reader computes what the draw computes. They are inputs, never compared with memory ([B757-30]); one not delivered yet reads "not read yet" or no color word, never a stale value. Measured on BlueBird's draw and memory, 2026-11-12. Pinned by the EHSI wiring tests' simulator-input asserts and `Bbs757EhsiMapExtrasTests.Wind_reads_dashes_when_the_screen_does`. Plan 28.

## B757-45

- A leg whose kind is the layout's `CapabilityLegKind` (a navaid leg) holds two positions, and BlueBird picks one by the leg's capability set (an unordered set of ints in the leg) with its own rule, which the layout carries as `CapabilityChoices`: the first choice whose capability the set holds gives the offsets, and one marked `UnlessZero` falls back to the kind's own offsets when its position reads 0, 0. `LegPositionOffsets` applies it to the route's legs and to the FIX pages' fix objects. Never the primary position alone: FIX INFO's TCM, a TACAN with the set {9, 19, 18, 3}, holds 0, 0 there and its real position in the second (measured 2026-11-12), so the primary would put it at 0° N 0° E. Without the map extras part the rule is unknown, and a navaid fix is listed with no position rather than a wrong one. Pinned by `Bbs757EhsiMapExtrasTests` (`A_tacan_only_leg_reads_its_second_position`, `Each_branch_of_the_leg_position_rule`, `A_capability_of_19_or_13_falls_back_when_the_second_position_is_zero`) and `Bbs757EhsiMapGuidesTests.Without_the_map_extras_a_navaid_fix_is_listed_with_no_place`. Plan 28.

## B757-46

- The rows copy the condition BlueBird's draw tests, never a tidier one, even where the draw looks wrong: the pilot must hear what a sighted pilot sees. Three cases a later change might "fix": TCAS FAIL is drawn, and hides TFC, TA ONLY and TCAS OFF, only while the nd's gate byte is set; with the gate clear (PLAN, the full rose) a failed TCAS draws by its level as a working one does (`FailShown`, `TcasRows`). TERR's amber threshold is the gear-down one only while the `GEAR POSITION` input equals the layout's gear-down value, compared as the draw compares its handle (`TerrainNumber`); with the input not delivered the color is told only where both thresholds agree. The wind row shows the dashes exactly when BlueBird's show flag is clear (`WindRow`): the draw itself clears the flag under 100 kt of ground speed, with its own 4 to 6 kt hysteresis on the wind, so the reader redoes neither test. Measured on BlueBird's draw, 2026-11-12. Pinned by `Bbs757EhsiTcasTests.A_failed_tcas_with_the_gate_clear_shows_its_level`, `Bbs757EhsiMapExtrasTests.Terrain_colors_follow_the_draws_thresholds` and `Bbs757EhsiMapExtrasTests.Wind_reads_dashes_when_the_screen_does`. Plan 28.
