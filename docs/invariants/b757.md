# BlueBird 757-200 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/b757.md`, which Claude Code loads when it reads matching code. Background: [b757.md](../b757.md).

## B757-1

- Never read or register the stock `BRAKE PARKING POSITION` on the 757. Measured on 2026-10-25 (`docs/b757/evidence/live-findings.md`, session 6): with BlueBird's parking brake set, the stock variable read 0; `K:PARKING_BRAKES` left BlueBird's own `L:B757_FC_PARK_BRAKE` at 1. BlueBird's variable is the truth: the Pedestal's Control stand "Parking Brake" toggle replays the lever's own click on it, and the status row and call-out (`Bbs757Readouts.ParkingBrakeKey`, "Parking brake set" / "released") read it. A readout or a First Officer step built on the stock variable would say "released" with the brake set. `Bbs757FlightReadinessTests.The_parking_brake_is_blueBirds_own_variable_never_the_stock_one` pins that no 757 variable reads the stock name. → [b757.md](../b757.md)

## B757-2

- The CHOCKS tile on BlueBird's EFB TOGGLES, so a press is safe only when its current state is known and differs from the wanted one. It is on the Aircraft app's GROUND SERVICES page (404,556) and flips `L:BBS757_vis_chocks` (0 removed, 1 in place; measured 0 → 1 → 0 with two taps); `Bbs757EfbLayout.MayClickChocks` allows the tap only when the variable, read fresh, differs from what the pilot asked for.

  Pressing it without that read can undo what the pilot has (INITIAL CHOCKS IN PLACE puts the chocks on at every load and the same tap would put them back), and a state that cannot be read presses nothing: the window says so. After the press the state is read again and the result said from it. Measured 2026-10-25 (`docs/b757/evidence/live-findings.md`, session 6). → [b757.md](../b757.md)

## B757-3

- Never step the MCP speed target one `K:AP_SPD_VAR_INC` or `DEC` per knot in one burst. BlueBird speeds the knob's events up within a burst, as a knob turned fast: events 1-10 move the target 1 kt each, events 11-25 2 kt each, every one from the 26th 5 kt. A burst is one calculator call or several back to back; a pause of about 0.3 s starts a new one (two 10-event calls 0.25 s or 0.5 s apart moved 20 kt, not 30). Measured on 2026-10-25 after the first flight (`docs/b757/evidence/live-findings.md`, session 7): 10 events +10 kt, 20 +30, 25 +40, 30 +65, and 50 hit the 100 kt floor.
- The first flight's sets sent one event per knot in calls of 25 back to back, and its bursts fit the tiers exactly: 53 events moved the target 180 kt, and 47 drove it to the 100 kt floor. A set ended far from the typed speed, and the corrections, sent the same way, chased it.
- `Bbs757Mcp.SetSpeedAsync` therefore sends one planned burst: `Bbs757Mcp.SpeedBursts` gives the most events whose tiered sum (`Bbs757Mcp.SpeedBurstKnots`) does not pass the change. It waits `Bbs757Mcp.SpeedBurstGapMs` (600 ms, twice the reset) and sends the 0-4 kt left as a burst of its own, 1 kt an event. It corrects only in bursts of at most `Bbs757Mcp.LinearBurstMax` (10) events, each followed by that pause, so every correction event moves 1 kt. Each burst is one RPN loop (`Bbs757Mcp.SpeedBurstCode`), short for any count.
- `Bbs757McpTests` runs the set against a simulated MCP with BlueBird's tiers (every speed from 100 to 399 lands with no correction) and against one with plain 1 kt steps (the corrections converge). → [b757.md](../b757.md)

## B757-4

- The EFB load (`Bbs757EfbLayout.LoadThroughEfb`) taps FETCH SIMBRIEF OFP and then, on the FUEL page, the defuel question's YES at (400,648) after IMPORT FROM SIMBRIEF and after START BOARDING, whether or not the question is up: that spot is empty background on the FUEL page (measured 2026-10-25, session 7). The fetch asks "switch the aircraft's weight units to the plan's?" whenever the two differ, and that question's YES is at (390,658), 14 px away; the window cannot see which question is on screen.
- So the load runs only when `Bbs757Loadsheet.UnitsRefusal` returns null: the plan's units (`Bbs757SimBriefPlan.Units`, from `params/units`) equal BlueBird's `units` setting read from its work folder. Different units refuse before any tap ("Your SimBrief plan is in kilograms and the aircraft in pounds. Fetch the SimBrief flight and accept its units, or create the plan in pounds, then try again."), and so do unreadable ones, since nothing then says whether the fetch would ask. Without the check, a load could switch the aircraft's units with a tap meant for the defuel question. `Bbs757LoadsheetTests` pins the refusals; `Bbs757EfbTests` pins the sequence.
- That check covers only a question the load's own fetch would raise. An earlier "Fetch SimBrief flight" with a plan in other units leaves the question up, unseen, and the refusal's own way out ("create the plan in pounds") then lets the next load past the units check while it is still there (the final review of Task 11). So that button fetches the same plan through the app to learn its units, and `Bbs757UnitsQuestion` counts the question as up on the tablet page the fetch ran on until Accept units or Keep units presses its answer, or a flight load makes a new page; a later fetch in matching units on the same page leaves it up (if the question is modal, that fetch's presses may never have arrived). While `Bbs757UnitsQuestion.MayBeOpen` holds for the page the tablet reports, the load refuses: "BlueBird is asking whether to switch the weight units. Press Accept units or Keep units first." `Bbs757EfbTests` pins it. → [b757.md](../b757.md)
