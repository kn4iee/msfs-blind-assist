# BlueBird 757-200 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/b757.md`, which Claude Code loads when it reads matching code. Background: [b757.md](../b757.md).

## B757-1

- Never read or register the stock `BRAKE PARKING POSITION` on the 757. Measured on 2026-10-25 (`docs/b757/evidence/live-findings.md`, session 6): with BlueBird's parking brake set, the stock variable read 0; `K:PARKING_BRAKES` left BlueBird's own `L:B757_FC_PARK_BRAKE` at 1. BlueBird's variable is the truth: the Pedestal's Control stand "Parking Brake" toggle replays the lever's own click on it, and the status row and call-out (`Bbs757Readouts.ParkingBrakeKey`, "Parking brake set" / "released") read it. A readout or a First Officer step built on the stock variable would say "released" with the brake set. `Bbs757FlightReadinessTests.The_parking_brake_is_blueBirds_own_variable_never_the_stock_one` pins that no 757 variable reads the stock name. → [b757.md](../b757.md)

## B757-2 (retired: the 757 EFB taps no blind chocks press since plan 18; the tile shows its state and the pilot presses it)

- The CHOCKS tile on BlueBird's EFB TOGGLES, so a press is safe only when its current state is known and differs from the wanted one. It is on the Aircraft app's GROUND SERVICES page (404,556) and flips `L:BBS757_vis_chocks` (0 removed, 1 in place; measured 0 → 1 → 0 with two taps); `Bbs757EfbLayout.MayClickChocks` allows the tap only when the variable, read fresh, differs from what the pilot asked for.

## B757-3

- Never step the MCP speed target one `K:AP_SPD_VAR_INC` or `DEC` per knot in one burst. BlueBird speeds the knob's events up within a burst, as a knob turned fast: events 1-10 move the target 1 kt each, events 11-25 2 kt each, every one from the 26th 5 kt. A burst is one calculator call or several back to back; a pause of about 0.3 s starts a new one (two 10-event calls 0.25 s or 0.5 s apart moved 20 kt, not 30). Measured on 2026-10-25 after the first flight (`docs/b757/evidence/live-findings.md`, session 7): 10 events +10 kt, 20 +30, 25 +40, 30 +65, and 50 hit the 100 kt floor.
- The first flight's sets sent one event per knot in calls of 25 back to back, and its bursts fit the tiers exactly: 53 events moved the target 180 kt, and 47 drove it to the 100 kt floor. A set ended far from the typed speed, and the corrections, sent the same way, chased it.
- `Bbs757Mcp.SetSpeedAsync` therefore sends one planned burst: `Bbs757Mcp.SpeedBursts` gives the most events whose tiered sum (`Bbs757Mcp.SpeedBurstKnots`) does not pass the change. It waits `Bbs757Mcp.SpeedBurstGapMs` (600 ms, twice the reset) and sends the 0-4 kt left as a burst of its own, 1 kt an event. It corrects only in bursts of at most `Bbs757Mcp.LinearBurstMax` (10) events, each followed by that pause, so every correction event moves 1 kt. Each burst is one RPN loop (`Bbs757Mcp.SpeedBurstCode`), short for any count.
- `Bbs757McpTests` runs the set against a simulated MCP with BlueBird's tiers (every speed from 100 to 399 lands with no correction) and against one with plain 1 kt steps (the corrections converge). → [b757.md](../b757.md)

## B757-17

- BlueBird's settings files, `efb_settings.json` and a `liveries\<registration>-opt.json` for each registration flown (in the aircraft's `work` folder; `Bbs757WorkFolder.Find` picks the newest), are written only through `Bbs757SettingsFile.Save` (`SaveToRegistrations` calls it for each registration file) and only while `Bbs757SimGuard.SettingsWritable` holds: no simulator process runs, BlueBird's settings file exists, and the check that looked for the processes did not fail. Measured 2026-10-27 (`docs/b757/evidence/efb-settings.md`, section 1; MSFS 2024 1.9.21.0, `bluebirdsim-aircraft-757-200` 0.1.0, BBS Nest running, registration G-BBS75; tablet taps through the EFB agent, both files read in full after each tap): BlueBird reads both files once, when the 757 loads. While it is loaded an edit is ignored, and BlueBird writes its own copy back over the file when its Settings app or a Settings section opens and on every change made on the tablet (every tap was in the file when it was read 1.3 s later; opening Settings > Livery options rewrote `G-BBS75-opt.json`, unchanged since 25 October). A value written then is ignored and replaced by that copy.
- A write while the 757 is not loaded takes, at the next load: `loading_speed` 2 and `irs_align_time` 2, written with the simulator at the main menu, were in the file when BlueBird loaded, which then wrote the file itself with 2 and 2, and Settings > Aircraft showed QUICK and 2 MIN (ending the flight did not write the file; not checked: an IRS alignment or a boarding at those rates, and "Restart flight"). An aircraft can also stay loaded behind the simulator's main menu, so the screen cannot say whether the 757 is loaded. The one safe moment is with no simulator process at all.
- A check that fails counts as running. `Bbs757SimGuard.Check` looks for processes named `FlightSimulator2024` (MSFS 2024) and `FlightSimulator` (MSFS 2020): any found is `Running`, a process list that could not be read is `Unknown` (the reason goes to debug.log, once), else `NotRunning`. `SettingsWritable` is true for `NotRunning` alone, and `Unknown` is `Bbs757SimState`'s first member, so a state nobody set is read-only too. The guard asks Windows itself and not `Utils/SimulatorDetector`, whose "Unknown" answers both "none runs" and "the check failed". `Save` takes the guard as its `mayWrite` delegate and asks it before it reads the file and again just before it writes, as the simulator may have started since the last one-second check of the 757 EFB settings window (Shift+T on the 757 with no simulator running); that window passes a fresh `Check` each time. `Bbs757SimGuardTests` pins the guard and `Bbs757SettingsFileTests` the two asks.
- That window is the only one that writes. Shift+T asks the same guard on each press (`Bbs757EfbWindowChoice.For` over `Bbs757SimGuard.Check`) and opens the settings window only for `NotRunning`; with a simulator running, or a check that failed (`Unknown`, which the guard treats as running), it opens the tablet window, which never writes BlueBird's files: a press there changes a setting through BlueBird's own tablet, and the file is only read to judge it (B757-20). `Bbs757EfbWindowChoiceTests` pins the choice for each state.
- One value's bytes change, and nothing else. `Bbs757SettingsFile.Edit` walks the file with a `Utf8JsonReader`, finds the token of the value at the dotted key path (by byte offset, so a key of the same name elsewhere cannot be hit) and replaces exactly those bytes with `Bbs757Value.ToJson`, which is always invariant: a float keeps its decimal point (`1.0`, never `1,0`) and an integer its plain minus under de-DE and sv-SE. Every other byte stays as BlueBird wrote it, a UTF-8 byte order mark included. The result is then parsed and checked (`Verify`): the value reads back, and every other value has the same text in the same order. It refuses rather than guesses, and the window says why (`Couldn't save <label>: <reason>`): a file that is not JSON, a key written twice on the path (which one BlueBird reads is unknown), a missing key, an object or list where a value belongs, a value of another type, text that cannot be read (an unpaired surrogate escape). A registration setting is saved in every registration's file, each on its own: one that cannot be changed is named ("Saved for 2 of 3 registrations; G-XXXX: the file is in use.") and the others are kept (the one exception is a group's switching-off of a callout that a file lacks, below).
- The replacement is atomic and the files are never created. The changed bytes are written to `<file>.msfsba-tmp` in the file's own folder, flushed to disk, and moved over the file (`File.Move` with overwrite): a rename within one folder, so a crash leaves the old file or the new one, never half of one. A failure removes the temp file and leaves the file as it was. `File.Replace` is not used: with no backup name it can lose the file (error 1176). `SettingsWritable` is false without BlueBird's settings file, and the window then says "BlueBird hasn't created its settings yet. Load the 757 once, then close the simulator to change them."; a save that finds its file gone refuses ("BlueBird's settings file is missing"). The accepted race: a delete in the milliseconds between a save's read and its move, with no simulator running, would let the move recreate the file, with BlueBird's own content and the one change.
- Before a file's first write, `Bbs757SettingsBackup.BeforeFirstWrite` copies it as it was to `%APPDATA%\MSFSBlindAssist\backups\bbs757\<folder key>\<file name>`, replacing the copy an earlier session left (one copy for each file). It does so once for each file for the life of the settings window's `Bbs757SettingsBackup` (the window is made at the first Shift+T that finds no simulator, hidden by Escape and shown again by the next one, and disposed when the profile switches away from the 757), so the copy holds the file from before the window's first change; a window made again after a profile switch copies the already-changed file on its first write, replacing that copy. The folder key is the first 8 hex digits of SHA-256 over the file's folder path, upper-cased invariantly (never `string.GetHashCode`, which differs from one process to the next), so the MSFS 2020 and 2024 work folders, or a registration flown in both, keep a copy each. A copy that fails is not tried again and never stops the write.
- The files hold the pilot's SimBrief ID, Hoppie logon code and SayIntentions ACARS key. The window shows them in plain text, and they are never logged: a save, or a refusal by the file layer, logs the file's name (`efb_settings.json`, `G-BBS75-opt.json`, never its folder) and its key and, only when `Bbs757Setting.MayLog` allows (false for those three), its value; a refusal before any write (`Bbs757SettingsSave`'s check that every key reads) logs the same without a file name.
- Only values BlueBird itself stores. `Bbs757EfbSettings` lists what the tablet shows: for each setting its file and key, the tablet's label, the tablet's words and the value BlueBird stores for each word, all measured by changing the setting on the tablet and reading both files (evidence sections 2 to 7), with three exceptions the catalog's summary names: Hoppie ACARS's On (taken by type: switching it on could log on to Hoppie with the owner's code), the "not set" values of the tablet's AIRAC data boxes (`simbrief_id` -1, and "" for the two codes; taken from earlier notes, not measured, as section 8 was not tapped) and the TOD pause distance's range of 1 to 999 (a ruling: the keypad's limits were not measured; 1 was kept through a load on 2026-10-28, 999 is not yet checked). The random failure frequency's slider writes only its own steps, 1x to 1000x along the tablet's continuous slider, which BlueBird stores as any float in that range. `Bbs757EfbSettings.WritesFor` plans every save and throws `ArgumentException`, before it returns a write, for a switch or choice value that none of the setting's choices stores and a slider value that is none of its steps; a number or text box's value comes from `TryParseEntry`, within the catalog's range. A key the tablet does not show for this aircraft (`units` on its own, `options.model_visibility.*`, `options.general.allow_capture_gs_before_loc`, the charts, map and debug keys) is not in the catalog, so nothing can change it. `Bbs757EfbSettingsTests` pins the measured values and the refusal.
- The tablet applies three rules of its own when a control changes, and the app, writing the files itself, must apply each (evidence section 9). Apart from them no control changed a second key: every General, Aircraft, AIRCRAFT app, Livery options, Callouts and Cabin audio control was checked against both whole files after a tap. Hoppie ACARS and the three boxes of the tablet's AIRAC data page (SimBrief ID, Hoppie logon code, SayIntentions ACARS key) were not tapped, so whether they write a second key is unmeasured. `WritesFor` keeps the first two and the window's rows the third:
  - Units writes two keys: `options.general.weight_unit` in every registration file (Imperial "lbs", Metric "kg") and `units` in `efb_settings.json` (1, 0). `WritesFor` returns the setting's own write, then its `Also` key with the chosen word's `AlsoStored`; the Units row reads "Differs between BlueBird's files" when the registrations agree on a unit and `units` reads but holds another value (`Bbs757SettingsRows.LinkedDiffersText`).
  - An exclusive callout group switches its others off first. Switching on one of 2500 and Radio altimeter (2500), of Plus hundred (DH + 100) and Approaching DH (DH + 100), or of Minimums, Minimums minimums, Minimum, Decide and Decision height writes false for each other member of its group, in catalog order, and then its own true, so a write that fails halfway leaves a state the tablet itself can produce. `Bbs757SettingsSave.Run` says `<label> turned off` for each that showed on. Switching one off changes only itself. The switching-off of the other members is the one write that a missing key does not refuse: `Run` does not check those first, and a registration file that lacks such a callout counts as done (a callout BlueBird does not have cannot be on), so one older livery file never blocks the group, while the saved callout's own key and a linked key keep the strict rule (a key that no registration file has, or a linked key the settings file lacks, refuses the whole change before anything is written; a key that only some registration files lack is saved in the others, and each file without it is named; `Bbs757SettingsSaveTests` pins both). BlueBird reads a missing callout as off: measured 2026-10-28 (in-sim check 7 of the handoff of the settings window, then a tab of the 757 EFB window), with `options.egpws_callouts.minimum` removed from `G-BBS75-opt.json` before a load, BlueBird wrote it back as false, in its usual place, when Settings > Livery options opened.
  - The announcement categories stay put while Announcements is off. Safety related and Non-safety related announcements (`EnabledBy` Announcements) take no change unless Announcements reads On in every registration file that has it: their rows (`Bbs757SettingRow.CanEdit`) stay focusable and readable, do not change, and say "Turn on Announcements to change this." Switching Announcements off leaves their stored values as they were.

  `Bbs757EfbSettingsTests`, `Bbs757SettingsSaveTests` and `Bbs757SettingsRowsTests` pin the three. → [b757.md](../b757.md)

## B757-18

- Every press on the 757 tablet window goes through `Bbs757EfbPressRunner`, which reads the tablet again from the module's memory right before the tap and taps the point that fresh read gives, never a point from the read the window was shown. The tablet is read from WASM memory (`Bbs757EfbModelReader`, not a screenshot, not OCR), so a press asks "where is the control now?" and "did the page change?" by re-reading the model (`Bbs757EfbPressIo.Read`), never by comparing pictures. The control is found in the new read (`Bbs757EfbPress.Relocate`) and tapped where it is now (`Bbs757EfbPressIo.Tap`, the Coherent agent's click, at the point `Bbs757EfbPress.TapPoint` gives); a control that is gone, or has turned into text (START BOARDING became "Boarding… 10 min"), is not tapped and the runner says "{label} is no longer on the tablet." What a press says once it is done is the runner's too, once, as the window's alert: a pressed control's new words whatever its key ("Req fuel truck" becoming "Requesting…", a door's "Left FWD: Open"), a tab that became the current one ("Hydraulic (current)", `Bbs757EfbPress.TabOutcome`), or that the press changed nothing (`Bbs757EfbPress.ButtonOutcome`), each control named as the window names it (`Bbs757EfbPress.SpokenName`: sentence case, a label first); the window says nothing of a control's words on its own.
- `Bbs757EfbPress.Relocate` takes, in this order: none when the two reads are of different pages; the control with the same key; the control of the same kind whose box overlaps the pressed one's by at least 0.6 (intersection over union, the best overlap first), which is a tile whose words changed in place ("Req fuel truck" becoming "Requesting…") and keeps its box give or take the few pixels the reader's box varies by; the control of the same kind that overlaps the pressed box at all and has the same words once the state word that ends them is left out ("Chocks, on", "Left FWD: Closed"), which is a tile that moved a little; else none. A neighbor with other words that covers the place in part is never taken, as tapping it would press another control (`Relocate_never_takes_a_control_with_other_words`).
- Whether the page changed is the model's fingerprint (`Bbs757EfbPress.PageUnchanged`, which skips the top bar and the notices): a change in the top bar or the notification panel alone is not a change of the page, so a countdown ticking or a notice arriving right after a tap is not mistaken for the tap's effect; anything on the page itself changing is, a slider's knob read from memory included (its place in whole percent, as the window shows it: a zoom button's tap moves only the knob). `Bbs757EfbPressRunner.WaitForChangeAsync` re-reads until the page changes or a timeout. Memory holds the whole page, on- and off-screen, and this build scrolls on a drag, not the wheel.
- Where a control is tapped. Each page control (one of the model's items) carries its clip (`Bbs757EfbItem.Clip`): the drawn rectangle of the scrollbox it sits in, the page area for a control in none (`Bbs757EfbScreen.PageArea`: the content area with the app's title row above it, where Systems keeps its page menu; plan 21, Task 7). `Bbs757EfbPress.TapPoint` clips the control vertically to its own clip: x stays the reader's `Hit.X`, y is the reader's when the whole box shows, else the middle of the strip that shows; with under `MinShownPx` (6) of the control showing it gives none (Settings, Aircraft's last switch shows whole at the end of the page's scroll, drawn at 1000.5; a strip of it shows only mid-scroll, and a 10.2 px strip was measured to take a tap, 2026-11-07). Where a control is drawn comes from the scrollbox's content offset, never its scrollbar thumb (B757-26). A control outside the page's items (the side menu, the top bar, a question's answers) keeps its `Hit`. So a page control is tapped only within its clip's top and bottom, never at a point from outside it. The model's `Viewport` and `Scrollable` describe the one scrollbox that scrolls, the first wrapping a taller stackbox (Settings' pages); an inner scrollbox that holds a text (the ACARS dashboard's route, Weather & NOTAM's report, the Checklist's lines) makes no page scroll, and the controls around it are clipped to the page area. The final review of plan 20 found that taking the largest scrollbox as every control's viewport (C1) left REFRESH SIMBRIEF OFP, Weather's tabs and the Checklist's RESET with no tap point at all; `Every_control_of_every_page_is_tapped_where_it_shows_or_scrolled_to` runs every committed tree. When a control has no tap point, the runner drags the page (`Bbs757EfbPress.DragFor`, through `CoherentBbs757EfbClient.DragAsync`, at most `MaxScrollSteps` times), re-reads and relocates the control each time; `DragFor` gives a drag only for a control whose clip is the scrollbox that scrolls, on a page whose model is `Scrollable`, since on any other a drag pans what lies under it (the map, a diagram) or moves nothing under the control. The drag is a run of the Coherent agent's, which the client waits for by its status, under the run lock, before the runner reads and taps again (the final review's I7: a fixed wait let the tap after it be refused as busy). A control that never comes into view is not tapped: "{name} could not be brought into view, not pressed." (`Bbs757EfbBridgeTests`: `A_control_below_the_viewport_is_scrolled_into_view_before_its_tap`, `The_last_row_of_the_real_settings_page_is_scrolled_into_view_and_tapped_from_the_top`, `A_control_that_never_comes_into_view_is_not_tapped`, `A_control_outside_an_inner_scrollbox_is_tapped_once_with_no_drag`; `Bbs757EfbPressTests`: the `TapPoint` and `DragFor` tests).
- Three more cases tap nothing. An answer to a question (YES, NO, OK, CANCEL) is keyed alike under every question (`q:YES`), so it is the one pressed only under the same question (`Bbs757EfbPress.SameQuestion`, which compares letters and digits, as the words wobble from read to read, "defuel?" and "defuel ?"); under another question it taps nothing and says nothing, since the read that found the new question said it, and with no question up it is gone, and said so. A question that came up over the page since the read takes no tap on the page under it: only the top bar and the question's own answers press, and a press on anything else taps nothing and says nothing, since the read that found the question said it. And a side-menu entry or a home-screen app whose page the tablet shows already (pressed twice, the first press took it there) taps nothing and says nothing: its tap is done.
- Why. A tap from an older read lands on whatever is there now. Measured 2026-10-29 (`docs/b757/evidence/tablet-presses.md`): after many taps BlueBird shows a notification at the top right for about 10 seconds, and it covered a page's first switch right after a tap. With OCR (plan 18) a tile the notification covered dropped out of the read, so the relocation found it gone and nothing was tapped. Read from memory (plan 21) it does not drop out: the top bar app draws the pop-up and its notification list from its own fields, not as controls, so the re-read still finds every control under them (the final review of plan 21, I1). So the press reads the panel as well: the layout's `OverlayPanelShown`, `OverlayPanelRect` and `OverlayPanelHeight` (about [1039.75,38 349.25x118] under a pop-up, 480 tall with the list open, measured 2026-11-07), read into `Bbs757EfbScreenModel.NoticePanel` while the shown byte is 1. A page press whose mouse-down point it covers, a tap's (`TapAsync`, for every tap: a control's, a slider's choice or percent place, a drop-down's face and row) or a page drag's (`LocateAsync`), is not made: "{name} is under a BlueBird notification, not pressed." (`Bbs757EfbPress.UnderNotice`, `Bbs757EfbPress.UnderNoticeText`), said at once, as the open-list check (B757-27) says its own, and checked before it, since the panel is drawn over the page and its lists. It is a precision check of where the control can be tapped now (B757-19); the pilot presses again once the pop-up has gone (about 10 s). The tap point is inside the control's own rectangle in memory, clipped to the viewport, so a reader that named a control wrongly still cannot land a tap on another control; the re-read and the relocation keep the tap on the control the pilot pressed when the tablet has moved on.
- `Bbs757EfbBridgeTests` pins the runner against a fake tablet (`A_press_reads_relocates_and_taps_the_tile_in_place`, `A_press_on_a_moved_control_taps_the_new_point`, `A_press_on_a_vanished_control_taps_nothing_and_says_so`, `A_control_that_turned_into_text_is_gone`, `A_control_a_new_question_covers_is_not_tapped`, `A_question_over_the_page_holds_back_a_page_press` (the live fuel input dialog over the Fuel page, plan 21), `A_question_raised_by_a_choice_step_stops_the_steps`, `A_control_under_a_BlueBird_notification_is_not_tapped`, `A_drop_down_under_a_BlueBird_notification_is_not_opened`, `A_page_drag_that_would_press_on_a_BlueBird_notification_is_not_made`, `A_yes_pressed_on_one_question_is_never_tapped_on_another`, `A_yes_whose_question_was_answered_meanwhile_is_gone`, `A_side_menu_entry_pressed_again_on_its_own_page_taps_nothing_and_says_nothing`) and `Bbs757EfbPressTests` the relocation (`Relocate_finds_a_moved_control_by_its_key`, `Relocate_finds_a_tile_whose_state_words_changed`, `A_control_the_notification_list_covers_is_gone_and_the_others_are_found`, `Every_control_of_a_real_page_is_found_again_on_another_capture_of_it`), the notification panel (`The_notification_panel_is_read_while_it_shows_and_covers_what_lies_under_it`, `The_notification_panel_round_trips_through_the_tree_format_and_is_no_page_change`) and the fingerprint (`The_fingerprint_covers_the_top_bar_the_notices_and_the_question`, `The_page_is_unchanged_when_only_the_top_bar_or_the_notices_differ`).
- How to apply. A new way to press, or a new tap added to an extra, finds its point as the runner does: a fresh memory read, the `Bbs757EfbPress.PageUnchanged` check, and `Relocate` to find the control in the new read. A slider with choices taps, reads back and steps toward the choice (`Bbs757EfbPress.NextChoiceX`, at most `MaxSliderTaps` taps): each step's x is the last tap's moved a third of a choice's width (at least 4 px) toward the wished choice, the read after that tap saying which way, kept on the track located before the first tap; its row comes from that read. → [b757.md](../b757.md)

## B757-19

- Never add a refusal to a press in the 757 tablet window. The owner's ruling of 2026-10-29, made after the measurement in `docs/b757/evidence/tablet-presses.md` and overturning the read-only ruling of 2026-10-27: every control the reader offers can be pressed as a sighted pilot presses it, and nothing refuses a press. In the owner's words: "If a user wants to tap Remove All with the GPU connected, they absolutely should be able to do just that." So the window taps REMOVE ALL with external power on line, a cockpit preset on the ground or in the air, SAVE and LOAD USER CONFIG, and the AIRAC page's UPDATE and REMOVE as the tablet labels them, and the Coherent agent refuses no click anywhere on the tablet. The owner made one exception on 2026-10-30, which no press meets: the EFB colors theme is offered as no control in the tablet window, only as a note, and as no choice in the settings window, which offers only a way back to Dark blue (B757-21).
- The ruling it overturned. The team's review of 2026-10-27 (`docs/b757/evidence/flight-11.md`, section 8) made the tablet reader read-only: a control placed by OCR must never be pressed, since a misread could become a press on the wrong control. It rested on Windows OCR's reading.
