# BlueBird 757-200 — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/b757.md`, which Claude Code loads when it reads matching code. Background: [b757.md](../b757.md).

## B757-1

- Never read or register the stock `BRAKE PARKING POSITION` on the 757. Measured on 2026-10-25 (`docs/b757/evidence/live-findings.md`, session 6): with BlueBird's parking brake set, the stock variable read 0; `K:PARKING_BRAKES` left BlueBird's own `L:B757_FC_PARK_BRAKE` at 1. BlueBird's variable is the truth: the Pedestal's Control stand "Parking Brake" toggle replays the lever's own click on it, and the status row and call-out (`Bbs757Readouts.ParkingBrakeKey`, "Parking brake set" / "released") read it. A readout or a First Officer step built on the stock variable would say "released" with the brake set. `Bbs757FlightReadinessTests.The_parking_brake_is_blueBirds_own_variable_never_the_stock_one` pins that no 757 variable reads the stock name. → [b757.md](../b757.md)

## B757-2

- The CHOCKS tile on BlueBird's EFB TOGGLES, so a press is safe only when its current state is known and differs from the wanted one. It is on the Aircraft app's GROUND SERVICES page (404,556) and flips `L:BBS757_vis_chocks` (0 removed, 1 in place; measured 0 → 1 → 0 with two taps); `Bbs757EfbLayout.MayClickChocks` allows the tap only when the variable, read fresh, differs from what the pilot asked for.

  Pressing it without that read can undo what the pilot has (INITIAL CHOCKS IN PLACE puts the chocks on at every load and the same tap would put them back), and a state that cannot be read presses nothing: the window says so. After the press the state is read again and the result said from it. Measured 2026-10-25 (`docs/b757/evidence/live-findings.md`, session 6). → [b757.md](../b757.md)

## B757-3

- Never step the MCP speed target one `K:AP_SPD_VAR_INC` or `DEC` per knot in one burst. BlueBird speeds the knob's events up within a burst, as a knob turned fast: events 1-10 move the target 1 kt each, events 11-25 2 kt each, every one from the 26th 5 kt. A burst is one calculator call or several back to back; a pause of about 0.3 s starts a new one (two 10-event calls 0.25 s or 0.5 s apart moved 20 kt, not 30). Measured on 2026-10-25 after the first flight (`docs/b757/evidence/live-findings.md`, session 7): 10 events +10 kt, 20 +30, 25 +40, 30 +65, and 50 hit the 100 kt floor.
- The first flight's sets sent one event per knot in calls of 25 back to back, and its bursts fit the tiers exactly: 53 events moved the target 180 kt, and 47 drove it to the 100 kt floor. A set ended far from the typed speed, and the corrections, sent the same way, chased it.
- `Bbs757Mcp.SetSpeedAsync` therefore sends one planned burst: `Bbs757Mcp.SpeedBursts` gives the most events whose tiered sum (`Bbs757Mcp.SpeedBurstKnots`) does not pass the change. It waits `Bbs757Mcp.SpeedBurstGapMs` (600 ms, twice the reset) and sends the 0-4 kt left as a burst of its own, 1 kt an event. It corrects only in bursts of at most `Bbs757Mcp.LinearBurstMax` (10) events, each followed by that pause, so every correction event moves 1 kt. Each burst is one RPN loop (`Bbs757Mcp.SpeedBurstCode`), short for any count.
- `Bbs757McpTests` runs the set against a simulated MCP with BlueBird's tiers (every speed from 100 to 399 lands with no correction) and against one with plain 1 kt steps (the corrections converge). → [b757.md](../b757.md)

## B757-4

- The EFB load (`Bbs757EfbLayout.LoadThroughEfb`) taps FETCH SIMBRIEF OFP and then, on the FUEL page, the defuel question's YES at (400,648) after IMPORT FROM SIMBRIEF and after START BOARDING, whether or not the question is up: that spot is empty background on the FUEL page (measured 2026-10-25, session 7). The fetch asks "switch the aircraft's weight units to the plan's?" whenever the two differ, and that question's YES is at (390,658), 14 px away; the window cannot see which question is on screen.
- So the load runs only when `Bbs757Loadsheet.UnitsRefusal` returns null: the plan's units (`Bbs757SimBriefPlan.Units`, from `params/units`) equal BlueBird's `units` setting read from its work folder. Different units refuse before any tap ("Your SimBrief plan is in kilograms and the aircraft in pounds. Fetch the SimBrief flight and accept its units, or create the plan in pounds, then try again."), and so do unreadable ones, since nothing then says whether the fetch would ask. Without the check, a load could switch the aircraft's units with a tap meant for the defuel question. `Bbs757LoadsheetTests` pins the refusals; `Bbs757EfbTests` pins the sequence.
- That check covers only a question the load's own fetch would raise. An earlier "Fetch SimBrief flight" with a plan in other units leaves the question up, unseen, and the refusal's own way out ("create the plan in pounds") then lets the next load past the units check while it is still there (the final review of Task 11). So that button fetches the same plan through the app to learn its units, and `Bbs757UnitsQuestion` counts the question as up on the tablet page the fetch ran on until Accept units or Keep units presses its answer, or a flight load makes a new page; a later fetch in matching units on the same page leaves it up (if the question is modal, that fetch's presses may never have arrived). While `Bbs757UnitsQuestion.MayBeOpen` holds for the page the tablet reports, the load refuses: "BlueBird is asking whether to switch the weight units. Press Accept units or Keep units first." `Bbs757EfbTests` pins it. → [b757.md](../b757.md)

## B757-17

- BlueBird's settings files, `efb_settings.json` and a `liveries\<registration>-opt.json` for each registration flown (in the aircraft's `work` folder; `Bbs757WorkFolder.Find` picks the newest), are written only through `Bbs757SettingsFile.Save` (`SaveToRegistrations` calls it for each registration file) and only while `Bbs757SimGuard.SettingsWritable` holds: no simulator process runs, BlueBird's settings file exists, and the check that looked for the processes did not fail. Measured 2026-10-27 (`docs/b757/evidence/efb-settings.md`, section 1; MSFS 2024 1.9.21.0, `bluebirdsim-aircraft-757-200` 0.1.0, BBS Nest running, registration G-BBS75; tablet taps through the EFB agent, both files read in full after each tap): BlueBird reads both files once, when the 757 loads. While it is loaded an edit is ignored, and BlueBird writes its own copy back over the file when its Settings app or a Settings section opens and on every change made on the tablet (every tap was in the file when it was read 1.3 s later; opening Settings > Livery options rewrote `G-BBS75-opt.json`, unchanged since 25 October). A value written then is ignored and replaced by that copy.
- A write while the 757 is not loaded takes, at the next load: `loading_speed` 2 and `irs_align_time` 2, written with the simulator at the main menu, were in the file when BlueBird loaded, which then wrote the file itself with 2 and 2, and Settings > Aircraft showed QUICK and 2 MIN (ending the flight did not write the file; not checked: an IRS alignment or a boarding at those rates, and "Restart flight"). An aircraft can also stay loaded behind the simulator's main menu, so the screen cannot say whether the 757 is loaded. The one safe moment is with no simulator process at all.
- A check that fails counts as running. `Bbs757SimGuard.Check` looks for processes named `FlightSimulator2024` (MSFS 2024) and `FlightSimulator` (MSFS 2020): any found is `Running`, a process list that could not be read is `Unknown` (the reason goes to debug.log, once), else `NotRunning`. `SettingsWritable` is true for `NotRunning` alone, and `Unknown` is `Bbs757SimState`'s first member, so a state nobody set is read-only too. The guard asks Windows itself and not `Utils/SimulatorDetector`, whose "Unknown" answers both "none runs" and "the check failed". `Save` takes the guard as its `mayWrite` delegate and asks it before it reads the file and again just before it writes, as the simulator may have started since the last one-second check of the app's Settings tab (in the 757 EFB window, Shift+T); that tab passes a fresh `Check` each time. `Bbs757SimGuardTests` pins the guard and `Bbs757SettingsFileTests` the two asks.
- One value's bytes change, and nothing else. `Bbs757SettingsFile.Edit` walks the file with a `Utf8JsonReader`, finds the token of the value at the dotted key path (by byte offset, so a key of the same name elsewhere cannot be hit) and replaces exactly those bytes with `Bbs757Value.ToJson`, which is always invariant: a float keeps its decimal point (`1.0`, never `1,0`) and an integer its plain minus under de-DE and sv-SE. Every other byte stays as BlueBird wrote it, a UTF-8 byte order mark included. The result is then parsed and checked (`Verify`): the value reads back, and every other value has the same text in the same order. It refuses rather than guesses, and the tab says why (`Couldn't save <label>: <reason>`): a file that is not JSON, a key written twice on the path (which one BlueBird reads is unknown), a missing key, an object or list where a value belongs, a value of another type, text that cannot be read (an unpaired surrogate escape). A registration setting is saved in every registration's file, each on its own: one that cannot be changed is named ("Saved for 2 of 3 registrations; G-XXXX: the file is in use.") and the others are kept (the one exception is a group's switching-off of a callout that a file lacks, below).
- The replacement is atomic and the files are never created. The changed bytes are written to `<file>.msfsba-tmp` in the file's own folder, flushed to disk, and moved over the file (`File.Move` with overwrite): a rename within one folder, so a crash leaves the old file or the new one, never half of one. A failure removes the temp file and leaves the file as it was. `File.Replace` is not used: with no backup name it can lose the file (error 1176). `SettingsWritable` is false without BlueBird's settings file, and the tab then says "BlueBird hasn't created its settings yet. Load the 757 once, then close the simulator to change them."; a save that finds its file gone refuses ("BlueBird's settings file is missing"). The accepted race: a delete in the milliseconds between a save's read and its move, with no simulator running, would let the move recreate the file, with BlueBird's own content and the one change.
- Before a file's first write, `Bbs757SettingsBackup.BeforeFirstWrite` copies it as it was to `%APPDATA%\MSFSBlindAssist\backups\bbs757\<folder key>\<file name>`, replacing the copy an earlier session left (one copy for each file). It does so once for each file for the life of the EFB window's `Bbs757SettingsBackup` (the window is made at the first Shift+T and closed when the profile switches away from the 757), so the copy holds the file from before the window's first change; a window made again after a profile switch copies the already-changed file on its first write, replacing that copy. The folder key is the first 8 hex digits of SHA-256 over the file's folder path, upper-cased invariantly (never `string.GetHashCode`, which differs from one process to the next), so the MSFS 2020 and 2024 work folders, or a registration flown in both, keep a copy each. A copy that fails is not tried again and never stops the write.
- The files hold the pilot's SimBrief ID, Hoppie logon code and SayIntentions ACARS key. The tab shows them in plain text, and they are never logged: a save, or a refusal by the file layer, logs the file's name (`efb_settings.json`, `G-BBS75-opt.json`, never its folder) and its key and, only when `Bbs757Setting.MayLog` allows (false for those three), its value; a refusal before any write (`Bbs757SettingsSave`'s check that every key reads) logs the same without a file name.
- Only values BlueBird itself stores. `Bbs757EfbSettings` lists what the tablet shows: for each setting its file and key, the tablet's label, the tablet's words and the value BlueBird stores for each word, all measured by changing the setting on the tablet and reading both files (evidence sections 2 to 7), with three exceptions the catalog's summary names: Hoppie ACARS's On (taken by type: switching it on could log on to Hoppie with the owner's code), the AIRAC data "not set" values (`simbrief_id` -1, and "" for the two codes; taken from earlier notes, not measured, as section 8 was not tapped) and the TOD pause distance's range of 1 to 999 (a ruling: the keypad's limits were not measured). `Bbs757EfbSettings.WritesFor` plans every save and throws `ArgumentException`, before it returns a write, for a switch or choice value that none of the setting's choices stores; a number or text box's value comes from `TryParseEntry`, within the catalog's range. A key the tablet does not show for this aircraft (`units` on its own, `options.model_visibility.*`, `options.general.allow_capture_gs_before_loc`, the charts, map and debug keys) is not in the catalog, so nothing can change it. `Bbs757EfbSettingsTests` pins the measured values and the refusal.
- The tablet applies three rules of its own when a control changes, and the app, writing the files itself, must apply each (evidence section 9). Apart from them no control changed a second key: every General, Aircraft, AIRCRAFT app, Livery options, Callouts and Cabin audio control was checked against both whole files after a tap. Hoppie ACARS and the three AIRAC data boxes (SimBrief ID, Hoppie logon code, SayIntentions ACARS key) were not tapped, so whether they write a second key is unmeasured. `WritesFor` keeps the first two and the tab's rows the third:
  - Units writes two keys: `options.general.weight_unit` in every registration file (Imperial "lbs", Metric "kg") and `units` in `efb_settings.json` (1, 0). `WritesFor` returns the setting's own write, then its `Also` key with the chosen word's `AlsoStored`; the Units row reads "Differs between BlueBird's files" when the registrations agree on a unit and `units` reads but holds another value (`Bbs757SettingsRows.LinkedDiffersText`).
  - An exclusive callout group switches its others off first. Switching on one of 2500 and Radio altimeter (2500), of Plus hundred (DH + 100) and Approaching DH (DH + 100), or of Minimums, Minimums minimums, Minimum, Decide and Decision height writes false for each other member of its group, in catalog order, and then its own true, so a write that fails halfway leaves a state the tablet itself can produce. `Bbs757SettingsSave.Run` says `<label> turned off` for each that showed on. Switching one off changes only itself. The switching-off of the other members is the one write that a missing key does not refuse: `Run` does not check those first, and a registration file that lacks such a callout counts as done (a callout BlueBird does not have cannot be on), so one older livery file never blocks the group, while the saved callout's own key and a linked key keep the strict rule (a key that no registration file has, or a linked key the settings file lacks, refuses the whole change before anything is written; a key that only some registration files lack is saved in the others, and each file without it is named; `Bbs757SettingsSaveTests` pins both); that BlueBird reads a missing callout as off when it loads such a file is unmeasured (in-sim check 7 of the settings tab's handoff: remove `options.egpws_callouts.minimum` from a registration file, load the 757 and read what BlueBird writes back).
  - The announcement categories stay put while Announcements is off. Safety related and Non-safety related announcements (`EnabledBy` Announcements) take no change unless Announcements reads On in every registration file that has it: their rows (`Bbs757SettingRow.CanEdit`) stay focusable and readable, do not change, and say "Turn on Announcements to change this." Switching Announcements off leaves their stored values as they were.

  `Bbs757EfbSettingsTests`, `Bbs757SettingsSaveTests` and `Bbs757SettingsRowsTests` pin the three. → [b757.md](../b757.md)
