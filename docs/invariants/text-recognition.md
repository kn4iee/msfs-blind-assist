# Text recognition — rules in full

Each section is the complete text of one rule. Its one-line form, under the same ID, is in `.claude/rules/text-recognition.md`, which Claude Code loads when it reads matching code. Background: [text-recognition.md](../text-recognition.md).

## OCR-1

- Load the models only from a folder whose `installed.json` marker matches `TextRecognitionModels.ListVersion`; the marker is written last, after every file's SHA-256 matched; a model that fails to load removes the marker, so the next check offers the download again. → [text-recognition.md](../text-recognition.md)

Why. The files in `%APPDATA%\MSFSBlindAssist\text-recognition` say nothing about whether they can be used: a download in progress, a job that the app's close or a crash killed, a model that an antivirus program cut short or took away, and a model that cannot be loaded all leave files behind. `installed.json` is the one statement that every listed file was fetched, or found there, and hashed against the list. `TextRecognitionDownloader` writes it last, after `RemoveUnlistedFiles`, through `TextRecognitionModels.WriteMarker`, so no moment of any job, a cancelled or a killed one included, leaves a folder that reads Ready with a file unverified. Its content is `{"version":1,"files":[{"name":"…","sha256":"…"},…]}`, compact, in the list's order, UTF-8 without a byte order mark or a newline; only the `version` is read back.

`TextRecognitionModels.Check` turns the folder into one of four states. Missing: no marker, and no listed file at its size. Incomplete: some listed files at their size but no marker, or this version's marker with a file missing or cut short. Outdated: a marker of another list version, or one that cannot be read. Ready: this version's marker and every listed file at its exact size. A file counts only at its exact size (a size is cheap enough to read for every status box and every menu pick; the job's hash is the real check, OCR-4), a `.part` file and anything the list does not name are never looked at, and a check never creates the folder. `Ready_marker_with_a_file_missing_is_incomplete` and `Ready_marker_with_a_wrong_size_file_is_incomplete` pin that a model removed or cut short after the install brings the offer back.

The reader opens only on Ready (`MainForm.ShowBBS757EfbReader` asks `TextRecognitionDownloader.Installed()` first), and `PaddleOcrEngine.Load` throws when the models cannot be loaded: missing, cut short, or not the models they should be (`Load_throws_when_the_models_are_not_there`, `Load_throws_when_a_model_is_not_a_model`). The bridge reports a failed load once (`Bbs757EfbBridgeIo.OcrFailed`), and `MainForm` logs it and calls `TextRecognitionModels.RemoveMarker`, which removes the marker and nothing else. The folder then reads Incomplete with all four files at their size, so the Settings tab says "Incomplete: the files are here but not checked. Download text recognition to check them.", the offer window comes back, and "Read the tablet screen" refuses until the pilot downloads again; that job hashes the four files, fetches the damaged one and writes the marker (OCR-4). Without the removal the folder would stay Ready: the Settings tab would keep saying "Ready: PaddleOCR PP-OCRv6 small." and the offer would never return, while the reader's status told the pilot to download again, and every showing of the tablet window would load the same bad file and fail the same way.

The list version. `TextRecognitionModels.ListVersion` (1) goes up with any change to the list: other models, another file, another name. A folder with another version's marker, or a marker that is no JSON object with an integer `version`, reads Outdated: "An update is needed: this version of the app uses new text recognition files. The download is 32 megabytes." The job keeps the old marker until it writes the new one, fetches only the files whose hash differs and removes the ones the list no longer names (`An_outdated_install_is_updated_and_keeps_its_old_marker_until_the_end`, `Files_not_in_the_list_are_removed`). The release's tag (`text-recognition-1`) is not a version number, so the updater never offers it as an app update (`The_release_tag_is_no_version`).

How to apply. Decide "installed" only from `TextRecognitionModels.Check`, through `TextRecognitionDownloader.Installed()`, never from a file's presence. Write the marker only with `WriteMarker`, only after every file was verified, and remove it only with `RemoveMarker`. Any new place that loads the engine and can fail to load it does what `OcrFailed` does.

## OCR-2

- The download offer at startup and at the 757 menu pick is governed only by `UserSettings.OfferTextRecognitionFor757` (`TextRecognitionOffer.ShouldOffer`), never by a remembered "Not now"; "Read the tablet screen" without the models always offers it. → [text-recognition.md](../text-recognition.md)

Why. The owner's ruling of 2026-10-28, and the rule of 2026-08-09 that UPD-9 applies to the startup data check: a recurring prompt is governed by exactly one visible setting and behaves the same every time. A remembered "Not now" would be a second, invisible setting that the pilot can neither see nor reason about; a pilot who pressed it once, perhaps by accident, would meet the download only as the reader's refusal. So the window is offered again at every startup on the 757 and at every pick of it until the models are Ready, and what silences it is the Text recognition tab's checkbox, "Offer this download when the BlueBird 757 is selected" (`UserSettings.OfferTextRecognitionFor757`, on by default). Nothing about a dismissal is stored anywhere.

`TextRecognitionOffer.ShouldOffer(is757, settingOn, state, running)` is pure and stateless: the loaded aircraft is the BlueBird 757 profile, the checkbox is on, the models are not Ready (Missing, Incomplete and Outdated all offer) and no download is running (a second window would only repeat the first). Only three of the 32 combinations offer (`Only_three_of_the_thirty_two_combinations_offer`), and the same inputs always give the same answer (`The_same_inputs_give_the_same_answer`). "Governed only by the setting" means that the checkbox is the one thing kept between asks; the other three inputs are what the profile, the folder and the job hold at the moment.

Where it is asked. At startup, in `MainForm_Shown`, after the startup data check (`OfferMissingData`) and the PMDG SDK check (`OfferPmdgSdkSetupAsync`) and before the update check; and in `BBS757MenuItem_Click`, right after `SwitchAircraft`. Never at connect: the window is modal and waits for the pilot, and at connect the simulator has the foreground, so it would open behind it, unheard (the reason of PSDK-2).

"Read the tablet screen" is not an offer. The button on the 757 EFB window's Flight page (`BBS757EfbForm.OpenScreenReader`, which is `MainForm.ShowBBS757EfbReader`) shows the same window in place of the reader whenever the models are not Ready, whatever the checkbox says and also while a download runs (the window follows the running job). The pilot asked for the reader, and the app never reads with a worse engine: there is no Windows OCR fallback (the owner's ruling, 2026-10-28). The checkbox silences only what the pilot did not ask for.

The update check. The window is modal and comes before the update check, so the update window never opens on top of it. A download started from it can still be running when `MainForm_Shown` reaches the update check, so that check is also skipped while the text recognition download runs, as it is for the location data download (UPD-9): an update accepted then restarts the app, and `TextRecognitionDownloader.Shutdown` cancels the download without a word. The skip is logged ("Startup update check skipped: the text recognition download is running.") and the next launch checks again.

How to apply. A new place that offers asks `ShouldOffer` with the real state and shows `TextRecognitionOfferDialog`. It adds no "don't ask again" button, no stored dismissal and no timer: a second way to silence the offer is the hidden state this rule exists to prevent.

## OCR-3

- PaddleOCR runs at most `PaddleOcrEngine.ThreadsFor` threads, one read at a time, and is loaded only while the tablet screen window is shown: `Bbs757EfbBridge` holds it in a `TextRecognitionEngineSlot` released only on its own loop (the inactive branch, and when the loop ends), never under a running read. → [text-recognition.md](../text-recognition.md)

Why. ONNX Runtime uses every logical processor unless told otherwise, and the tablet is read while the simulator runs on the same PC. `PaddleOcrEngine.ThreadsFor` gives the sessions one thread per eight logical processors, at least 1 and at most 4 (`ThreadsFor_is_an_eighth_of_the_processors_from_one_to_four`): 4 on the owner's PC. The 2026-10-27 benchmark harness that chose the cap (the owner's PC, the median page of the 11 test pages) timed 466 ms with all the processors, 548 ms on 4 threads and 705 ms on 2; the extra 82 ms is what leaves the simulator its other cores. Those are that harness's timings, not the shipped reader's, which takes 334 to 503 ms a page on the 11 test pages with 4 threads (`docs/b757/evidence/tablet-ocr.md`). `MainForm` passes `Environment.ProcessorCount` and nothing else.

One read at a time. `PaddleOcrEngine.ReadAsync` takes a `SemaphoreSlim`: a second call waits its turn outside the engine, where it can be cancelled, and a failed or cancelled read leaves the lock whole (`ReadAsync_runs_one_read_at_a_time`, `A_failed_read_releases_its_copy_and_the_next_read_goes_ahead`, `A_read_cancelled_while_it_waits_never_recognizes_and_leaves_the_lock_whole`). The recognition itself, about half a second, runs on a thread-pool thread, so the caller's thread stays free.

Loaded only while the window is shown. The models are 32 megabytes on disk. Loading them takes 125 to 223 ms and raises the process's working set from about 30 MB to about 97 MB (the 757 probe's `reread`, 2026-10-29), so a pilot who never opens the tablet window pays nothing, and the models are freed when the window hides. `Bbs757EfbBridge` holds the engine in a `TextRecognitionEngineSlot<PaddleOcrEngine>`: `Get()` loads it at the first read while the window is shown (`LoadOcr`, on the bridge's loop, off the UI thread) and `Release()` frees it when the window hides.

Released only on the loop. `PaddleOcrEngine.Dispose` is not safe during a read, and every read runs on the bridge's loop, one after another. So only that loop touches the slot: `Get()` before a read; `ForgetFailure()` when it takes a retry (below; it releases nothing); `Release()` in the loop's inactive branch (the window is hidden, and no read runs between two turns of the loop); `Dispose()` in the `finally` around `RunLoopAsync` (the loop has ended). `SetActive`, `Bbs757EfbBridge.Dispose` and the UI never release it, and `RetryTextRecognition` only sets a flag. `Dispose` waits only 1.5 s for the loop, and a read can take longer; a release from there, or from a hide handler on the UI thread, would free the models under a running read.

A load that fails. The slot reports a failed load once (the bridge's `OcrFailed`, OCR-1, then the reader's status "Text recognition could not start, so the tablet cannot be read. Download it again from Settings, Text recognition.") and returns null from every `Get()` until `Release()` or `ForgetFailure()`: nothing is captured or read meanwhile. A status that takes the window's place in the meantime (the tablet could not be reached, say) gives way to the reader's status again at the next read, with no second report, so the window never blames something else (`A_later_status_never_takes_the_place_of_an_engine_that_cannot_start`).

The load is tried again after the window was hidden and shown (`A_failed_load_is_reported_once_until_released`), or when the pilot asks for the reader again with the models Ready. The status sends the pilot to download them again; "Read the tablet screen" then passes `MainForm.ShowBBS757EfbReader`'s Ready check, so OCR-1's marker rule holds, and calls `Bbs757EfbBridge.RetryTextRecognition`, which only sets a volatile flag. The loop takes it at the top of its next turn while the window is shown, before any read (`TakeTextRecognitionRetry`), with `ForgetFailure()`, which keeps a loaded engine: the next read loads again, and a load that fails again is reported again (`ForgetFailure_has_the_next_Get_load_again`, `ForgetFailure_keeps_a_loaded_engine`, `A_failed_load_is_said_once_and_tried_again_only_when_the_loop_takes_a_retry`). Without it, a pilot who did what the status said met silence: the window was still shown, so nothing hid it, and the slot kept its failure (plan 17's final review, 2026-10-29). F5 and "Read the tablet again" do not try again, since they cannot check that the models are Ready. The inactive branch and a taken retry both take back the status, so a retry that works does not keep showing the failure, and after any status the next read is forced (`Status` sets `_forceRead`), so an unchanged tablet is read again rather than left behind the status.

How to apply. Only the bridge's loop touches `_ocr`. Add no `Release`, `Dispose`, `ForgetFailure` or second `Get` anywhere else (a hide handler, `SetActive`, a menu): a request from the UI sets a flag that the loop takes, as `RetryTextRecognition` does, and a retry is asked for only after a Ready check. Never raise the thread cap without measuring what it costs the simulator; never let two reads run at once.

## OCR-4

- `TextRecognitionDownloader` keeps a model file only when its SHA-256 matched, never by its size: after a failed load all four files sit at their size with no marker, and a damaged one must be fetched again; `.part` files never count and are deleted when a job starts. → [text-recognition.md](../text-recognition.md)

Why. `TextRecognitionModels.Check` counts a file by its exact size alone. That is right for "is anything installed" (it is read for every status box and every menu pick) and wrong for "which files may the job skip". A model that fails to load leaves all four files at their size and, after OCR-1's removal, no marker: a job that skipped files by size would see nothing to fetch, write the marker over the damaged file and say "Text recognition ready.", and the next showing of the window would fail the same way, every time. Plan 17's work on the downloader found it (2026-10-29). `TextRecognitionDownloader.RunAsync` therefore hashes the files in the folder first (`IsKeptAsync`: the file is there at its exact size and its SHA-256 is the list's) and fetches the rest; the hash pass over the 32 megabytes takes a fraction of a second. `A_damaged_file_of_the_right_size_is_fetched_again_and_the_good_ones_are_not` pins it, on the test's scaled-down list: only the damaged file is requested, and the job says what it fetches ("Downloading text recognition, 21 megabytes." with the real recognizer damaged), with the milestones the verified files already cover left unspoken.

A fetched file is written to `<name>.part`, hashed again and renamed into place only when the hash matches (a mismatch is retried and, after 3 attempts, fails the job: "a file did not match its checksum"), so a file under its real name is always a verified one, and a cancel or a failure keeps those for the next job (`Cancel_keeps_verified_files_and_the_next_job_fetches_only_the_rest`, `A_checksum_mismatch_fails_and_keeps_the_verified_files`). With every file kept there is nothing to download: the job writes the marker and says only that it is ready (`Files_that_are_all_here_are_checked_and_marked_without_a_request`).

`.part` files. A `.part` file is a fetch that did not finish: the app was closed or killed, or the attempt failed. It is never resumed (the largest file is 21 megabytes and each is fetched whole, with no `Range` request and no sidecar, unlike LOC-4's 400 MB dump), never counted by `Check` (`A_part_file_never_counts`) and never trusted. `DeletePartFiles` removes them at the start of a job, before the disk check, since they may be what the space is short of (`A_killed_jobs_partial_files_are_gone_before_the_disk_is_checked`); and even a `.part` that holds the whole, correct bytes is fetched again (`A_part_file_left_by_a_killed_job_is_fetched_again`).

How to apply. Whatever decides what the job fetches compares SHA-256, never a length. `Check`'s `FilesKept` and `BytesToFetch` are for the status lines and the offer only.

## OCR-5

- Every status box and offer button reads `TextRecognitionDownloader.DisplayStatus()` (and `Installed()`), never `Status`: `Status` keeps a finished job's Ready after a failed load removed the marker, so the offer's Download button, never disabled, would read "Text recognition ready" and a press would do nothing all session. → [text-recognition.md](../text-recognition.md)

Why. `Status` is the job's last status as the job set it: after a job that ended in Ready it says Ready until the next job starts, whatever happened to the files since. The case that matters: the pilot downloads, the reader's engine then fails to load, and `OcrFailed` removes the marker (OCR-1). `Status` still says Ready, so a status box that read it would show "Ready: PaddleOCR PP-OCRv6 small." over models that cannot be used, and the offer window that "Read the tablet screen" then opens would build its Download button from the phase: it would read "Text recognition ready" and start nothing when pressed (`TextRecognitionText.OfferButton` makes a press start nothing once the phase is Ready), for the rest of the session. Plan 17's work on the downloader found it (2026-10-29).

`DisplayStatus()` is the status a box may show: the running or last job's, except that no job yet (Idle), or a finished job's Ready that the folder no longer backs (`Installed().State` is not Ready), reads as what the folder holds (`TextRecognitionText.Idle(Installed())`). A failure or a cancel stays until the next job. `A_ready_status_does_not_outlive_the_files` and `DisplayStatus_shows_the_running_or_last_job_else_the_folder` pin it. `Installed()` reads the folder fresh each time and is what the offer button's second argument and every "is it Ready" test use.

How to apply. A window or tab that shows the download calls `DisplayStatus()` once per refresh and feeds the box and the buttons from that one snapshot, so they never disagree (`TextRecognitionPanel`, `TextRecognitionOfferDialog`); the status box is a read-only `TextBox` (VAT-13) updated in place. `Status` and `IsRunning` stay for the job's own bookkeeping (`MainForm` asks `IsRunning` before the update check and for `ShouldOffer`).
